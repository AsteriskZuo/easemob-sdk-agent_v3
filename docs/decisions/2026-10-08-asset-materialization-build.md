# 决策：资产物化与构建链路（bind 时初始化）

- **日期**：2026-10-08
- **状态**：已定
- **背景**：v2 业务迁移验证暴露出缺口——模板清单 `programs` 指向 `dist/programs/*.js`，但 `.gitignore` 忽略 `dist/`，git clone 物化出的资产没有构建产物，任何业务包都跑不起来；「上传转译 + sdk bundle 注入」只在文档里，代码无实现。本决策定下物化与构建的完整链路。

## 结论

1. **构建时机 = 业务创建/更新时的绑定校验**（同步执行）。clone + install + 构建需要时间网络，失败即创建/更新失败，错误（clone/auth/install/构建/入口缺失）透传到控制台。更新同样先验后写：全部通过才落库，任何一步失败旧配置原样保留。同步阻塞是接受的取舍（构建分钟级，控制台 loading 即可）。
2. **物化 = 平台侧规范脚本**（固定流程，不依赖业务仓的 npm scripts）：clone → checkout commit → `npm ci` → 自定义钩子或默认转译 → 机械校验清单 programs 路径存在。脚本化保证任何复杂项目的初始化都走同一条规范流程，可检查、可复现。
3. **自定义初始化钩子**：资产仓库根可放约定文件 `agent.materialize.mjs`，存在则由物化脚本执行（cwd = 资产目录）；不存在则平台默认构建（下条）。简单项目零配置，复杂项目（monorepo 业务、生成代码、资源拷贝）有标准逃生口。信任级别与运行业务代码相同（v1 无沙箱，显式认账）。
4. **默认构建 = 转译，不是 bundle**：esbuild 把 `src/**/*.ts` 转译到资产缓存的 `.build/`（保持模块结构，依赖保持外部引用），`node_modules` 保留在缓存中，node 按常规向上解析。不做全量 bundle——native 模块（.node）、动态 require、`__dirname` 相对资源三类依赖打包即坏。
5. **清单 programs 指向源码**：`agent-asset.json` 的 programs 值指向 `src/**/*.ts`，物化产物路径由平台内部计算，业务不感知。
6. **v1 只认 npm**：业务仓必须提交 `package-lock.json`，缺失 = 创建/更新失败并明确提示。不支持 tsconfig paths 别名等高级解析特性，业务 import 一律相对路径。
7. **构建只作用于 package / tool 两类资产**；skill 纯文档不构建。
8. **缓存治理**：控制台加「清理缓存」按钮（修复工具式入口），清空 `cache/assets/`，下次绑定时重建。已知脆弱性写明：缓存清理后重建依赖 npm registry 状态（依赖被 unpublish 则老版本重建失败），锁文件钉死 + 保守清理缓解。
9. **同资产多业务绑定**：v1 不做并发锁与去重优化；缓存按资产 id 共享一份，并发物化的竞态接受（clone/构建落临时目录后原子 rename 兜底），两个业务用同一资产的不同版本本就没有共享问题。
10. **自检补充**：npm 可用性、node 主版本、npm registry 可达性进启动自检，缺则拒启动；registry 地址可配置（内网镜像场景）。
11. **sdk 注入设计废弃**：sdk 是普通 npm 依赖（见同日改名决策），物化时经 `npm ci` 自然就位，平台无任何注入机制。

## 理由与取舍

- **否掉「业务构建后提交 dist」**：git 追踪构建产物不合理（diff 噪音、忘 build 即坏）。
- **否掉「平台不跑 install、要求业务零依赖」**：业务包可有三方依赖是原则，不能因 sdk 分发方式牺牲。
- **install/build 放 bind 时而非首次运行时**：错误前置到配置期，运行期零构建不确定性；缓存键 (url, commit, subpath) 保证同版本只构建一次。
- **不跑业务仓 `npm run build`**：平台流程必须机械可控，构建命令平台自有；业务自定义构建需求走 `agent.materialize.mjs` 钩子（规范流程的一部分，不是散乱的 scripts）。
