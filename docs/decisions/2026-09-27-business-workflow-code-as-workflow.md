# 决策：业务工作流 = 代码即流程（code-as-workflow）

- **日期**：2026-09-27
- **状态**：已定
- **背景**：业务的检查、门禁、自定义处理器的落地方式讨论，最终汇成一个更大的问题——**业务的工作流编排由谁提供、以什么形态提供**。
- **前置决策**：`docs/decisions/2026-09-27-agent-kernel-and-execution-mode.md`（agent 内核 pi、子进程执行、沙箱分期）

## 结论

1. **业务工作流用代码表达，不用流程语言（DSL）**。业务 = 一个**业务流程程序**（独立可执行程序，TypeScript + 平台业务 SDK）+ 控制台登记的业务资料（提示词总纲、skill 组、模型、入口、出口、环境配置）。分支、循环、多次大模型调用都是程序里的普通代码。
2. **平台只提供两种原语**：spawn 一个 JSON 契约的子进程；提供 agent 调用服务。平台不做流程编排，不认识业务内容。
3. **一入一出是平台对业务流程的关键约束**：平台 spawn 业务流程程序，stdin 注入入口信封与上下文，stdout 收唯一结果；进程退出 = 本次 run 结束。
4. **平台提供业务 SDK**（业务侧唯一推荐编程面）：读输入、读配置/密钥、调 agent、调子程序、返回结果。进程管理与协议编解码全部封在 SDK 内。
5. **失败语义**：run 内任何一步失败 = 整个 run 失败，不重跑、不断点续跑，错误上报平台（业务标记 failed + 日志）；扇出规则不变（默认不扇出，`on_failure` 例外）。
6. **稳定性是一等设计目标**：平台是基础组件，任何业务错误（崩溃、死循环、垃圾输出、OOM）不得影响平台与其他业务。防线 = 子进程隔离 + 超时强杀 + 输出大小上限 + agent 调用配额，全部机械执行。
7. **验收锚点**：平台实现完成后，以**单轮审查工单**业务全链（webhook 入口 → 检查 → 拉取工单 → 脱敏 → 大模型审查 → 还原 → 门禁 → 企微群 webhook 出口）做端到端验收。

## 候选方案与取舍

| | A. 流程语言（ASL / BPMN 等） | B. 代码即流程（选定） |
|---|---|---|
| 表达力 | 表达式语言孱弱，真实判断逻辑最终逃逸到外部程序，DSL 只剩路由皮 | 语言原生分支/循环，零天花板 |
| 平台代价 | 平台变解释器（选择/循环/并发/重试语义都要自己实现维护），等于造半个工作流引擎 | 平台只会按序 spawn，承诺少、代码少 |
| source of truth | 定义文件是真相，图可由其渲染 | 代码即真相，图只能由执行轨迹渲染——映射方向永远正确 |
| 调试 | 无法本地单步调试状态机 | 本地 `node workflow.ts < mock.json` 即可跑通整条流程（已有实证：`docs/researches/jira-review-masking-hooks/run-all.sh` 就是手工版流程驱动） |
| AI 友好度 | AI 需学一套私有 DSL 语义 | AI 直接读写代码，所见即所得 |
| 静态可视 | 平台可静态预览流程结构 | 不能；以 trace 事件事后渲染执行图补偿（第一版只记平台服务调用，业务不上报自定义节点） |
| 断点续跑 | 可逐步持久化 | 不支持；分钟级 run 整体重跑即可，将来需要再加 checkpoint（增强，不推翻） |

决定性理由：**路线 A 的所有能力最终都要靠逃逸到程序实现，不如一开始就让程序是一等公民**。业界印证：Temporal 以代码即工作流胜过上一代 DSL 编排引擎；LLM 场景（LangGraph 等）同样是 code-first。UI 拖拽编排（Dify 类）在 v0.5 已否决，本次进一步明确：连「代码↔图」的双向映射都不存在，只有单向渲染。

失控循环的风险由平台侧机械防线兜底：`sdk.agent()` 必经平台，按 run 设调用次数配额与 wall-clock 超时，超限强杀。

## 职责边界（最终版）

- **平台做**：spawn 业务进程（一入一出）、注入入口上下文、提供 agent 调用服务、执行内容无关的机械边界（入口信封 schema、出口结果 schema、超时、配额、输出上限）、记录业务状态与结果、调度下一个任务。
- **平台不做**：不认识业务内容、不编排流程、不保管业务上下文、不做断点续跑。
- **业务做**：用自己的代码写完整流程；自己管理上下文；自己实现检查、数据获取、脱敏、还原、门禁等环节（函数或独立子程序，经 `sdk.run()` 组合）。

由此，此前讨论的「平台钩子（pre-check / post-gate）」概念被本方案吸收：**检查与门禁不再需要平台挂接点，它们就是业务流程程序内部的环节**。pi 层 hooks 保留唯一职责——skill 附带的会话内守卫（见 `design/skill-package.md` §6）。

## SDK 的定位：约定层，不是封锁层

SDK 负责让正路最好走（约定 + 便利 + 可观测）；它物理上封不死业务进程绕过 SDK 直接操作进程/环境——**真边界画在系统层**（第二阶段沙箱、文件系统/网络权限，见前置决策），不靠藏 API 自欺。

## 沙箱兼容

第一版不实现沙箱，但设计不挡路：业务流程程序从第一天起就是子进程 + per-run 资源显式声明（可写工作目录、注入凭据、只读仓库），这些声明即第二阶段沙箱 profile/容器配置的直接输入，无需桥接模块（同前置决策第 3、4 条）。
