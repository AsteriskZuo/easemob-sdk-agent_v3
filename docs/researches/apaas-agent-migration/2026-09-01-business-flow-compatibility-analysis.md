# 四个 AI 工具迁移调查助手：业务流程兼容性分析

- 日期：2026-09-01
- 前置文档：`2026-09-01-apaas-agent-migration-evaluation.md`（技术可行性调研）、`2026-09-01-consultation-questions-to-platform-owner.md`（第一轮咨询文案）
- 分析视角：业务流程兼容性。前提假设：第一轮咨询中平台负责人已答复的硬技术问题（Jira base-url 改造、webhook 事件驱动协商、自定义字段读取）都能解决，本文只讨论业务流转层面的适配。

## 1. 结论摘要

四个工具都是只读/轻写入的 AI 分析工具，与调查助手"AI 调查员"的平台定位大方向兼容，但**业务匹配度差异很大**，建议按匹配度分批迁移：

| 工具 | 业务匹配度 | 核心原因 |
| --- | --- | --- |
| 问题排查工具（多轮企微对话） | ★★★★★ 天然匹配 | 这就是平台的核心场景：企微会话 + 多轮调查，几乎原样落地 |
| 工单审查工具（主工具） | ★★★★ 基本匹配，语义需对齐 | Jira 定查入口、只读审查、结论交付都匹配；但去重语义、@人通知、新建延迟审查三处业务语义需要对齐或改造 |
| crash 分析工具 | ★★★ 有前提 | 分析本身可做；但"审查通过 → webhook 推送外部服务 → 写 Jira 评论"这条跨系统链路，在平台边界内没有对应物，需要改变触发方式 |
| 日志分析工具 | ★★★ 有前提，且有一个未证实能力 | 前提同 crash；额外需要确认平台能否读取 Jira 工单附件内容（日志文件），该能力文档未明确 |

两个新的硬约束（第一轮问题清单之外，本文新增）：

1. **出站推送目标在内网**：crash 工具当前部署在 `10.202.3.37:3001`（10 段私网 IP）。调查助手运行在声网云端，**不可能直接 POST 到我们的内网地址**。要么把下游工具也迁入平台（推荐），要么下游服务暴露公网入口（需安全评估），要么反转方向由下游轮询。
2. **工具自定义状态无处存放**：平台的 Codex 任务工作区是会话级隔离、用完即清的，Skill 是无状态代码。我们各工具自己的持久化（审查记录去重、webhook 订阅表、会话映射）不能指望写本地文件，必须要么映射到平台已有的数据模型（Jira issue 生命周期去重），要么保留一个自己的外部存储服务。

## 2. 四个工具现状盘点（本仓库实测事实）

### 2.1 工单审查工具（本仓库）

- **触发**：三种模式装配（`src/server.ts:177-223`）：Jira webhook（`POST /jira/webhook`，收 `issue_created/updated`）、第三方转发 webhook（当前生产用）、JQL 轮询（默认 60s）。端口 3000，接收端无鉴权无验签。
- **流程**：事件过滤（Bug 类型、负责人白名单）→ 去重检查 → 新建工单进延迟队列（默认 5 分钟，等提单人补全字段，`config.ts:105`）→ 预取工单全字段+全部评论并脱敏 → 终态工单短路 skip → 一次性大模型调用（codex exec，read-only，prompt 明确禁止再调 Jira 和写评论）→ 输出契约 JSON `{decision: pass|fail|skip, classification, scenarios[], ...}`。
- **持久化**（全部是 `$APP__DATA_DIR` 下的 JSON 文件，tmp+rename 原子写）：
  - `review-records.json`：`{issueKey: {status, reviewedAt, ticketUpdatedAt}}`。去重语义：**pass 永久不再审；fail/skip 只在工单 updated 时间戳变化后复审**。
  - `delayed-review-requests.json`：延迟队列，重启恢复。
- **通知**：首选企微群机器人 webhook（`mentioned_list` 实现 @人：pass @负责人、fail @创建者，映射靠 `src/data/jira-wecom-mapping.json` + 拼音猜测）；回退 AI Bot WS 通道（不支持 @）。若结果场景全部已被分类订阅覆盖则不 @。
- **下游分发**：`WebhookDeliveryObserver` 按订阅表（`webhook-subscriptions.json`，企微里用"订阅 <url> <分类>"命令注册）把审查结果 JSON POST 给下游（fire-and-forget，2s 超时，连续失败 15 次自动挂起，定时探活恢复）。

### 2.2 crash 分析工具（外部服务，本仓库只有推送方）

- 部署在 `http://10.202.3.37:3001/wecom/webhook/analyze`（内网）。
- 触发：订阅审查工具的 `crash` 分类事件，收到的是审查结果 JSON（issueKey、scenarios、summary 等，**不含附件内容**）。
- 后续动作：自行拉取工单继续分析，结果写入 Jira 评论。单次大模型调用。

### 2.3 日志分析工具（外部服务）

- 同 crash 的订阅触发链路；针对特定场景、带日志附件的工单做分析；结果通知到企业微信（不写 Jira）。

### 2.4 问题排查工具（独立服务）

- 多轮企微对话，不操作 Jira，但是需要多个仓库的只读访问权限，与本仓库无代码关系。注意：本仓库里的企微多轮入口路由后走的仍是工单审查 prompt，不是独立的排查工具。

## 3. 平台业务模型与我们的差异本质

调查助手的业务闭环是：**入口（企微提问 / Jira Filter 定时拉单）→ Codex 调查任务（团队 Prompt + Skill + 代码库 + 附件）→ 结论交付（评论/回复 + HTML 报告）→ 解决率闭环判定（一次定位/最终定位/人工判断）→ 看板**。它的所有数据模型都围绕"定位率"设计：Jira 侧是 `jira_issues`（一 issue 一条 + lifecycle，重开递增），有 `skipped_already_triaged` 去重、关闭结算、人工评论判定和 `agent_resolved/unresolved/unreviewed` 标签。

我们的业务闭环是：**Jira 事件 → 规则化质检（字段完整性审查）→ pass/fail 结果分发（企微@人 + 下游工具触发）**。它的产出是"审查裁决"，平台的产出是"调查结论"。这决定了：平台能承载我们的分析动作，但**不天然承载我们的业务语义**——"审查通过/不通过"不是"定位/未定位"，我们的质检结论如何进入平台的数据模型（还是完全绕开它），是迁移设计的第一性问题。

## 4. 逐工具业务流程兼容性分析

### 4.1 问题排查工具：天然匹配，可作为迁移试点

平台核心场景就是这个：企微智能机器人私聊/群聊、多轮会话、`/steer` 改方向、附件上传、历史会话继承、HTML 报告。我们的工具逻辑（多轮对话、不碰 Jira）落到平台上就是"团队 Prompt + 若干 Skill"，不需要任何平台改造。**建议把它作为第一个 PoC**，用来验证 Skill 仓库接入、模型配置、企微机器人体验，成本最低、风险最小。

注意点：现有工具的会话状态（会话映射、上下文）迁移后由平台接管，行为细节（上下文压缩、模型降级会重置会话并摘要续跑）与现有实现不同，需要体验验收。

### 4.2 工单审查工具：基本匹配，三处业务语义需对齐

**匹配的部分**：只读审查对应平台的"Jira 定查保持只读"；JQL Filter + cron 可以近似替代我们的事件监听（平台方也已表态 webhook 事件驱动可协商）；预取全字段+评论与平台"单条工单读取校验字段"方向一致（自定义字段已确认要支持）；一次性大模型调用与平台 Codex 任务模型兼容。

**需要对齐的三处语义**：

1. **去重语义不同**。我们：pass 永久跳过，fail/skip 按工单 updated 时间戳变化触发复审。平台：`skipped_already_triaged` 按生命周期去重，issue 重开才进入新 lifecycle。"fail 后用户按反馈修改了工单 → 自动复审"这个我们的核心运营动作，在平台模型里对应什么？可能的方案：Filter 的 JQL 里加"更新时间"条件让 cron 自然捞起修改过的工单，靠平台/自定义逻辑区分"是否已 pass"。需要与平台确认 Filter 复查的触发条件和去重粒度能否按我们的语义配置。
2. **新建工单延迟 5 分钟审查**。这是我们给提单人留的补全字段窗口。平台 Filter cron 天然有延迟（最小粒度分钟级），JQL 加 `created <= -5m` 即可等效，不构成问题，但要在 JQL 设计里落实。
3. **@人通知**。我们的结果通知强依赖群机器人 webhook 的 `mentioned_list`（pass @负责人、fail @创建者），且我们有 Jira 用户→企微 userid 的映射表。平台只支持 API 模式智能机器人（WebSocket），文档明确普通 webhook 机器人不能替代；平台机器人的**主动推送和 @成员能力文档未描述**（群聊只在有会话时回复）。这是第一轮咨询已列、仍需平台明确答复的关键项。如果平台机器人不能 @，审查结果"通知到人"的运营效果会打折，需要评估可接受度或要求平台支持。

**可以舍弃/被平台接管的部分**：在途去重、队列、延迟队列持久化、进程恢复——平台有自己的任务编排和恢复器，我们的这些机制不需要搬过去。审查 prompt 和 15 场景审查标准天然就是 Skill/`jira.triage` 覆盖项的素材。

### 4.3 crash 分析工具：链路需要重构

当前链路"审查工具 → POST 内网地址 → crash 工具 → 写 Jira 评论"在平台边界内无法原样存在，原因有二：

1. **网络**：`10.202.3.37` 是私网地址，声网云端不可达。即使平台开放出站白名单，也只能白名单公网 Host。
2. **平台没有"任务完成事件外发 webhook"机制**：平台的对外出口是企微消息和受控 Jira 评论，没有"把任务结果 POST 给任意 URL"的能力。

可选的重构方向（按推荐排序）：

- **方案 A：链路内化**。crash 分析不再收 webhook，而是作为平台内审查任务的后续环节：同一个 Codex 任务（或同 issue 的复查任务）里，审查 pass 且命中 crash 场景 → 继续执行 crash 分析 Skill → 通过平台"受控单条 Jira Comment"写回评论。平台文档明确支持"已发布团队 Skill 明确规定的流程"触发受控评论，且评论以 `【Agent定位 - 结论】` 开头、需服务端验收。这条链路完全在平台能力内，但 crash 分析的触发时机、评论内容格式要适配平台的验收协议，且"一次任务里串两级分析"会拉长单任务时长（平台单任务上限 2 小时，够用）。
- **方案 B：下游保留，方向反转**。crash 工具仍部署在我们侧，但不再收推送，改为定时轮询 Jira（捞带特定标签/评论的工单）或轮询平台 API。改动大、引入新轮询服务，不推荐。
- **方案 C：下游服务暴露公网 + 平台白名单**。安全和运维成本高，最不推荐。

方案 A 的副作用：crash 分析结果从"外部服务自主写评论"变成"平台协议约束下的评论"，评论格式、验收失败时的兜底都要重新设计。

### 4.4 日志分析工具：同 crash，外加一个未证实能力

触发链路的重构与 crash 完全相同（结果改为发企微，平台内反而更自然——会话回复即可）。额外的硬问题：**它需要读取 Jira 工单的日志附件内容**。平台文档只明确了企微会话附件的处理，Jira 工单读取只提到"字段"（含自定义字段，已确认要支持），**附件内容（二进制日志文件下载）能否读、有无大小限制，文档未提**。如果平台 Jira Client 不支持附件下载，日志分析工具无法迁入，这是需要在第二轮咨询中确认的新问题。

### 4.5 审查结果的"注册-分发"机制：平台无对应物，建议随方案 A 一并取消

我们的"订阅 <url> <分类>"命令 + 订阅表 + 失败挂起/探活，本质是一个微型的内部事件总线。如果 crash/日志分析都内化为平台内 Skill 环节（方案 A），这套机制整体退役，订阅表、探活 job 都不用搬。如果有下游必须留在平台外，则需要一个平台外的"事件适配器"服务承接——尽量避免走到这一步。

## 5. 横向注意点（迁移准备工作清单）

1. **持久化语义映射**：`review-records.json` 的"pass 永久跳过"要映射为平台能力（jira_issues 生命周期 / Filter 去重）还是保留一个外部状态服务？建议优先用平台 Filter + JQL 表达，把状态语义上移到 JQL；迁移动作本身要包含历史已 pass 工单的口径确认（已 pass 的存量工单在平台上第一次被 Filter 捞到时会不会被重审一遍？需要一次性初始化策略，比如先用 JQL 排除历史已审工单）。
2. **@人映射表搬迁**：`jira-wecom-mapping.json` + 拼音猜测逻辑是数据+代码，可作为 Skill 资源带入，但前提是平台支持 @人（见 4.2）。
3. **双层认证的落点**：平台 Jira 认证只有 basic/pat 等标准模式，我们 Jira 是网关 Basic 头 + 表单 Cookie 登录的双层非标认证。第一轮已确认"Jira 需要改造满足使用条件"，迁移准备时要和平台把改造范围写清楚：是平台客户端支持自定义认证流程，还是我们侧在网关层为标准 REST 开放一个直通通道（例如专用账号 + IP 白名单绕开表单登录）。后者可能比我们想象的更省事。
4. **接收端零鉴权的技术债不用搬**：我们 webhook 接收端无验签，迁移后由平台的 Jira 集成负责，这笔债自然消掉，不要在平台侧复刻。
5. **通知文案与运营习惯的再培训**：平台企微回复是 streaming + 原生"思考"折叠区 + HTML 报告，与我们现在的 markdown 群消息体验不同；审查结果的"标题+链接+原因+@"格式要重新设计为平台评论/回复格式，并考虑是否启用平台的会话标签分类（可以把 pass/fail/场景分类映射为平台标签，白赚一个看板）。
6. **健康检查/SMTP 日报退役**：平台有 Readiness、看板和失败任务记录，我们的 nodemailer 日报不需要迁移。
7. **Skill 仓库载体**：四个工具的规则（审查标准、crash 分析规则、日志分析规则、排查知识）都要整理成 SKILL.md 结构的仓库，且 Git Host 要在平台白名单内（GitHub 私有仓库的支持情况第一轮已列入咨询）。建议迁移准备的第一步就是建这个仓库，把 `.agents/skills/jira-ticket-review/SKILL.md` 作为种子。
8. **模型与密钥**：平台模型配置组只支持"OpenAI API Key + 模型 + 倍率"，provider base URL 由平台固定，不能自带任意端点；我们现在经 codeproxy 桥接 DeepSeek/千问的做法在平台上不可复用，用哪个模型取决于平台网关提供什么（第一轮已确认为非问题，但成本/效果要用 PoC 实测）。工具所需的下游凭证走平台的 Secret 环境变量（最多 64 项，注入 Codex 子进程）。
9. **并发与配额**：平台按团队有 Codex 会话/Jira 并发上限（1-100），我们当前单进程串行队列没有并发概念，迁移后审查+排查共用配额，上线前要估算峰值。
10. **四个工具的边界重划**：迁入平台后，"审查→crash→日志"从四个独立服务变成"一个团队下的若干 Skill + 流程编排"，运维主体从我们自己变成平台，故障排查方式、发布节奏（Prompt 草稿-发布、Skill Release）都要重新约定。

## 6. 建议的迁移顺序

1. **PoC 1：问题排查工具**（纯 Skill + 团队 Prompt，验证平台基线能力）。
2. **PoC 2：工单审查只读链路**（Jira Filter 接入 + 自定义字段 + 审查 Skill + 企微通知，验证去重语义和 @人）。
3. **PoC 3：crash/日志分析内化**（受控评论写入、附件读取验证）。
4. 全部跑通后再讨论存量状态迁移（已 pass 工单口径）和旧服务下线。

## 7. 第二轮待确认问题（新增，供咨询平台方）

1. Jira 工单附件（日志文件）内容能否被 Agent 读取/下载？有无大小和类型限制？
2. Filter 复查的去重粒度和触发条件能否表达我们的语义："fail/skip 的工单在 updated 变化后复审，pass 的工单永久跳过"？
3. 平台是否有"任务完成后向外部 URL 推送结果"的机制？（用于评估下游工具必须内化的范围；我们预计答案是没有，主要确认是否规划支持）
4. 一个 Codex 任务内串联"审查 → 分类 → 二级分析 → 受控评论"的多阶段流程，是否有平台侧的编排约束（例如评论必须在任务最终报告验收后才能发）？crash 分析的评论能否作为独立动作在任务中段发出？
5. 智能机器人是否支持向群内主动发消息并 @ 指定成员（企微 userid）？
6. 已 pass 的历史工单在平台首次接入 Filter 时如何避免全量重审？
