# Jira 6.3.6 长轮询兜底方案调研

日期：2026-07-11

## 背景

主方案是使用 Jira webhook 接收工单创建、更新事件，调研材料位于：

`docs/research/jira-webhook/`

但当前用户没有 Jira 管理员权限，短期无法自行配置 webhook。因此需要一个兜底方案：本系统定时查询 Jira 中“需要关注的工单”，尤其是指派给指定人的工单，避免 webhook 暂时不可用时完全丢失 Jira 侧变化。

## 结论

Jira 6.3.6 REST API v2 支持通过 `/rest/api/2/search` 使用 JQL 搜索工单。可以用它实现轮询兜底方案。

推荐兜底查询模型：

```text
assignee = "<username>"
AND updated >= "<cursor>"
ORDER BY updated ASC, key ASC
```

如果需要限定项目，再加：

```text
project in ("ABC", "DEF")
```

如果只关注未完成工单，再加：

```text
resolution = Unresolved
```

完整示例：

```text
project in ("ABC")
AND assignee = "operator"
AND updated >= "2026-07-11 00:00"
AND resolution = Unresolved
ORDER BY updated ASC, key ASC
```

## 官方资料依据

Jira 6.3.6 REST API v2 官方文档：

https://docs.atlassian.com/jira/REST/6.3.6/

其中 `/rest/api/2/search` 是搜索资源，支持：

- `GET /rest/api/2/search?jql=...`
- `POST /rest/api/2/search`

参数包括：

- `jql`：JQL 查询语句。
- `startAt`：返回结果起始位置，0-based。
- `maxResults`：最大返回数量，默认 50，实际上限受 Jira 属性 `jira.search.views.default.max` 影响，超过上限会被截断。
- `validateQuery`：是否校验 JQL，默认 `true`。
- `fields`：返回字段列表。Search 默认只返回 navigable 字段，和 `GET issue` 默认返回所有字段不同。
- `expand`：扩展字段，例如 `changelog`。

文档也明确：如果 JQL 太长，不适合放在 query param 中，应使用 POST。

## 与 webhook 方案的关系

Polling 是兜底方案，不是主方案。

推荐优先级：

1. webhook 可用时，以 webhook 事件为准。
2. polling 作为补偿任务，低频扫描最近变化，发现 webhook 漏投或配置不可用期间的变化。
3. webhook 不可用时，临时提高 polling 频率，承担主要同步职责。

不建议只依赖 polling，原因：

- 延迟取决于轮询间隔。
- 查询窗口、分页和去重需要谨慎处理。
- 无法像 webhook 的 `changelog` 那样天然拿到“这次修改了哪些字段”。如果需要变更明细，必须额外 `GET issue?expand=changelog` 或在 search 里 `expand=changelog`，成本更高。

## 推荐数据流

```text
定时任务
  -> 读取 assignee 列表和上次 cursor
  -> 构造 JQL
  -> POST /rest/api/2/search
  -> 按页读取 issues
  -> 对每个 issue 做幂等处理
  -> 更新 cursor
```

## Cursor 设计

Jira issue 的 `fields.updated` 精度通常到毫秒，但 JQL 中日期/时间比较的实际解析精度需要真实实例验证。为了避免边界漏数据，不建议用“严格大于上次最大 updated”的单点游标。

推荐使用重叠窗口：

1. 持久化上次成功扫描到的最大 `updated`。
2. 下一轮查询时，把 cursor 回退一段时间，例如 5 分钟：

```text
updated >= "<lastSeenUpdated - 5 minutes>"
```

3. 对结果按 `issue.key + fields.updated` 或 `issue.id + fields.updated` 去重。
4. 如果后续需要变更级去重，再结合 changelog id。

这样会重复处理少量工单，但比漏掉边界更新更稳。

## JQL 建议

### 单个 assignee

```text
assignee = "operator"
AND updated >= "2026-07-11 00:00"
ORDER BY updated ASC, key ASC
```

### 多个 assignee

```text
assignee in ("operator", "support_a")
AND updated >= "2026-07-11 00:00"
ORDER BY updated ASC, key ASC
```

### 限定项目和未完成工单

```text
project in ("ABC")
AND assignee in ("operator", "support_a")
AND resolution = Unresolved
AND updated >= "2026-07-11 00:00"
ORDER BY updated ASC, key ASC
```

### 包含未指派工单

如果业务需要关注未指派工单：

```text
(assignee in ("operator", "support_a") OR assignee is EMPTY)
AND updated >= "2026-07-11 00:00"
ORDER BY updated ASC, key ASC
```

当前需求明确是“指派给指定人”，所以默认不包含未指派。

## 字段选择

轮询列表阶段建议只取必要字段，降低 Jira 压力：

```json
[
  "summary",
  "status",
  "assignee",
  "reporter",
  "updated",
  "created",
  "priority",
  "issuetype",
  "project"
]
```

如果后续确实需要修改明细，再对具体 issue 调用：

```text
GET /rest/api/2/issue/{issueKey}?expand=changelog
```

或在 search 中加：

```json
{
  "expand": ["changelog"]
}
```

但不建议默认对所有轮询结果展开 changelog。

## 分页策略

Search 返回结构包含：

- `startAt`
- `maxResults`
- `total`
- `issues`

建议：

1. `maxResults` 初始设为 50 或 100。
2. 如果返回 `issues.length === maxResults`，继续请求下一页。
3. 下一页 `startAt += issues.length`，不要假设 Jira 一定接受请求中的 `maxResults`。
4. 单轮扫描设置最大页数或最大 issue 数，避免异常 JQL 导致一次扫描过重。

## 权限要求

Polling 不需要 Jira 管理员权限，但需要调用账号具备：

- 登录 Jira 的权限。
- Browse Project / Browse Issues 权限。
- 能看到目标项目和目标工单。

如果查询指定 assignee 没有结果，需要区分：

- assignee 用户名写错。
- 调用账号无权浏览相关工单。
- 工单不在 JQL 限定范围内。
- Jira 字段或工作流配置导致 `resolution = Unresolved` 不适用。

## 架构建议

后续实现时，建议将 polling 作为独立同步组件，不复用 webhook receiver：

```text
JiraPollingScheduler
  -> JiraSearchClient
  -> JiraIssueChangeDetector
  -> 业务事件队列/同步处理器
```

边界：

- `JiraSearchClient` 只负责 search 请求、分页和错误映射。
- `JiraPollingScheduler` 只负责定时、cursor 和重试。
- `JiraIssueChangeDetector` 负责幂等、去重、识别新变化。

当前阶段只做调研和验证脚本，不落地运行时代码。
