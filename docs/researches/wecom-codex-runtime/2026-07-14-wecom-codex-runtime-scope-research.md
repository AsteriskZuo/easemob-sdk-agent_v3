# 企业微信 + Codex CLI 运行模式边界研究

日期：2026-07-14

## 背景

当前项目正在进行 Agent Runtime 重写。新的方向是让宿主服务只负责外部协议接入、请求封装、Codex CLI 调用、结果分发和必要状态持久化，业务处理由大模型基于 prompt、skill 和 MCP 自主完成。

在讨论 Docker 服务化运行时，一个关键问题浮现出来：

```text
Codex CLI 天然以本地工作目录为中心；
Docker 服务天然隔离宿主机文件系统；
企业微信用户和服务大概率不在同一台机器上。
```

因此，如果把企业微信作为用户和 Codex CLI 的连接入口，需要明确这种模式适合什么任务，不适合什么任务。

## 核心结论

企业微信 + Codex CLI 更适合做远程分析型 Agent，不适合在第一阶段做远程开发执行型 Agent。

简化表达：

```text
企业微信 + Codex CLI：适合审查、分析、问答、建议。
本地 Codex CLI：适合修复、开发、测试、提交。
```

当前服务不应定位为多人远程代码修改平台，而应定位为企业微信到 Codex CLI 的轻量桥梁，用于低环境依赖的分析、审查、问答和外部系统操作。

## 为什么 Docker 服务不适合第一阶段承载开发执行任务

本地使用 Codex CLI 时，开发者天然拥有完整开发环境：

```text
源码目录
当前工作目录
git 配置
SSH key / token
依赖缓存
语言工具链
私有配置
测试数据
未提交变更
项目 AGENTS.md / skill / MCP
CODEX_HOME
shell 环境
```

Docker 服务化后，这些上下文不会天然存在。服务如果要直接修 bug、增加新特性或提交代码，就必须额外解决：

- 用户本地目录无法被远程 Docker 服务直接访问。
- 多个用户可能同时操作不同仓库或同一仓库的不同分支。
- 每个任务需要隔离工作区，避免工作树互相污染。
- 服务端需要托管或 clone 仓库。
- 服务端需要管理 git 凭据、分支、push 权限和冲突。
- 服务端需要准备不同项目的语言工具链、依赖缓存和测试环境。
- 目标仓库自己的 skill、MCP 和 AGENTS.md 加载边界需要额外设计。
- 写代码任务的副作用和权限风险明显高于只读分析任务。

这些问题会把当前服务从“企业微信到 Codex CLI 的桥梁”扩大成“多人远程开发工作台”。这超出了当前 Agent Runtime 重写的第一阶段边界。

## 适合企业微信 + Codex CLI 的任务

这类任务主要依赖阅读、推理、查询外部系统和生成文本结果，对本地运行环境要求低。

典型任务：

- Jira 工单审查。
- Jira 工单信息补全建议。
- Jira 工单创建过程中的问答和草稿整理。
- 错误日志解释。
- 基于只读源码的结构分析。
- 回答“某个功能在哪里实现”。
- 分析某个改动的大致影响面。
- 给出修复建议和排查步骤。
- 评审技术方案。
- 生成测试建议。

这类任务的输出通常是：

```text
企业微信回复
Jira 评论
分析结论
修复建议
排查步骤
测试建议
```

它们不要求服务端修改仓库代码，也不要求服务端具备完整项目运行环境。

## 更适合本地 Codex CLI 的任务

这类任务需要真实开发环境、写文件能力、项目依赖、测试执行和 git 状态管理。

典型任务：

- 修复 bug。
- 增加新特性。
- 重构代码。
- 跑完整测试。
- 调试构建失败。
- 修改多个仓库。
- 提交代码。
- 处理 git 冲突。
- 创建 PR 前整理变更。

这些任务更适合由用户在本地 Codex CLI 中完成。用户本地天然拥有项目目录、依赖、私有配置、未提交状态和开发者权限，风险边界也更清晰。

企业微信服务可以为这类任务提供前置分析，例如：

```text
这个 bug 可能涉及哪些模块？
建议从哪些文件开始看？
修复思路是什么？
本地应该运行哪些测试？
```

但第一阶段不应直接替用户修改代码。

## 关于仓库名称与本地路径

如果只是进行源码分析，用户不应提供本地源码路径。企业微信用户和 Docker 服务不在同一台机器时，本地路径没有稳定意义。

更合理的表达是用户提供仓库名称，例如：

```text
分析 easemob-web-sdk 的登录流程。
看一下 easemob-ios-sdk 里消息发送失败可能在哪里处理。
```

服务端可以维护只读仓库副本或受控源码目录，让 Codex CLI 基于仓库名称进行只读分析。

但仓库名称、分支、分析目标仍然属于用户自然语言意图，不应为了这一点扩展 `AgentRequest` 字段。

## 对 AgentRequest 的影响

本次讨论不要求修改当前 `AgentRequest` 结构。

当前最小结构仍然成立：

```ts
type AgentRequest = {
  id: string;
  type: "jira_ticket_review";
  source: "wecom" | "jira_webhook" | "jira_polling";
  sessionId: string;
  content: string;
};
```

原因：

- 用户想表达的仓库名称、分支、问题背景、分析目标，都可以由 `content` 承载。
- 大模型天然适合理解自然语言意图。
- 将 repo、branch、workdir、action 等提前结构化，会把宿主服务推向任务路由和远程开发平台方向。
- 当前设计原则是宿主只处理外层协议和运行时封装，不理解业务内部结构。

如果后续增加通用企业微信直连 Codex 场景，可以新增业务类型，例如：

```text
interactive_codex
source_code_analysis
```

但仍不需要把 repo、branch、workdir 加入 `AgentRequest`。

## 对 Runtime 的影响

虽然 `AgentRequest` 不需要增加字段，但 runtime 仍需要提供一个安全、稳定的 Codex CLI 初始工作目录。

对于当前第一阶段的 Jira 工单审查：

```text
Codex CLI 可以运行在服务项目工作目录。
Jira 工单内容通过 Jira MCP 获取。
不依赖目标代码仓库。
```

对于后续只读源码分析：

```text
服务端可以提供受控的只读仓库目录。
Codex CLI 默认使用 read-only sandbox。
用户通过 content 表达仓库名称和分析目标。
模型在允许范围内读取源码并返回分析结果。
```

需要避免的是：

```text
默认允许写代码。
默认创建分支。
默认 push。
默认运行任意项目测试。
默认把 Docker 服务当成多人开发工作站。
```

## 与当前 Runtime 重写设计的关系

当前 `docs/superpowers/specs/2026-07-13-agent-runtime-rewrite-design.md` 的第一阶段目标是跑通 Jira 工单审查。这个目标与本次边界判断一致。

Jira 工单审查是企业微信 + Codex CLI 模式的高匹配场景：

- 不依赖本地仓库。
- 主要依赖 Jira MCP 查询和写评论。
- 输出是人类可读文本和 Jira 评论。
- 不需要修改代码。
- 不需要完整项目运行环境。

后续如果扩展基于源码的问答，也应优先保持只读边界。

## 决策建议

建议后续架构文档明确以下边界：

```text
当前服务不是多人远程开发平台。
当前服务是企业微信到 Codex CLI 的轻量桥梁。
它优先支持 Jira 等外部系统操作，以及基于只读仓库的源码理解、分析和问答。
需要修改代码、运行项目环境、提交分支的任务，默认由用户在本地 Codex CLI 完成。
```

这个边界可以防止架构过早膨胀，也能让第一阶段聚焦在可稳定落地的场景上。
