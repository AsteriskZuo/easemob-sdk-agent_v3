# Jira 字段调研：jira-ticket-review 优化前置

日期：2026-07-17
状态：调研完成，结论已收敛，待进入开发阶段讨论

## 1. 背景与目的

`jira-ticket-review` skill 目前用一套人工枚举的 Bug 必填标准审查所有 HIM 工单，且 `jira_get_issue` 只映射 14 个固定字段，自定义字段全部丢失。本调研回答三个问题：

1. 当前 Jira 实际有哪些字段可用？
2. HIM 工单（尤其 Bug）实际在用哪些字段、内容形态如何？
3. 哪些字段应成为大模型审查的分析对象？

## 2. 方法与数据

工具：`jira-field-research.mjs`（认证移植自 `src/jira/jira-client.ts`，只读）。三类数据：

| 数据集 | 来源 | 样本 |
|---|---|---|
| 字段全景 | `GET /rest/api/2/field` | 全部 132 个字段定义 |
| 全类型抽样 | `project = "HIM" ORDER BY updated DESC` | 30 个（项目共 21,456 个工单） |
| Bug 抽样 | `+ issuetype = Bug` | 50 个（Bug 共 3,322 个，占 15.5%） |

数据纪律：只落聚合统计与共享模板文本，不落完整工单内容。原始数据见 `field-definitions.json`、`sample-field-stats.json`、`sample-field-stats-bug.json`。

## 3. 事实：字段全景

全实例共 **132 个字段（系统 40 + 自定义 92）**。与审单相关的自定义字段形成明显的业务分组：

| 字段 | 名称 | 类型 | 备注 |
|---|---|---|---|
| customfield_11900 | HIM需求内容 | string | 需求类工单内容字段 |
| customfield_11901 | HIM缺陷内容 | string | **Bug 主内容字段** |
| customfield_11902 | 问题归因 | string | 关闭阶段填写 |
| customfield_11903 | 修复方式 | string | 关闭阶段填写 |
| customfield_11906 | 测试内容及范围 | string | Test 类工单使用 |
| customfield_11908 | 文档问题描述 | string | 实测无人填写（见 §4） |
| customfield_11910 | 客户端/服务端 | array | — |
| customfield_11911 | 文档错误类型 | array | — |
| customfield_10306 | Epic Link | array（实际为 string） | 业务归属 |
| customfield_102xx 组 | 工单名称/工单级别/产品线/提交团队/问题描述/客户信息/研发支持内容 | — | 客服支持工单体系，HIM 抽样中未出现 |

issuetype 实际词表（抽样观测）：`Bug`、`Sub-task`、`Task`、`Improvement`、`Test`、`New Feature`、`Epic`。
status 词表：`To Do`、`In Progress`、`Complete`、`部署完成`、`沙箱测试`、`Readed`、`PM 已处理`、`等待部署`。
priority 词表：`Minor`、`Major`、`Critical`。

## 4. 事实：HIM 工单字段使用现状

### 4.1 HIM 创建界面为四个内容字段预置了默认模板

`present ≠ 有人填写`。以众数值为默认模板做比对（n=50 Bug）：

| 字段 | present | 完全等于模板 | 有人工内容 | 剥离模板后内容长度 p50 |
|---|---:|---:|---:|---:|
| customfield_11901（HIM缺陷内容） | 41/50 (82%) | 12 (24%) | **26 (52%)** | 74 字符（p90=476, max=2953） |
| customfield_11900（HIM需求内容） | 49/50 | **49 (98%)** | 0 | 0 |
| customfield_11906（测试内容及范围） | 49/50 | **49 (98%)** | 0 | 0 |
| customfield_11908（文档问题描述） | 47/50 | **47 (94%)** | 0 | 0 |
| description | 16/50 (32%) | 1 | 13 (26%) | 154 字符 |

结论性事实：**在 Bug 工单上，11900/11906/11908 三个字段是创建界面自动填充的模板，无人手工填写**；唯一被人工填写的内容字段是 `customfield_11901`（主）和 `description`（辅）。

### 4.2 字段 × issuetype 使用矩阵（全类型抽样 n=30，present/有人工内容）

| issuetype | 11900 | 11901 | 11906 | 11908 | description |
|---|---|---|---|---|---|
| Bug (6) | 5/0 | **4/4** | 5/0 | 5/0 | 2/2 |
| Sub-task (8) | 4/1 | 8/0 | 8/0 | 8/0 | **8/7** |
| Task (6) | **5/5** | 5/0 | 5/0 | 5/0 | 1/1 |
| Improvement (2) | **2/2** | 2/0 | 2/0 | 1/0 | 0/0 |
| Test (4) | 4/0 | 4/0 | **3/3** | 4/0 | **4/4** |
| New Feature (3) | **3/3** | 3/0 | 3/0 | 2/0 | 0/0 |

每种工单类型有且仅有一个被真正填写的内容字段：Bug→11901，Task/New Feature/Improvement→11900，Test→11906+description，Sub-task→description。

### 4.3 其他字段（Bug 抽样 n=50）

- `environment`：**0/50，全实例弃用**（全类型抽样同样 0/30）。环境信息由 11901 模板内的结构化条目承载
- `attachment`：21/50 (42%) 有附件，共 53 个
- `comment`：28/50 (56%) 有评论，最多 24 条
- `components`：50/50 必填；`customfield_10306`（Epic Link）：21/50 (42%)
- `labels`：3/50 (6%)；`fixVersions`：10/50 (20%)；`versions`：0（搜索响应中未返回）

### 4.4 HIM缺陷内容默认模板（已完整捕获，众数命中 22 次）

```text
【客户信息收集】
AppKey：
Cluster：
SDK信息：
客户APP名称：
涉及终端：如IOS、Android、Web、鸿蒙OS等等
环境信息：核心中间件版本，如涉及，请填写
【问题描述（重点）】
建议包含以下内容：
1、客户的业务场景
2、问题出现的场景（条件）和具体现象
3、是否存在替代方案，如存在，为什么不满足
4、客户原始反馈信息
【预计结果】
客户预期结果，建议明确范围。
【日志或者补充说明】
包含日志记录、图片说明、代码片段、返回值等等
【期望解决时间】
客户希望解决的时间
```

模板条目与审查维度存在直接映射：AppKey≈appId、SDK信息≈sdkVersion、涉及终端≈sdkPlatform、环境信息≈deviceInfo、【预计结果】=expected、【问题描述】含 actual/场景、【日志或者补充说明】=证据。注意模板**没有显式要求"复现步骤"**，只要求"问题出现的场景（条件）和具体现象"。

## 5. 推断

1. **审查必须做模板识别**。四个内容字段的"非空"没有信息量；判断充分性时要先剥离默认模板（模板文本已捕获，可直接写进 skill 作参照），再看剩余内容。
2. **"有内容但薄"是 Bug 单常态**。有人工内容的 Bug 中，剥离模板后中位数仅 74 字符。合格线如果按"覆盖模板所有条目"卡会误杀大量可用工单；反过来 24% 纯模板 + 18% 无字段是明确的 fail 候选。
3. **42% 的 Bug 有附件**。现阶段不处理图片/文件，意味着证据可能不在文本里。审查结论应对"文本不足但存在附件"保持区分（提示人工看附件），而不是直接等同"无证据"。
4. **约 18% 的 Bug 无 11901 字段**（9/50），其中部分用 description 兜底。证据可出现在任何叙述字段，审查输入应合并 11901 + description + summary + comment 统一判断。
5. **11902 问题归因 / 11903 修复方式**是关闭阶段字段，intake 审查用不上，但是未来做"关闭质量"场景的分析对象。

## 6. 判断：审查字段推荐集

| 层 | 字段 | 用途 |
|---|---|---|
| 路由 | issuetype | 分类主依据：Bug 进入充分性审查，其余按类型标记 |
| 核心证据 | customfield_11901、description、summary、comment | 充分性判断的合并输入，先剥模板 |
| 辅助证据 | customfield_11900、customfield_11906 | 识别"标 Bug 实为需求/测试"的内容冲突；Test 类工单主字段 |
| 上下文 | priority、components、labels、fixVersions、status、reporter、creator、assignee、created、updated、project、customfield_10306（Epic Link） | 背景与归因（Epic Link 为用户指定重要字段，42% 填写率） |
| 附件元数据 | attachment（数量/文件名/mimeType，不下载） | 区分"无证据"与"证据在附件里"，为后续附件处理留口 |
| 明确排除 | environment（0% 使用）、versions（0%）、customfield_11908（100% 模板）、timetracking/worklog/votes/watches/progress 等过程字段 | 不进入分析集 |

`jira_get_issue` 需要在现有 14 字段基础上新增映射：`customfield_11901`、`customfield_11900`、`customfield_11906`、`customfield_10306`、`attachment`（仅元数据）、`created`、`resolution`。

## 7. 对开发阶段的建议

1. **字段能力落地**：调研已验证 `GET /rest/api/2/field` 与认证流程可用。建议开发阶段在 MCP 侧（`.agents/mcps/jira/src/jira-client.ts`，src 旧版在迁出）增加 `getFields()` 方法及 `jira_list_fields` tool，并按 §6 扩展 `mapIssue`。
2. **skill 两阶段重写**：阶段一以 issuetype 为主、内容（11900/11901 填写情况）为辅做分类，只放行 Bug；阶段二按 §4.4 模板映射的维度做充分性判断，模板识别用已捕获的模板文本。
3. **输出契约**：非 Bug 工单需要新的 `skip` 语义（或明确的兼容方案），下游 `review-notification-observer` 与去重 store 随之调整。

## 8. 真实工单验证：HIM-22543（2026-07-17）

用 `inspect` 子命令对真实 Bug 工单验证，结果与上述结论一致，并补充了三个细节：

**工单概况**：Bug | Readed | Major | SDK/UIKit | Epic Link HIM-4495；附件 5 个（3 个日志 txt + 2 张截图）；评论 8 条（含负责人初步根因分析）。

**11901 逐区块填充**（去模板后 436 字符）：

| 区块 | 填充 | 内容 |
|---|---|---|
| 【客户信息收集】 | ✓ | AppKey、Cluster、SDK信息（flutter sdk 4.19.1）均有值 |
| 【问题描述（重点）】 | ✓ | 360 字符，问题现象描述完整 |
| 【预计结果】 | ✗ | 空 |
| 【日志或者补充说明】 | ✗ | 空——**但 5 个附件里就是日志和截图** |
| 【期望解决时间】 | ✗ | 空 |

**验证发现**：

1. **"证据在附件"案例真实存在**（推断 3 被验证）：该单日志区块为空，但证据实际以附件形式存在。文本审查必须区分这两种情况。
2. **模板标签不一定被保留**：用户把"涉及终端：如IOS、Android…"整行替换为"iOS、Android"，标签前缀丢失，内容落入区块自由行。按区块而非按标签判断填充，容错更好。
3. **需求模板结构顺带捕获**：11900 默认模板为【需求描述（重点）】【友商信息】【预期效果】【期望解决时间】【其他补充】，可用于"标 Bug 实为需求"的内容识别。
4. **【预计结果】为空是否 fail 需要权衡**：该单预期结果可从问题描述推出（displayname 应为非必传），旧 skill 的"expected 必填"会误杀此类工单——支持"按维度判断、逐区块参考"的改法。

## 9. 已确认的决策（2026-07-17 与用户确认）

1. **非 Bug 工单不做处理**。issuetype ≠ Bug → 不进入审查流程，不在本次任务范围；issuetype = Bug → 进入审查。
2. **类型误标要识别并给建议**。issuetype=Bug 但内容实为需求等（如 11900 有人工内容而 11901 纯模板）是典型不规范提交，大模型应判断出来并给出 actionable 建议，例如"这不是 bug，请修改工单类型为需求（需求是产品经理的工作内容）"。
3. **定位：工单审查 ≠ 问题分析**。审查只卡"最基本的要求"，不分析附件、日志内容、源码等（那是问题分析的深度）。附件/日志分析等场景待工单审查完成后再考虑接入。
4. **充分性按整体维度判断，不按字段必填**。采纳 evaluate-jira-bug-quality 的原则：证据可出现在任何叙述字段（11901/description/summary/comment 合并看）、仅模板不算内容、不强求与该 Bug 无关的信息。无 11901 但 description 有实质内容 → 可放行。
5. **getFields() 暂不落 MCP 侧**，保留在调研脚本中；字段映射扩展等开发阶段再议。
6. **删除 8 个子分类，Bug 取广义缺陷定义**。bug 不一定是程序问题，可能是文档、环境、配置、demo 问题（如"按照文档执行失败了"），只要问题描述清晰，工单内容即为合格。区分子类需要问题分析深度，超出工单审查定位。classification 只承载类型层面判断：`Bug` / `类型误标：需求` / `类型误标：其他`。
7. **全部评论都计入证据**。创建者和讨论者的评论都影响工单审查（评论往往相互触发补充，且无约束谁可补充），统一作为大模型审查输入。附带收益：failed 工单有人评论后 updated 变化会触发重审，评论补充可使工单转为合格，与既有去重机制自然衔接。

## 10. 讨论中（未收敛）

- "证据存在性"的口径：日志区块/正文有日志文本 **或** 存在附件（仅看有无、不看内容）即算有证据。待确认
- skip 的去重语义：按 failed 同构记录（记录工单 updated，更新后重查），工单类型后续改为 Bug 时能重新触发审查。已提方案，用户未异议

## 11. 场景细分与动态要求（讨论稿，2026-07-17）

统一的硬卡项不成立：纯 UI 问题只需 SDK 版本，登录失败才需要 AppKey。合格标准应为**通用底座 + 场景动态要求**。

### 11.1 真实数据观察（最近 100 个 HIM Bug 标题分析）

**三类报单人群体**（可用标题前缀、components、11901 模板填写情况辅助识别）：

| 群体 | 识别信号 | 环境身份的合理要求 |
|---|---|---|
| 客户工单 | 标题带客户群名/AppKey（如【T2-元梦空间（1102231218169353）】）；走 11901 模板 | AppKey + SDK版本 + 平台 |
| QA/内部测试单 | 标题带功能前缀（【单聊迁移】【消息搜索】【thread子区】【第二通道】【ngi】）；component = QA | 测试环境/集群 + 功能入口 |
| 内部服务单 | component = REST/msync/Console/Callback（队列、DLQ、迁移、计费、网关） | 环境/集群 + 服务名 |

**标题聚类**（用户原始 4 类之外的发现）：崩溃类（崩溃/crash，5+ 个）、安全漏洞类（IDOR/Token/泄漏/未授权，4 个）、消息搜索簇（8 个）、撤回/编辑/pin 等消息操作簇、推送簇、回调簇、计费/账单簇（3 个）、服务端基础设施簇（队列/DLQ/迁移/flink，8+ 个）。

### 11.2 场景清单草案（15 个 + 通用底座）

**通用底座（所有 Bug 必须）**：问题现象 = 什么操作/条件下 + 实际结果（预期可明确推断即可）。

**环境身份（所有 Bug 必须，按报单群体取其一）**：客户单 → AppKey + SDK版本 + 平台；QA 单 → 测试环境/集群；内部服务单 → 环境/集群 + 服务名。SDK 侧问题（含 QA 测 SDK）必须有 SDK版本 + 平台。

| # | 场景 | 识别信号（关键词/component） | 场景必须项 | 建议项 |
|---|---|---|---|---|
| 1 | 崩溃/卡死 | 崩溃、crash、闪退、ANR | 崩溃堆栈（正文或附件）；触发路径 | 机型/OS、复现率 |
| 2 | 登录/连接 | 登录、连接、断线、code 2xx/3xx、地区/VPN | 错误码/错误信息；发生时间 | 账号、网络/地区、日志 |
| 3 | 消息收发 | 发送失败、收不到、丢失、延迟、重复、乱序 | 会话类型（单聊/群/聊天室）；消息类型；现象+时间 | 消息ID、收发双方、日志 |
| 4 | 附件/媒体 | 上传、下载、图片、语音、视频、缩略图、附件 | 文件类型/大小；现象/报错 | 网络、样本附件 |
| 5 | 消息操作 | 撤回、编辑、搜索、置顶、pin、已读回执 | 操作 + 现象 + 预期差异 | 消息ID、时间 |
| 6 | 联系人/群组/聊天室/子区 | 好友、黑名单、群、聊天室、thread、成员 | 对象ID（群/聊天室/用户）；操作 + 现象 | 角色、双方账号 |
| 7 | 会话/多端同步 | 会话列表、未读数、多端、漫游、同步 | 什么数据与预期不符 | 账号、多端对比、截图 |
| 8 | 离线推送 | 推送、push、APNs、厂商通道、角标 | 平台 + 推送通道；现象（收不到/展示错误） | 推送token、证书、消息ID |
| 9 | 回调 | 回调、callback、发送前/发送后 | 回调类型；现象（未收到/内容错误）；时间 | 回调地址、请求/响应示例 |
| 10 | 控制台/计费 | console、配置、计费、账单、套餐、支付 | 配置项/功能入口；预期 vs 实际 | 截图、时间点 |
| 11 | 文档/demo | 文档、demo、示例、按照文档 | 文档链接/位置；执行到哪一步失败；预期 | 环境信息 |
| 12 | UI/交互 | UI、按钮、页面、弹窗、显示、CallKit 界面 | 操作路径；现象（截图/录屏，附件可承载） | 机型/系统版本 |
| 13 | 安全 | 漏洞、泄漏、IDOR、未授权、token、安全 | 受影响接口/组件；复现路径 | 严重度、发现方式 |
| 14 | 服务端内部 | 队列、DLQ、迁移、集群、flink、job、网关 | 现象 + 影响；时间窗 | 日志、告警 |
| 15 | 性能/资源 | 卡顿、内存、CPU、耗电、延迟高 | 场景 + 指标现象 | 性能数据、火焰图 |

**归类规则**：LLM 取主场景（必要时主+次），按主场景检查必须项；无法归入任何场景时按通用底座 + 环境身份检查。必须项缺失 → fail（reason 列出场景和缺失项）；建议项缺失 → 写进建议不 fail。

### 11.3 确认情况

- 场景清单颗粒度（15 个）：**已通过**（2026-07-18 用户确认"这个分类就挺好的"）
- 审查范围：QA 内部测试单和内部服务单是否与客户工单同等进入审查？（仍未确认；动态要求已支持按报单群体区分）
- 各场景必须项/建议项的划分：随整体框架一并确认，未逐项异议

### 11.4 兜底标准（归入不了 15 场景时启用，2026-07-18 讨论稿）

**旧 skill 9 个必填字段在新框架中的去向**：sdkVersion/sdkPlatform/appId → 环境身份；description/actual → 通用底座；deviceInfo → 场景项（崩溃/UI/性能）；steps → 场景项（文档/UI）或放宽为触发条件；expected → 宽松项；module → 不再要求（components 字段 100% 自带）。

**用户提出的兜底硬卡 5 项**（2026-07-18 确认通过）：`sdkVersion`、`sdkPlatform`、`expected`、`actual`、`description`。内容填写位置不规范可接受（证据可出现在任何叙述字段），但信息必须存在。同时确认：①这 5 项是 15 个场景的公共底座（场景 = 底座 + 场景必须项；兜底 = 只查底座）；②expected 按"可推断算有"放行，不硬卡显式填写；③sdk\* 按适用条件执行（SDK 相关单必须，纯服务端/控制台单用环境/集群+服务名替代）；④AppKey 不进底座，保留为场景必须项。
