# Jira 6.3.6 Webhook 调研结论

日期：2026-07-11

## 背景

当前项目第一版 Jira 集成代码位于：

`/Users/asterisk/Codes/ai/easemob-sdk-agent/src/jira/jira-client.ts`

该文件已经实现 Jira REST API v2 的工单动作，包括：

- 获取工单：`GET /rest/api/2/issue/{issueKey}`
- 创建工单：`POST /rest/api/2/issue`
- 修改工单：`PUT /rest/api/2/issue/{issueKey}`
- 删除工单：`DELETE /rest/api/2/issue/{issueKey}`
- 添加关注人：`POST /rest/api/2/issue/{issueKey}/watchers`

本次调研目标是确认 Jira 6.3.6 是否支持 webhook，以便后续通过 webhook 接收用户提交工单、修改工单事件。

## 结论

Jira 6.3.6 支持 webhook，可以用于接收工单创建和工单更新事件。

但需要注意：webhook 不属于 Jira 6.3.6 的 `/rest/api/2` issue CRUD API。Jira 6.3.6 REST API v2 官方文档中没有 `webhook` 资源。Webhook 是 Jira 的独立扩展能力，管理入口在 Jira 管理后台，也有独立 REST 资源路径。

对本项目架构的直接影响：

1. 可以继续采用 webhook 作为 Jira 到本系统的事件入口。
2. 不应把 webhook 接收逻辑塞进现有 `JiraClient` 的 issue CRUD 代码里。
3. 建议拆出独立模块，例如：
   - `JiraWebhookReceiver`：本系统暴露 HTTP endpoint，接收 Jira POST。
   - `JiraWebhookAdminClient`：可选，仅当需要程序化注册 webhook 时才实现。
4. 如果没有 Jira 管理员权限，无法完成真实 webhook 配置。需要运维或 Jira 管理员在 Jira 后台配置。

## 官方资料依据

### Jira 6.3 管理后台支持 Webhooks

Jira 6.3 官方文档存在 `Managing Webhooks` 页面：

https://confluence.atlassian.com/jira063/managing-webhooks-683542588.html

该页面说明：

- Webhooks 是用户定义的 HTTP POST callback。
- 它用于让远端应用接收 Jira 的 push notification，避免轮询。
- 管理入口为 Jira 管理后台：
  `System > Advanced > Webhooks`
- 操作需要 `JIRA Administrators` 全局权限。

这说明 Jira 6.3 已经具备 webhook 管理界面。

### Jira webhook 支持 issue created / issue updated

Atlassian Jira Server webhook 文档：

https://developer.atlassian.com/server/jira/platform/webhooks/

该文档列出的 issue 相关事件包括：

- `jira:issue_created`
- `jira:issue_updated`
- `jira:issue_deleted`
- `jira:worklog_updated`

本项目当前需要的是：

| 业务动作 | Jira webhook 事件 |
| --- | --- |
| 用户提交/创建工单 | `jira:issue_created` |
| 用户修改工单 | `jira:issue_updated` |

### webhook REST 管理路径独立于 `/rest/api/2`

Atlassian Jira Server webhook 文档说明，注册 webhook 使用独立路径：

```text
POST <JIRA_URL>/rest/webhooks/1.0/webhook
```

查询、修改、删除路径为：

```text
GET    <JIRA_URL>/rest/webhooks/1.0/webhook
GET    <JIRA_URL>/rest/webhooks/1.0/webhook/{id}
PUT    <JIRA_URL>/rest/webhooks/1.0/webhook/{id}
DELETE <JIRA_URL>/rest/webhooks/1.0/webhook/{id}
```

这与现有 `JiraClient` 使用的 `/rest/api/2/issue` 不是同一组 API。

### Jira 6.3.6 REST API v2 文档没有 webhook 资源

Jira 6.3.6 REST API v2 官方文档：

https://docs.atlassian.com/jira/REST/6.3.6/

在该文档中搜索 `webhook`、`jira:issue_created`、`jira:issue_updated` 均未发现对应 REST v2 资源。

这进一步确认：不能根据 `/rest/api/2` 文档判断 webhook 不存在；webhook 是独立能力。

## Jira 管理员需要如何配置

在 Jira 6.3 后台：

1. 使用具备 `JIRA Administrators` 全局权限的账号登录。
2. 进入 `System > Advanced > Webhooks`。
3. 创建 webhook。
4. URL 填写本系统暴露的 webhook 接收地址，例如：

```text
https://<our-domain>/integrations/jira/webhook
```

5. 事件选择：

```text
Issue Created
Issue Updated
```

6. Scope 建议不要选 all issues，优先用 JQL 限定项目，例如：

```text
project = ABC
```

7. 不要勾选 `Exclude body`。本系统需要 JSON body 中的 `issue`、`user`、`changelog` 等信息。
8. 保存后创建或修改一个测试工单，观察本系统接收日志。

## webhook payload 关键信息

Jira issue webhook 的 body 通常包含：

- `webhookEvent`
- `timestamp`
- `user`
- `issue`
- `changelog`
- `comment`

对本项目最重要的字段：

```json
{
  "webhookEvent": "jira:issue_updated",
  "timestamp": 1525698237764,
  "user": {
    "name": "operator",
    "key": "operator",
    "displayName": "Operator"
  },
  "issue": {
    "id": "10001",
    "key": "ABC-1",
    "fields": {
      "summary": "Example issue"
    }
  },
  "changelog": {
    "items": [
      {
        "field": "summary",
        "fromString": "Old summary",
        "toString": "New summary"
      }
    ]
  }
}
```

`changelog` 只在 `jira:issue_updated` 事件中稳定有用。后续如果要判断“用户修改了哪些字段”，应优先读取 `changelog.items`。

## 架构建议

推荐方案：Jira webhook 接收端独立于 Jira REST client。

建议数据流：

```text
Jira issue event
  -> Jira webhook HTTP POST
  -> 本系统 webhook receiver
  -> 快速校验并返回 2xx
  -> 事件入队/落库
  -> 异步处理：识别 created/updated、解析 issue key、读取 changelog、同步业务状态
```

原因：

- webhook 是 Jira 主动推送，不是本系统主动调用 Jira。
- webhook 接收端的可靠性、鉴权、幂等、异步处理，与 `JiraClient` 的 issue CRUD 职责不同。
- Jira 6.3 很老，webhook 很可能是同步触发。接收端不应在 HTTP 请求里执行长耗时逻辑。

## 风险与约束

1. 需要 Jira 管理员权限。

   当前用户不是管理员，因此无法直接完成真实 Jira 配置。必须由运维或 Jira 管理员配置 webhook。

2. 真实环境可能存在安全策略。

   即使 Jira 6.3 支持 webhook，企业环境仍可能因为网络、代理、白名单、插件禁用等原因导致回调失败。需要实际验证。

3. webhook 默认缺少强签名机制。

   接收端应至少做以下一种保护：

   - 只允许 Jira 出口 IP 访问。
   - URL 中带随机 token。
   - 反向代理层做 Basic Auth 或固定 header 校验。
   - 内网专线或 VPN 限制访问面。

4. 接收端必须快速返回。

   建议 HTTP handler 完成基础校验后立即返回 `204` 或 `200`，复杂处理异步执行。

5. 需要幂等处理。

   Jira webhook 可能因为网络或重试导致重复事件。后续实现时建议使用事件关键信息做去重，例如：

   - `webhookEvent`
   - `timestamp`
   - `issue.id`
   - `issue.key`
   - `changelog.id`

   具体幂等键需要等真实 payload 验证后再最终确定。

## 待真实环境验证的问题

以下问题无法仅靠公开文档完全确认，需要运维配置后用测试脚本验证：

1. 当前 Jira 6.3.6 实例是否启用了 webhook 管理功能。
2. `System > Advanced > Webhooks` 是否可见。
3. Jira 服务器是否能访问本系统 webhook URL。
4. 真实 payload 是否包含 `webhookEvent`、`issue`、`user`、`changelog`。
5. `jira:issue_updated` 是否在所有目标修改动作中都带 `changelog.items`。
6. Jira 失败重试行为如何，是否会重复投递。
7. 是否能通过 `/rest/webhooks/1.0/webhook` 程序化注册，或只能由管理员后台手动配置。

## 验证材料

本目录提供两个验证脚本/文件：

- `webhook-receiver.mjs`：本地 webhook 接收服务，用于接收 Jira POST 并打印关键信息。
- `sample-issue-updated-payload.json`：模拟 Jira `jira:issue_updated` payload。

本地先用模拟 payload 验证接收脚本：

```bash
node docs/research/jira-webhook/webhook-receiver.mjs
```

另一个终端执行：

```bash
curl -i \
  -X POST \
  -H 'Content-Type: application/json' \
  --data-binary @docs/research/jira-webhook/sample-issue-updated-payload.json \
  'http://127.0.0.1:8097/jira/webhook?token=local-test-token'
```

预期：

- curl 返回 `204 No Content`。
- 接收脚本终端打印 `jira:issue_updated`、issue key、user、changelog 字段变更。

运维配置真实 Jira webhook 时，可以临时把 URL 指到可被 Jira 访问的测试服务地址：

```text
https://<test-domain>/jira/webhook?token=<shared-secret>
```

如果真实 Jira 成功投递，本脚本会打印真实 payload 摘要，并把完整 body 写入本地日志文件。
