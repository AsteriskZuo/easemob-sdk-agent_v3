# easemob-agent · 架构设计 Spec（骨架）

> 版本：v0.6（双循环 + 出口工具群）
> 日期：2026-09-14（2026-09-26 修订）
> 状态：待评审
> 定位：本文档是全部设计的**入口与骨架**——只固化原则、架构与机制清单。每个关键概念与机制是 `design/` 下的独立文档：**骨架有问题调骨架，细节有问题调节点文档**；细节文档可增删改，骨架保持瘦身。
> 一句话：一个以 **skill 包**为能力单元、以**业务组合体**（提示词 + skill 组 + agent-cli + 大模型）为执行单位、以**双循环 + 处理链**为消化机制的模块化单体平台——触发从入口进来包装成任务，入口事件循环驱动业务在处理链上执行，业务完成即把结果无脑扇出：派生事件回入口队列由关注业务消化、投出口队列由出口工具投递。

## 1. 设计原则

| 原则 | 说明 |
|------|------|
| Skill 一等公民 | skill 是遵循公开规范的能力单元，业务的组成部分；不为本平台做适配 |
| 业务组合体 | 业务 = 提示词 + 一组 skill + agent-cli + 大模型（+ 必选入口、可选出口）；触发与订阅属于业务，不属于 skill |
| 公共能力平台化 | 入口、出口、密钥、日志、会话、控制台、任务队列由平台统一提供 |
| 契约优先，接口稳定 | 模块间一切交互受版本化契约约束。**接口一旦发布不轻易修改**：只向后兼容新增，破坏性变更升契约版本号（changelog 随文档维护） |
| Agent 配置化 | agent 与 model 是部署配置而非代码耦合；适配器要薄（候选 agent 名单唯一定义见 `design/lifecycle.md` §5） |
| 单进程部署，多进程执行 | 平台是一个部署单元；agent 与 skill 的执行永远在独立子进程/沙箱中 |
| 最小设计 | **没有真实用途的字段与功能不预先设计**（反例：已有 `timestamp` 就不再设 `last_timestamp`）。与架构扩展区分：扩展点要预留，但不预填没有用途的内容 |

## 2. 总体架构：模块化单体

一个服务，内部分为边界清晰的模块群：

```
┌──────────────────────────────────────────────────────────────┐
│ 入口模块群（每个事件源一个独立小模块）                          │
│   企业微信入口（智能机器人）│ Jira 入口 │ GitHub 入口 │          │
│   Webhook 入口 │ 定时/手动 | …                                │
├──────────────────────────────────────────────────────────────┤
│ 出口工具群（每个通知目的地一个内置投递器模块）                   │
│   企微智能机器人 │ 企微群 webhook │ 邮件 │ 自定义 webhook │      │
│   jira / confluence / github 操作 │ …                          │
├──────────────────────────────────────────────────────────────┤
│ 编排内核（平台心脏：一副机械，两个循环）                          │
│   入口事件循环 │ 出口事件循环 │ 业务注册表 │ 生命周期运行时       │
│   任务队列 ×2（SQLite：入口队列 / 出口队列）                     │
├──────────────────────────────────────────────────────────────┤
│ Skill 包仓（动态加载，public / private）                        │
│   Skill 注册表 │ jira 工具 │ 企微工具 │ 各业务私有 skill │ …    │
├──────────────────────────────────────────────────────────────┤
│ 平台公共模块                                                    │
│   密钥管理 │ 日志模块 │ 通道模块 │ 出口注册表 | …                │
├──────────────────────────────────────────────────────────────┤
│ 控制台模块（含 UI）                                             │
└──────────────────────────────────────────────────────────────┘
```

> 注：**出入口对称**——出口 = 出口事件循环 + 出口工具群。业务完成即把派生事件无脑扇出到两个队列：入口队列由关注业务消化（订阅匹配），出口队列由产出方业务的出口绑定消化（归属匹配，不过 LLM、毫秒级）。两类「触达能力」各司其职：**结果投递**归出口工具；**执行内调用**（如审查过程中读写 Jira）以 public skill 形式由 Skill 包仓提供。

**要点：**

1. **模块契约纪律（命门）**：模块间只许通过公开接口调用，禁止跨模块直接引用内部实现，包结构与依赖规则在代码层面强制。契约纪律就是未来拆分能力的保险单。
2. **出入口对称抽象**：新事件源只是新增一个入口小模块；新通知目的地只是新增一个出口工具模块，不动内核。
3. **心脏不认识业务**：入口模块做源适配（含会话标识提取规则），心脏只读信封字段做机械调度。
4. **双循环隔离**：LLM 推理（分钟级、沙箱百 MB 级）与结果投递（毫秒级网络 IO）资源画像完全不同——分开后大并发下耗时任务再堵，已完成业务的通知也不被堵；两道并发闸门各自可调（见 `design/scheduler.md` §5）。

## 3. 核心机制一览

| 机制 | 一句话 | 详见 |
|------|--------|------|
| 调度循环（心脏） | 一副机械两个实例：入口事件循环驱动业务执行（LLM），出口事件循环专司结果投递（不过 LLM）；取任务 → 找关注者 → 挂通道 → 驱动消化 | `design/scheduler.md` |
| 任务队列 | 入口/出口两条，同一契约；统一入口缓冲带；FIFO、SQLite 持久化；第一阶段不预留并行接口 | `design/scheduler.md` |
| 入口适配器 | 一个事件源一个小模块：验签 → 包装信封 → 落队，立即返回；新事件源不动内核 | `design/entries.md` |
| 出口 | 内置出口工具菜单（企微/邮件/webhook/jira/confluence/github…）+ 业务出口绑定；完成即扇出、归属匹配、同目标串行 | `design/glossary.md` |
| 通道 | 业务通道 channel_id = `source__session_id__business_id`（同会话同业务串行，其余并行）；出口通道 = `exit__目标`（同目标串行，保序 + 天然限流）；并发语义是通道属性而非业务配置 | `design/scheduler.md` `design/channel-model.md` |
| 并发闸门 | 两道全局信号量：业务闸门 `task_concurrency` 保机器（LLM 推理任务、沙箱百 MB 级，量级几十），出口闸门 `result_concurrency` 管结果投递（毫秒级，可宽）；控制台各自可调 | `design/scheduler.md` |
| 业务处理链 | 事件的全部关注者，**链内并行消化**；顺序的唯一表达方式 = 关注上游产出事件；门禁判输入就绪 | `design/processing-chain.md` |
| 生命周期 | 业务的一次完整执行，跑完即销毁；多阶段需求转化处理，平台不支持多阶段代码 | `design/lifecycle.md` |
| 通道模型 | 业务通道 ↔ agent-cli 会话，一张映射表；创建/恢复/压缩/清空四操作；三种「会话」辨析 | `design/channel-model.md` |
| Skill 包 | 公开规范的能力单元；public/private 可见性；MCP 不支持、不预留 | `design/skill-package.md` |
| 事件契约 | 信封 v1 是唯一稳定边界；契约稳定、传输可换；大产物走引用 | `design/event-contract.md` |
| 日志 | 通道/总/模块三层；error/warn/info 必打；logrotate 管分割 | `design/logging.md` |
| 控制台 | 全部控制开关与仪表盘的集合，本身无业务逻辑 | `design/console-design.md` |
| 用户与账号 | admin/member 两角色；业务归创建者、全局归管理员；不开放注册 | `design/accounts.md` |

## 4. 技术选型

**语言：TypeScript 5.x（strict）/ Node.js 24（LTS）**——① IO 密集编排与「调度循环 + 大量通道」天然同构；② 契约可编译期强制，接口稳定有工具保障；③ 控制台前后端同构，契约类型共享；④ agent CLI 生态 TS 系，适配器同语言。边界：只约束平台本体；skill 内脚本与沙箱子进程语言不限；平台不做模型推理（外包给 agent-cli），Python 的 AI 库优势用不上。

**包管理：yarn 4.14.1（corepack 启用）**——版本锁定、依赖可复现；单一仓库前后端共享 `contracts/` 类型。

**数据库：SQLite**——内部工具、无高频并发，单进程写入与模块化单体天然匹配；零配置零运维，备份即文件拷贝。取舍说明：不选大型数据库是为避免配置/部署/维护成本；数据访问层保持薄抽象，未来数据量真上来时迁移 PostgreSQL 成本可控。驱动选型实现期前定（倾向 Node 24 内置 `node:sqlite`，零依赖；备选 `better-sqlite3`）。

## 5. MVP 路线

**一条链跑通**：GitHub 入口 + 代码 Review 业务（pi + qwen3.8max）+ 企微群 webhook 出口。

1. **M1**：事件信封契约 v1 + 注册表 + 双调度循环 + SQLite 队列 ×2（死信告警）
2. **M2**：生命周期运行时（单次执行、通道、并发闸门）+ 执行沙箱
3. **M3**：代码 Review + 企微出口工具，端到端跑通
4. **M4**：控制台 + 第二个业务（日志分析），验证「只写业务组合」承诺与处理链串联

## 6. 演进方向

契约纪律保证拆分能力常备，触发条件是真实需求而非预防性设计：

- **执行层 worker 化**：执行规模/隔离要求上升时，把执行沙箱层拆为独立 worker 集群，信封契约原样平移——两个循环天然就是两个 worker 池的雏形（业务执行池 + 投递池）；虚拟通道届时物化为子任务队列，语义不变；
- **入口独立部署**：入口适配器本就无状态，按需拆出；出口工具同为无状态投递器，随出口循环拆出即可；
- **数据库升级**：SQLite → PostgreSQL，数据访问层薄抽象保证迁移成本可控。

## 7. 风险与待决策项

| 项 | 说明 | 对策 |
|----|------|------|
| Agent 适配器维护 | agent CLI 升级可能破坏适配；各家配置与模型优先级差异大 | 适配器薄 + 版本锁定 + 接入时逐项确认（见 `design/lifecycle.md`） |
| 循环通知 | 配置错误可致雪崩 | 业务不得订阅自己的通知 + hop_count + 死信（已定）；出口循环不派生事件，天然无循环 |
| 单体爆炸半径 | 主进程故障影响全平台 | 执行沙箱化（已隔离）；主进程无状态化，状态全在 DB |
| 沙箱冷启动 | 按需唤起有启动开销 | 热池预热 |
| 出口平台限流 | 企微/Jira 侧有调用限制 | 出口通道同目标串行 = 天然排队限流（见 `design/channel-model.md` §2） |
| 厂商配额触顶 | 按主账号计，内部规模充足 | 商务提额 → 多账号 → 多厂商（见 `design/scheduler.md`） |
| 失败重试策略 | 待真实失败样本分析 | 第二阶段再议（见 `design/failure-handling.md`）；第一阶段日志留痕 + 出口投递有界重试（已定例外） |
| 会话上下文托管 | 上下文在 agent-cli 侧 | 平台只维护通道映射（见 `design/channel-model.md`），token 成本不成立为平台风险 |
