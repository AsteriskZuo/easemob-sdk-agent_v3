# easemob-agent · 架构设计 Spec（骨架）

> 版本：v0.8（双循环 + 出口工具群 + 代码即流程 + 资产三族）
> 日期：2026-09-14（2026-09-30 修订；2026-10-04 修订：§2 总体架构图补装配层、对账 monorepo 模块）
> 状态：待评审
> 定位：本文档是全部设计的**入口与骨架**——只固化原则、架构与机制清单。每个关键概念与机制是 `design/` 下的独立文档：**骨架有问题调骨架，细节有问题调节点文档**；细节文档可增删改，骨架保持瘦身。
> 一句话：一个以**资产三族（包/工具/skill，git 登记、使用时组合）**为资产形态、以**业务流程程序**（业务 = 包 + 配置；代码即流程 + 业务 SDK）为执行单位、以**双循环 + 处理链**为消化机制的模块化单体平台——触发从入口进来包装成任务，入口事件循环驱动业务在处理链上执行（spawn 业务流程程序，一入一出），业务完成即把结果无脑扇出：派生事件回入口队列由关注业务消化、投出口队列由出口工具投递。

## 1. 设计原则

| 原则 | 说明 |
|------|------|
| Skill 一等公民 | skill 是遵循公开规范的能力单元，独立的可复用资产；不为本平台做适配 |
| 代码即流程 | 业务 = 包 + 配置（包承载全部流程逻辑，配置是资源声明）；平台不编排流程、不认识业务内容；触发与订阅属于业务，不属于 skill |
| 公共能力平台化 | 入口、出口、密钥、日志、会话、控制台、任务队列、agent 调用服务由平台统一提供 |
| 契约优先，接口稳定 | 模块间一切交互受版本化契约约束。**接口一旦发布不轻易修改**：只向后兼容新增，破坏性变更升契约版本号（changelog 随文档维护） |
| 稳定优先 | 平台是基础组件：任何业务错误不得影响平台与其他业务——子进程隔离 + 超时强杀 + 输出上限 + agent 配额四道机械防线（`design/business-workflow.md` §6） |
| Agent 内核唯一 | agent 内核 = pi（决策见 `docs/decisions/2026-09-27-agent-kernel-and-execution-mode.md`）；模型是部署/业务配置而非代码耦合 |
| 单进程部署，多进程执行 | 平台是一个部署单元；业务流程程序与 agent 的执行永远在独立子进程/沙箱中 |
| 最小设计 | **没有真实用途的字段与功能不预先设计**（反例：已有 `timestamp` 就不再设 `last_timestamp`）。与架构扩展区分：扩展点要预留，但不预填没有用途的内容 |

## 2. 总体架构：模块化单体

一个服务，内部分为边界清晰的模块群（维护版图源：`design/architecture-overview.puml`（PlantUML）与 `design/architecture-overview.mmd`（Mermaid，GitHub/在线可直接渲染），内容一致、改图同步）：

```
┌──────────────────────────────────────────────────────────────┐
│ 控制台 app/console（React SPA，经管理 API 读写，无业务逻辑）      │
├──────────────────────────────────────────────────────────────┤
│ 装配层 app/server（模块化单体的进程本体）                       │
│   main 组装根（配置解析 + 启动自检 + 依赖接线）                  │
│   管理 API（独立 HTTP 端口）│ EntryAdapter 接口 │ ExitDriver     │
├──────────────────────────────────────────────────────────────┤
│ 入口模块群（每个事件源一个独立小模块）                          │
│   Webhook 入口 │ 企业微信入口 │ Jira 入口 │ GitHub 入口 │       │
│   定时/手动 │ …                                                │
├──────────────────────────────────────────────────────────────┤
│ 出口工具群（每个通知目的地一个内置投递器模块）                   │
│   企微群 webhook │ 邮件 │ 自定义 webhook │ 企微智能机器人 │      │
│   jira │ confluence │ github 操作                              │
├──────────────────────────────────────────────────────────────┤
│ 编排内核（平台心脏：一副机械，两个循环）                          │
│   入口事件循环 │ 出口事件循环 │ 任务队列 ×2（SQLite）            │
│   业务注册表 │ 业务组装器 ContextLoader │ 生命周期 Lifecycle      │
│   流程执行器 WorkflowRunner │ agent 调用服务 AgentService        │
├──────────────────────────────────────────────────────────────┤
│ 资产仓（git 登记、使用时物化；包/工具/skill 三族）              │
│   资产注册表 AssetRegistry（平台不内置资产）                     │
├──────────────────────────────────────────────────────────────┤
│ 平台公共模块                                                    │
│   环境配置 EnvProvider（vars/secrets 两桶）│ 日志模块 │          │
│   通道模块（ChannelPool ×2 + ChannelStore）│ 出口注册表 │ …      │
├──────────────────────────────────────────────────────────────┤
│ 基础设施（被所有模块依赖，不反向依赖）                           │
│   Database（唯一数据口）│ 契约 contracts │ env │ 日志底层        │
└──────────────────────────────────────────────────────────────┘
```

> 注：**出入口对称**——出口 = 出口事件循环 + 出口工具群。业务完成即把派生事件无脑扇出到两个队列：入口队列由关注业务消化（订阅匹配），出口队列由产出方业务的出口绑定消化（归属匹配，不过 LLM、毫秒级）。两类「触达能力」各司其职：**结果投递**归出口工具（平台内置模块）；**执行内调用**（如审查过程中读写 Jira）归工具资产（git 仓库登记，`sdk.run` 按名调用，见 `design/asset-model.md`）。

**要点：**

1. **模块契约纪律（命门）**：模块间只许通过公开接口调用，禁止跨模块直接引用内部实现，包结构与依赖规则在代码层面强制。契约纪律就是未来拆分能力的保险单。
2. **出入口对称抽象**：新事件源只是新增一个入口小模块；新通知目的地只是新增一个出口工具模块，不动内核。
3. **心脏不认识业务**：入口模块做源适配（含会话标识提取规则），心脏只读信封字段做机械调度。
4. **双循环隔离**：LLM 推理（分钟级、子进程百 MB 级）与结果投递（毫秒级网络 IO）资源画像完全不同——分开后大并发下耗时任务再堵，已完成业务的通知也不被堵；两道并发闸门各自可调（见 `design/scheduler.md` §5）。

## 3. 核心机制一览

| 机制 | 一句话 | 详见 |
|------|--------|------|
| 调度循环（心脏） | 一副机械两个实例：入口事件循环驱动业务执行（LLM），出口事件循环专司结果投递（不过 LLM）；取任务 → 找关注者 → 挂通道 → 驱动消化 | `design/scheduler.md` |
| 任务队列 | 入口/出口两条，同一契约；统一入口缓冲带；FIFO、SQLite 持久化；第一阶段不预留并行接口 | `design/scheduler.md` |
| 入口适配器 | 一个事件源一个小模块：验签 → 包装信封 → 落队，立即返回；新事件源不动内核 | `design/entries.md` |
| 出口 | 内置出口工具菜单（企微/邮件/webhook/jira/confluence/github…）+ 业务出口绑定；完成即扇出、归属匹配、同目标串行 | `design/glossary.md` |
| 通道 | 业务通道 channel_id = `source__session_id__business_id`（同会话同业务串行，其余并行）；出口通道 = `exit__目标`（同目标串行，保序 + 天然限流）；并发语义是通道属性而非业务配置 | `design/scheduler.md` `design/channel-model.md` |
| 并发闸门 | 两道全局信号量：业务闸门 `task_concurrency` 保机器（执行任务、子进程百 MB 级，量级几十），出口闸门 `result_concurrency` 管结果投递（毫秒级，可宽）；控制台各自可调 | `design/scheduler.md` |
| 业务处理链 | 事件的全部关注者，**链内并行消化**；顺序的唯一表达方式 = 关注上游产出事件；门禁判输入就绪（业务流程程序内部环节，平台无契约） | `design/processing-chain.md` |
| 业务工作流 | 代码即流程：业务 = 一个流程程序（子进程，一入一出），经业务 SDK 调 agent 服务与子程序；平台不编排 | `design/business-workflow.md` |
| 生命周期 | 业务的一次完整执行 = 流程程序的一次进程运行，退出即销毁；多阶段是程序内普通代码 | `design/lifecycle.md` |
| 通道模型 | 业务通道 ↔ agent-cli 会话，一张映射表；创建/恢复/压缩/清空四操作；三种「会话」辨析 | `design/channel-model.md` |
| 资产三族 | 包（业务代码单位，不共享）/ 工具（可复用代码组件）/ skill（可复用提示词组件）；git 三元组标识；属主 + 共享标记（创建时定、不可改）；使用时在业务上组合 | `design/asset-model.md` |
| 事件契约 | 信封 v1 是唯一稳定边界；契约稳定、传输可换；大产物走引用 | `design/event-contract.md` |
| 日志 | 四类：系统级（总纲）/ 入口循环 / 出口循环 / 业务（SDK 日志 API，按业务按 run）；error/warn/info 必打；logrotate 管分割 | `design/logging.md` |
| 控制台 | 全部控制开关与仪表盘的集合，本身无业务逻辑 | `design/console-design.md` |
| 用户与账号 | admin/member 两角色；业务归创建者、全局归管理员；不开放注册 | `design/accounts.md` |

## 4. 技术选型

**语言：TypeScript 5.x（strict）/ Node.js 24（LTS）**——① IO 密集编排与「调度循环 + 大量通道」天然同构；② 契约可编译期强制，接口稳定有工具保障；③ 控制台前后端同构，契约类型共享；④ agent CLI 生态 TS 系，适配器同语言。边界：只约束平台本体；skill 内脚本与业务子进程语言不限；平台不做模型推理（外包给 agent-cli），Python 的 AI 库优势用不上。

**包管理：yarn 4.14.1（corepack 启用）**——版本锁定、依赖可复现；单一仓库前后端共享 `contracts/` 类型。

**数据库：SQLite**——内部工具、无高频并发，单进程写入与模块化单体天然匹配；零配置零运维，备份即文件拷贝。取舍说明：不选大型数据库是为避免配置/部署/维护成本；数据访问层保持薄抽象，未来数据量真上来时迁移 PostgreSQL 成本可控。驱动选型实现期前定（倾向 Node 24 内置 `node:sqlite`，零依赖；备选 `better-sqlite3`）。

## 5. MVP 路线

**一条链跑通**：GitHub 入口 + 代码 Review 业务（pi + qwen3.8max）+ 企微群 webhook 出口。

1. **M1**：事件信封契约 v1 + 注册表 + 双调度循环 + SQLite 队列 ×2（死信告警）
2. **M2**：生命周期运行时（WorkflowRunner + AgentService + 业务 SDK、通道、并发闸门）+ 执行沙箱（分期，见 `design/business-workflow.md` §7）
3. **M3**：代码 Review + 企微出口工具，端到端跑通
4. **M4**：控制台 + 第二个业务（日志分析），验证「只写业务代码」承诺与处理链串联

**验收锚点**：平台实现完成后，以**单轮审查工单**业务全链做端到端验收（webhook 入口 → 检查 → 拉取工单 → 脱敏 → 大模型审查 → 还原 → 门禁 → 企微群 webhook 出口，见 `design/business-workflow.md` §8）。

## 6. 演进方向

契约纪律保证拆分能力常备，触发条件是真实需求而非预防性设计：

- **执行层 worker 化**：执行规模/隔离要求上升时，把执行层拆为独立 worker 集群，信封契约原样平移——两个循环天然就是两个 worker 池的雏形（业务执行池 + 投递池）；虚拟通道届时物化为子任务队列，语义不变；
- **入口独立部署**：入口适配器本就无状态，按需拆出；出口工具同为无状态投递器，随出口循环拆出即可；
- **数据库升级**：SQLite → PostgreSQL，数据访问层薄抽象保证迁移成本可控。

## 7. 风险与待决策项

| 项 | 说明 | 对策 |
|----|------|------|
| Agent 内核升级 | pi 版本升级可能破坏扩展/钩子行为；各家 hook 语义差异大（codex-cli 已否决） | 版本锁定为项目依赖 + 接入时逐项确认（见 `design/lifecycle.md` §5 与决策记录） |
| 循环通知 | 配置错误可致雪崩 | 业务不得订阅自己的通知 + hop_count + 死信（已定）；出口循环不派生事件，天然无循环 |
| 单体爆炸半径 | 主进程故障影响全平台 | 执行全部子进程化（业务流程程序 + pi，已隔离）；主进程无状态化，状态全在 DB |
| 进程冷启动 | 按需唤起有启动开销 | 热池预热 |
| 出口平台限流 | 企微/Jira 侧有调用限制 | 出口通道同目标串行 = 天然排队限流（见 `design/channel-model.md` §2） |
| 厂商配额触顶 | 按主账号计，内部规模充足 | 商务提额 → 多账号 → 多厂商（见 `design/scheduler.md`） |
| 失败重试策略 | 待真实失败样本分析 | 第二阶段再议（见 `design/failure-handling.md`）；第一阶段日志留痕 + 出口投递有界重试（已定例外） |
| 会话上下文托管 | 上下文在 agent-cli 侧 | 平台只维护通道映射（见 `design/channel-model.md`），token 成本不成立为平台风险 |
