# easemob-agent · 架构设计 Spec（骨架）

> 版本：v0.5（骨架与关键点设计基线）
> 日期：2026-09-14
> 状态：待评审
> 定位：本文档是全部设计的**入口与骨架**——只固化原则、架构与机制清单。每个关键概念与机制是 `design/` 下的独立文档：**骨架有问题调骨架，细节有问题调节点文档**；细节文档可增删改，骨架保持瘦身。
> 一句话：一个以 **skill 包**为能力单元、以**业务组合体**（提示词 + skill 组 + agent-cli + 大模型）为执行单位、以**任务队列 + 处理链**为消化机制的模块化单体平台——触发从入口进来包装成任务，调度循环驱动业务在处理链上执行，结果统一成信封回队，由关注者消化。

## 1. 设计原则

| 原则 | 说明 |
|------|------|
| Skill 一等公民 | skill 是遵循公开规范的能力单元，业务的组成部分；不为本平台做适配 |
| 业务组合体 | 业务 = 提示词 + 一组 skill + agent-cli + 大模型（+ 必选入口、可选出口）；触发与订阅属于业务，不属于 skill |
| 公共能力平台化 | 入口、出口、密钥、日志、会话、控制台、任务队列由平台统一提供 |
| 契约优先，接口稳定 | 模块间一切交互受版本化契约约束。**接口一旦发布不轻易修改**：只向后兼容新增，破坏性变更升契约版本号（changelog 随文档维护） |
| Agent 配置化 | agent（pi / codex-cli / opencode）与 model 是部署配置而非代码耦合；适配器要薄 |
| 单进程部署，多进程执行 | 平台是一个部署单元；agent 与 skill 的执行永远在独立子进程/沙箱中 |
| 最小设计 | **没有真实用途的字段与功能不预先设计**（反例：已有 `timestamp` 就不再设 `last_timestamp`）。与架构扩展区分：扩展点要预留，但不预填没有用途的内容 |

## 2. 总体架构：模块化单体

一个服务，内部分为边界清晰的模块群：

```
┌──────────────────────────────────────────────────────────────┐
│ 入口模块群（每个事件源一个独立小模块）                          │
│   企业微信入口（智能机器人）│ Jira 入口 │ GitHub 入口 │ 定时/手动 | … │
├──────────────────────────────────────────────────────────────┤
│ 编排内核（平台心脏）                                            │
│   调度循环 │ 业务注册表 │ 生命周期运行时 │ 任务队列（SQLite）    │
├──────────────────────────────────────────────────────────────┤
│ Skill 包仓（动态加载，public / private）                        │
│   Skill 注册表 │ jira 工具 │ 企微工具 │ 各业务私有 skill │ …    │
├──────────────────────────────────────────────────────────────┤
│ 平台公共模块                                                    │
│   密钥管理 │ 日志模块 │ 会话模块 | …                              │
├──────────────────────────────────────────────────────────────┤
│ 控制台模块（含 UI）—— 详见 design/console-design.md             │
└──────────────────────────────────────────────────────────────┘
```

> 注：**出口不是独立分层**——出口 = 任务队列中的可选任务，由出口型业务消化；企业微信通知、Jira 编辑、Webhook 通知等触达外部系统的能力，以 public skill 形式由 Skill 包仓提供。

**要点：**

1. **模块契约纪律（命门）**：模块间只许通过公开接口调用，禁止跨模块直接引用内部实现，包结构与依赖规则在代码层面强制。契约纪律就是未来拆分能力的保险单。
2. **出入口对称抽象**：新事件源只是新增一个入口小模块；新通知目的地只是新增/选用一个出口型业务（触达能力以 public skill 已在包仓中提供），不动内核。
3. **心脏不认识业务**：入口模块做源适配（含会话键规则），心脏只读信封字段做机械调度。

## 3. 核心机制一览

| 机制 | 一句话 | 详见 |
|------|--------|------|
| 调度循环（心脏） | 唯一主循环：取任务 → 找处理链 → 挂会话通道 → 驱动生命周期 | `design/scheduler.md` |
| 任务队列 | 统一入口缓冲带；FIFO、SQLite 持久化；第一阶段不预留并行接口 | `design/scheduler.md` |
| 会话通道 | 通道键 = `source__session_id`；同通道串行、跨通道并行；并发语义是通道属性而非业务配置 | `design/scheduler.md` `design/session-model.md` |
| 并发闸门 | 全局信号量保机器——瓶颈在本机沙箱（agent 进程百 MB 级），量级几十，控制台可调 | `design/scheduler.md` |
| 业务处理链 | 任务的有序处理序列；依赖可配置（前置失败默认不执行）；门禁判输入就绪 | `design/processing-chain.md` |
| 生命周期 | 业务的一次完整执行，跑完即销毁；多阶段需求转化处理，平台不支持多阶段代码 | `design/lifecycle.md` |
| 会话模型 | 我们的会话 ↔ agent-cli 会话，一张映射表；创建/恢复/压缩/清空四操作 | `design/session-model.md` |
| Skill 包 | 公开规范的能力单元；public/private 可见性；MCP 不支持、不预留 | `design/skill-package.md` |
| 事件契约 | 信封 v1 是唯一稳定边界；契约稳定、传输可换；大产物走引用 | `design/event-contract.md` |
| 日志 | 会话/总/模块三层；error/warn/info 必打；logrotate 管分割 | `design/logging.md` |
| 控制台 | 全部控制开关与仪表盘的集合，本身无业务逻辑 | `design/console-design.md` |
| 用户与账号 | admin/member 两角色；业务归创建者、全局归管理员；不开放注册 | `design/accounts.md` |

## 4. 技术选型

**语言：TypeScript 5.x（strict）/ Node.js 24（LTS）**——① IO 密集编排与「一个调度循环 + 大量会话通道」天然同构；② 契约可编译期强制，接口稳定有工具保障；③ 控制台前后端同构，契约类型共享；④ agent CLI 生态 TS 系，适配器同语言。边界：只约束平台本体；skill 内脚本与沙箱子进程语言不限；平台不做模型推理（外包给 agent-cli），Python 的 AI 库优势用不上。

**包管理：yarn 4.14.1（corepack 启用）**——版本锁定、依赖可复现；单一仓库前后端共享 `contracts/` 类型。

**数据库：SQLite**——内部工具、无高频并发，单进程写入与模块化单体天然匹配；零配置零运维，备份即文件拷贝。取舍说明：不选大型数据库是为避免配置/部署/维护成本；数据访问层保持薄抽象，未来数据量真上来时迁移 PostgreSQL 成本可控。驱动选型实现期前定（倾向 Node 24 内置 `node:sqlite`，零依赖；备选 `better-sqlite3`）。

## 5. MVP 路线

**一条链跑通**：GitHub 入口 + 代码 Review 业务（pi + qwen3.8max）+ 企微出口。

1. **M1**：事件信封契约 v1 + 注册表 + 调度循环 + SQLite 队列（死信告警）
2. **M2**：生命周期运行时（单次执行、会话通道、并发闸门）+ 执行沙箱
3. **M3**：代码 Review + 企微出口，端到端跑通
4. **M4**：控制台 + 第二个业务（日志分析），验证「只写业务组合」承诺与处理链串联

## 6. 演进方向

契约纪律保证拆分能力常备，触发条件是真实需求而非预防性设计：

- **执行层 worker 化**：执行规模/隔离要求上升时，把执行沙箱层拆为独立 worker 集群，信封契约原样平移；虚拟会话通道届时物化为子任务队列，语义不变；
- **入口独立部署**：入口适配器本就无状态，按需拆出；出口型业务随内核执行，无独立部署需求；
- **数据库升级**：SQLite → PostgreSQL，数据访问层薄抽象保证迁移成本可控。

## 7. 风险与待决策项

| 项 | 说明 | 对策 |
|----|------|------|
| Agent 适配器维护 | agent CLI 升级可能破坏适配；各家配置与模型优先级差异大 | 适配器薄 + 版本锁定 + 接入时逐项确认（见 `design/lifecycle.md`） |
| 循环通知 | 配置错误可致雪崩 | 业务不得订阅自己的通知 + hop_count + 死信（已定） |
| 单体爆炸半径 | 主进程故障影响全平台 | 执行沙箱化（已隔离）；主进程无状态化，状态全在 DB |
| 沙箱冷启动 | 按需唤起有启动开销 | 热池预热 |
| 出口平台限流 | 企微/Jira 侧有调用限制 | 触达 skill 内置速率限制，经任务队列天然排队 |
| 厂商配额触顶 | 按主账号计，内部规模充足 | 商务提额 → 多账号 → 多厂商（见 `design/scheduler.md`） |
| 失败重试策略 | 待真实失败样本分析 | 第二阶段再议（见 `design/failure-handling.md`）；第一阶段日志留痕 |
| 会话上下文托管 | 上下文在 agent-cli 侧 | 平台只维护会话映射（见 `design/session-model.md`），token 成本不成立为平台风险 |
