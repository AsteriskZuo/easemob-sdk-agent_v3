# 业务处理链

> 机制文档。术语定义见 `design/glossary.md`（处理链、门禁、event_type 为唯一定义处）。场景验证见 `design/validation.md`。

## 1. 链的生成

任务是事件包装后的可执行单元。任务被取出后，关注 `(source, event_type)` 的业务组成该任务的**处理链**——关注是下游的声明，上游不知道谁关注了自己。

**链内并行消化**：每个关注者有自己的串行键（`source__session_id__business_id`），各自挂通道、互不等待。无依赖关系的业务（如「审查完成」的企微通知与 crash 分析）天然并行，互不阻塞。

## 2. 顺序与依赖：唯一表达方式 = 关注上游产出事件

**平台不提供链内排序机制**——业务间有先后要求时，用事件订阅表达：

- **B 依赖 A** → B 关注 A 的产出事件类型（`业务id.产出类型`）。A 不完成、事件不存在，B 自然不会被触发——顺序是事件流的自然结果；
- **多重依赖**（如日志分析依赖「审查 + crash」）→ 关注**最后一段**的产出事件（`crash.completed`）：链式蕴含前序已完成（crash 存在 ⇒ 审查已完成），前序结果经 payload 引用 / `correlation_id` 追溯获取；
- **失败传播**：产出方失败**默认不派生** → 下游天然不触发（这就是「前置失败默认不执行」）；确需「失败也执行」时，产出方配置**失败也派生**（派生事件带失败状态），由下游门禁验收决定接不接。

## 3. 门禁：只验收，不等待

门禁的定义与实现形式（双门禁、大模型执行、弱/强约束）见 `design/glossary.md`——唯一定义处。

与本文相关的纪律只有一条：**门禁不做「等待」**。需要等待的依赖必须表达为事件订阅（§2）。反例：日志分析若配成「关注审查结果 + 门禁检查 crash 已完成」——它与 crash 分析并行触发，门禁不过即 failed 完结，crash 随后完成也不会再唤醒它，**日志分析永久丢失**（验证见 `design/validation.md` S4'）。

## 4. 业务间的数据约定：没有隐性接口

**平台内不存在隐性接口**——业务间的输入输出约定不在系统内部，而在 **skill 层**：

- 上游 skill 规定自己的输出格式，下游 skill 按约定读取；
- 格式不一致是 skill 层的问题，**不需要也不应该修改服务**；
- 所有跨业务的数据格式约定都必须显性列举（例如 Jira comments 的格式约定），不允许"靠默契"。

数据媒介两种：结果信封（入队）与外部业务系统（如 Jira comments——单一真相留在业务系统，人也可读）。

## 5. 防循环

两道防线：

1. **业务不得订阅自己的通知**（注册时校验，不言而喻的基本纪律）；
2. **hop_count（跳数上限）**：信封里的转发计数器——任务 A 的结果触发任务 B 时 +1，B 又触发 C 时再 +1……超过阈值判定为循环，进死信并告警。防的是 A→B→A 式的乒乓循环（阈值属实现期配置）。

## 6. 示例（仅为理解；完整验证矩阵见 `design/validation.md`）

`R.2 → B.2 →p {C.2, B.3 →p B.4}`：jira 工单更新触发单轮审查（B.2）→ 审查完成派生 `b2.review.completed` → 企微通知（C.2）与 crash 分析（B.3）**并行**消化 → crash 完成派生 `b3.crash.completed` → 日志分析（B.4）执行。B.4 的双重依赖（审查 + crash）由「关注最后一段产出」一个订阅蕴含；B.2 失败不派生，下游全部静默。
