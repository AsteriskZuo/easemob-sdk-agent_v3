# 失败处理

> 状态：**占位**。第一阶段只做日志留痕；系统的失败处理属于第二阶段工作。

## 第一阶段（当前）

**有且仅有：日志留痕。** 任何失败都能按 `event_id` / `lifecycle_id` / 通道键 / `correlation_id` 回溯现场（规则见 `design/logging.md`）。

## 第二阶段（待实际代码与业务落地后再议）

失败处理策略必须建立在已实现业务的真实失败样本上深入分析，**只增加必要的异常处理**——设计阶段（无论人还是 AI）不写代码就想不全，不预先空想方案。届时要回答的问题先占位：

1. **失败分类**：开发期失败（配置错误、prompt 问题、契约不符）vs 运行期失败（agent 崩溃、厂商 429、超时、沙箱资源耗尽）——先分类再谈针对性策略，不一概而论、不盲目扩大；
2. **重试粒度与预算**：任务级重跑的边界与成本（agent 调用分钟级、数万 token；区分可重试与重试无意义的失败）；
3. **人工介入位**：死信之后，控制台能否「改输入重投」。

## 相关已定语义

处理链内的失败传播规则已定，见 `design/processing-chain.md` §2：依赖的前置失败时后者是否执行按依赖配置（默认不执行），无依赖失败不株连，门禁判输入就绪兜底。
