# 失败处理

> 状态：第一阶段只做日志留痕（外加一个已定例外：出口投递有界重试，见下）；系统的失败处理属于第二阶段工作。

## 第一阶段（当前）

**日志留痕。** 任何失败都能按 `event_id` / `lifecycle_id` / channel_id / `correlation_id` 回溯现场（规则见 `design/logging.md`）。

**已定例外：出口投递的有界重试。** 出口投递失败（网络类）是失败处理的第一个已知样本类，策略随出口循环落地：指数退避、次数上限（实现期配置）；重试在出口通道内原地进行（同目标本就该串行排队），耗尽进死信 + error 日志告警。投递为 at-least-once——接收方可凭信封 `event_id` 幂等。

## 第二阶段（待实际代码与业务落地后再议）

失败处理策略必须建立在已实现业务的真实失败样本上深入分析，**只增加必要的异常处理**——设计阶段（无论人还是 AI）不写代码就想不全，不预先空想方案。届时要回答的问题先占位：

1. **失败分类**：开发期失败（配置错误、prompt 问题、契约不符）vs 运行期失败（agent 崩溃、厂商 429、超时、进程资源耗尽、出口投递失败）——先分类再谈针对性策略，不一概而论、不盲目扩大；
2. **重试粒度与预算**：任务级重跑的边界与成本（agent 调用分钟级、数万 token；区分可重试与重试无意义的失败）；
3. **人工介入位**：死信之后，控制台能否「改输入重投」。

## 相关已定语义

处理链内的失败传播规则已定，见 `design/processing-chain.md` §2：依赖的前置失败时后者是否执行按 `on_failure` 配置（默认不扇出 = 不执行、不通知），无依赖失败不株连，门禁判输入就绪兜底。
