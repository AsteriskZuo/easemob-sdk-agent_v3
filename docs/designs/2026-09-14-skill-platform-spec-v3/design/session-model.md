# 会话模型

> 机制文档。术语定义见 `design/glossary.md`。

## 1. 两种会话，一张映射表（关键认知）

**我们的会话 ≠ agent-cli 的会话。**

- **我们的会话**：解决业务场景问题——多轮交互的串联、跨任务的上下文恢复、通道并发的粒度依据；
- **agent-cli 会话**：大模型的会话，推理上下文保存在 agent-cli 侧（会话内容在他们那边，不在我们这边）；
- **会话模块维护两者的映射**：我们的 session_id ↔ agent-cli 的会话 id。恢复、清空等操作通过映射落到 agent-cli 侧执行。

由此，「多轮会话 token 成本」不成立为平台风险：上下文由 agent-cli 托管，平台只存映射与元数据。

## 2. 会话标识

**会话标识 = `source__session_id`**（双下划线分隔，不用冒号——避免文件名/路径转义问题）。

**session_id = `{业务id}_{时间戳}_{源生标识}_{随机数}`**——四段以**单下划线**相连。**本页是 session_id 组成的唯一定义处**，其他文档一律引用本页，不重复定义。

- **业务 id**：业务创建时生成、不可修改（业务名可改，子目录等内部引用一律用 id）；
- **时间戳**：会话创建时间（如 `20260915103000`）；
- **源生标识**：从触发对象提取的可区分串，目的是与**同来源同类型**的其他事件区分开（如 GitHub PR 取仓库名 + PR 号）；不得使用无意义字符串，提取规则按来源定义，见 §4；
- **随机数**：兜底防撞。

session_id 整体视为**不透明字符串**：任何模块不解析它、不从中提取信息（要信息查映射，见 §3）。

示例：`wecom__b01J8xk_20260915103000_wmAb3xK9Qf_a7f3`（企微群 id 作源生标识）

## 3. 会话模块职责

1. **绑定映射**：外部对象 ↔ session_id（企微会话、Jira 工单、GitHub PR）；
2. **agent-cli 会话映射**：session_id ↔ agent-cli 会话 id（§1）；
3. **四个基本操作**：
   - **创建会话**：新外部对象首次触发时创建（生成 session_id、建立两类映射）；
   - **恢复会话**：已有会话再次触发时，按映射找回 agent-cli 会话继续；
   - **压缩会话**：上下文过长时调用 agent-cli 的压缩能力；
   - **清空会话**：结束当前会话并解除映射；下次触发即创建新会话（新 session_id，历史仍可按时间追溯）。

## 4. 各来源的会话键规则

会话外部键用于建立映射（§3）；session_id 四段中的**源生标识**（§2）从外部键按来源规则提取——取外部键的可读、可区分部分。

| source | 会话外部键 |
|--------|-----------|
| wecom | 群 id / 用户 id |
| github | 仓库名 + PR 号 |
| jira | 工单 key |
| internal | **和上游会话无关，任务完全独立** |
| cron / manual | 不建会话，走业务级串行兜底（见 `design/scheduler.md`） |

**通道键 = 会话标识**，同通道串行、跨通道并行（见 `design/scheduler.md`）。

> 待调研：同一来源有多类 webhook 事件时（如 GitHub 的建分支 / push / CI 通知），事件种类是否并入源生标识——GitHub 各事件的通知形态需单独调研。 **不用调研，增加source关键字就可以了。**

## 5. 一个业务多个入口

业务与入口机械绑定（不会错配）；一个业务可绑定多个入口，**每个入口独立决定自己的会话键规则**：

| 入口 | 会话键 | 并发效果 |
|------|--------|----------|
| Jira webhook | 工单 key | 同工单串行，不同工单并行 |
| 企微消息 | 群/用户 id | 同会话串行，不同群/人并行 |

业务本体一份（提示词 + skill 组 + agent-cli + 大模型），入口多个，**并发语义由通道自然决定，零配置**。

## 6. memory（占位留白）

会话级长期记忆（memory）是后续阶段的候选能力，**第一阶段不实现**，仅在此留白。

## 7. 常见问题

1. 同一个业务不同来源的场景

场景一：
jira事件通知自动审查工单 和 企业微信多轮对话审查工单，虽然都是审查工单，但是他们是不同的业务，虽然可能会用到相同的skill，但是他们就是不同的业务。所以，这类问题的解决思路就是创建不同的业务解决问题。

场景二：
jira事件通知自动审查工单 和 定时审查工单，如果一起发生会发生严重的写冲突，建议，这种的场景最好二选一，不要一起用。
