# 生命周期与执行

> 机制文档。术语定义见 `design/glossary.md`。

## 1. 定义

生命周期 = 业务组合体的**一次完整执行**：任务触发创建、单次执行、跑完即销毁。

- **平台视角一次性**：一次任务 = 一次完整执行；执行中调用几次大模型、是否流式，都是业务内部细节，平台不关心；
- 无挂起/恢复机制：多轮交互的连续性由通道模块承接（见 `design/channel-model.md`）。

## 2. 多阶段需求的转化（平台不支持多阶段代码）

复杂业务的多阶段组合，用两种路径转化，而不是让平台支持多阶段代码：

| 路径 | 做法 | 适用 |
|------|------|------|
| **包内多阶段** | 一个 skill 内部实现多阶段串行：每阶段明确输出作为下一阶段输入；阶段间设门禁，不合格重做，重做次数有上限 | 阶段间耦合紧、数据不出包的流程 |
| **拆业务串联** | 拆成多个业务，经内部任务队列串联：上一个业务的产出信封 = 下一个业务的入口任务，下游主动关注（见 `design/processing-chain.md`） | 阶段可独立成业务、需独立监控/复用的流程 |

**理由**：多阶段代码会同时给运行时（阶段状态机、挂起/恢复）和控制台（编排 UI）引入复杂度；转化之后，两者都不需要。

## 3. 执行隔离

- **单体 ≠ 同进程执行**：agent 与 skill 一律在独立子进程/沙箱中执行，配操作系统级资源配额（CPU/内存）。主进程只做编排，任何跑飞的执行不会拖垮入口与调度；
- **任务级 workspace 隔离**：每次执行使用独立运行目录（`businesses/{业务id}/runs/{run_id}/`，见 `design/console-design.md` §工作目录）；
- **冷启动**：按需唤起有启动开销——常用 skill 可热池预热。

## 4. Agent 调用超时

- **默认 60 分钟**，在业务创建/配置时可修改（可选设置）；
- **通用配置与业务配置的优先级**：平台设通用配置，业务配置可与通用配置重合，**业务配置优先级更高**——超时只是第一条适用该规则的配置项，后续同类配置都按此规则。

## 5. Agent 适配槽

- 统一调用接口：`invoke(context, prompt, config) → { result, usage }`；
- **适配器一定要薄**：项目初期不做复杂封装，控制成本；只统一调用方式，不封装能力差异；
- **适配器要解决的痛点**：不同 agent-cli 的配置方式差异非常大，其配置大模型的方式差异也非常大，且模型配置存在多层优先级（全局/项目/用户等）——接入新 agent 时需逐项仔细确认，这不是小问题；
- **候选 agent 名单（本节为唯一定义处，骨架等文档一律引用本节）**：**pi、claudecode-cli、codex-cli、kiro-cli**；
- **MVP 范围**：仅支持 **pi** + **qwen3.8max**，其他 agent 与模型暂不考虑；第一期不复杂，但必要接口（invoke 签名）保持稳定，防止后续改动过大；
- 调用经适配槽统一埋点：token 用量、耗时、成本上报控制台。

## 6. 资源事实

- agent CLI 进程**百 MB 级内存起步**——并发闸门据此而定，量级为几十（见 `design/scheduler.md`）；
- 响应形态：一次性或流式；流式只占一个连接，对服务是廉价 IO，不构成并发压力。
