# 调度循环与任务队列

> 机制文档。术语定义见 `design/glossary.md`。

## 1. 心脏的工作方式

调度循环是平台唯一主循环。每跳一次：

1. 从任务队列**有序摄取**下一个任务；
2. 读信封，按 `(source, event_type)` 匹配全部关注者（处理链）；
3. **对每个关注者**，按串行键将 (任务, 业务) 挂入对应通道——各挂各的，链内并行；
4. 通道轮到该 (任务, 业务) 时：过并发闸门 → 创建生命周期 → 执行 → 销毁 → 按结果处置派生新事件回队或终结。

**心脏不认识业务细节**：入口模块做源适配时把会话标识填进信封，心脏只读信封字段——入口懂业务，信封带答案，心脏只读字段。

## 2. 任务队列

- **统一包装**：外部通知、内部通知、定时到点，统一包装为任务；
- **特性**：FIFO、**持久化（SQLite）**、有序消化；
- **第一阶段不预留并行接口**：并行化只是调度器的内部实现变更（一个 take 循环 → 多 worker），任务契约与业务配置一概不动，按最小设计原则无需预留。

## 3. 派发规则：串行键

**串行键 = `source__session_id__business_id`**（三维，双下划线分隔，不用冒号——避免文件名/路径转义问题）。定义见 `design/glossary.md` 通道词条，各来源 session_id 提取规则见 `design/channel-model.md` §4。

- `source`：来源命名空间，入口写入；
- `session_id`：**源生会话标识**，入口按来源规则直接从事件提取（群 id / 工单 key / 仓库+PR号 …），平台不生成；
- `business_id`：**执行业务** id——信封创建时业务未知，匹配后按关注者逐业务补入。

串行规则：**相同会话 + 相同业务 = 同通道串行；其余一切组合 = 跨通道并行**。

| 情形 | 规则 |
|------|------|
| 已识别来源（wecom / jira / github …） | 按该来源的会话标识规则处理（见 `design/channel-model.md` §4） |
| **未识别来源** | **忽略该任务 + 日志记录**（不创建通道、不报错扩散） |
| 无会话的来源（cron / manual） | session_id 兜底为业务标识 → **业务级串行** |

## 4. 通道

- **虚拟通道**：以串行键为索引的执行链；同通道串行，跨通道并行，用完即焚；
- **持久化**：**通道创建即记录到数据库**（防意外丢失），后续只做状态变更（进行中/完结），不在完成时才落库；
- **通道并发**：准确说是「通道并发」——串行键唯一，不同通道并行推进；**最大通道并发数可在控制台修改**；
- 跨通道并行是自然结果，不是新功能——10 人群聊 = 10 条通道同时推进，各自（同业务）的连续消息仍严格有序。

## 5. 并发闸门

全局信号量。瓶颈不在服务框架，在**本机沙箱**：每个并发执行 = 一个 agent 沙箱进程（百 MB 级内存起步）+ 独立 workspace。闸门值按部署机器资源定，量级为几十，**控制台可修改**。

## 6. 压力分布（已核实）

| 层 | 压力 | 结论 |
|----|------|------|
| 服务框架（调度/队列） | 可忽略 | 不构成瓶颈 |
| 本机沙箱（agent 进程） | 真实约束 | 并发闸门据此而定 |
| 流式响应 | 仅占一个连接 | 廉价 IO，不是问题 |
| 厂商配额（RPM/TPM） | 按主账号计，内部规模充足 | 触顶再议：商务提额 → 多账号 → 多厂商 |

**要点**：厂商限流按账号（组织）合并统计，不按单个 Key、不按 IP——**多 API Key 不扩配额**，控制台暂不做多 Key 管理（最小设计）。

## 7. 演进

虚拟通道 → 实体子任务队列：将来拆分执行层为 worker 集群时物化，语义不变。
