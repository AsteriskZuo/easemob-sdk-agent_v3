# 调度循环与任务队列

> 机制文档。术语定义见 `design/glossary.md`。

## 1. 心脏：一副机械，两个循环

调度循环机械在平台有两个实例——**入口事件循环**与**出口事件循环**，同一套工作方式、不同的注册表与执行器（对照表见 `design/glossary.md` 调度循环词条）。每跳一次：

1. 从自己的任务队列**有序摄取**下一个任务；
2. 读信封匹配关注者——入口循环按 `(source, event_type)` **订阅匹配**业务，出口循环按 `producer_business_id` **归属匹配**出口绑定；
3. **对每个关注者**，按 channel_id 将 (任务, 关注者) 挂入对应通道——各挂各的，链内并行；
4. 通道轮到该任务时：过本循环的并发闸门 → 执行（入口循环 = 业务生命周期；出口循环 = 出口工具投递）→ 完结处置。

**结果无脑扇出**：入口循环里业务完成（或失败且配置 `on_failure`）即派生 internal 事件，**同时投入两个队列**——入口队列无关注者则丢弃，出口队列无出口绑定则丢弃，各自过滤、互不影响。

**心脏不认识业务细节**：入口模块做源适配时把会话标识填进信封，心脏只读信封字段——入口懂业务，信封带答案，心脏只读字段。

## 2. 任务队列（两条，同一契约）

- **入口队列**：外部通知、内部派生、定时到点的统一缓冲带；
- **出口队列**：仅业务产出的派生事件；
- **共同特性**：FIFO、**持久化（SQLite）**、有序消化；
- **第一阶段不预留并行接口**：并行化只是调度器的内部实现变更（一个 take 循环 → 多 worker），任务契约与业务配置一概不动，按最小设计原则无需预留。

## 3. 派发规则：channel_id

**业务通道 channel_id = `source__session_id__business_id`**（三维，双下划线分隔，不用冒号——避免文件名/路径转义问题）。定义见 `design/glossary.md` 通道词条，各来源 session_id 提取规则见 `design/channel-model.md` §4。

- `source`：来源命名空间，入口写入；
- `session_id`：**源生会话标识**，入口按来源规则直接从事件提取（群 id / 工单 key / 仓库+PR号 …），平台不生成；
- `business_id`：**执行业务** id——信封创建时业务未知，匹配后按关注者逐业务补入。

**出口通道 channel_id = `exit__destination_id`**：destination_id = 投递目标标识，由出口工具从绑定配置提取（webhook URL、群 id、邮箱地址等）。**同目标串行，不分业务**——同一目标的全部通知按入队序投递，既保序又天然消化目的地平台的频率限制（详见 `design/channel-model.md` §2）。

串行规则统一：**同通道串行，其余一切组合 = 跨通道并行**。

| 情形 | 规则 |
|------|------|
| 已识别来源（wecom / jira / github …） | 按该来源的会话标识规则处理（见 `design/channel-model.md` §4） |
| **未识别来源** | **忽略该任务 + 日志记录**（不创建通道、不报错扩散） |
| 无会话的来源（cron / manual） | session_id 兜底为业务标识 → **业务级串行** |

## 4. 通道

- **虚拟通道**：以 channel_id 为索引的执行链；同通道串行，跨通道并行，用完即焚；
- **持久化**：**通道创建即记录到数据库**（防意外丢失），后续只做状态变更（进行中/完结），不在完成时才落库；
- **通道并发**：准确说是「通道并发」——channel_id 唯一，不同通道并行推进；**两个循环的最大通道并发数各自在控制台修改**；
- 跨通道并行是自然结果，不是新功能——10 人群聊 = 10 条业务通道同时推进，各自（同业务）的连续消息仍严格有序。

## 5. 并发闸门（两道）

每个循环一道全局信号量。**业务闸门（`task_concurrency`）**保本机执行资源：每个并发执行 = 一个业务流程进程（可再拉起 agent 子进程，百 MB 级内存起步）+ 独立 workspace，闸门值按部署机器资源定，量级为几十；**出口闸门（`result_concurrency`）**管结果通知投递：毫秒级网络调用、不占执行进程，量级可大得多。两道闸门值各自在控制台修改。

出口独立成循环 + 独立闸门的理由：出口投递与业务执行的资源画像完全不同（毫秒级网络 IO vs 分钟级子进程）——分开后，大并发下耗时任务再多，已完成业务的通知也不会被堵在执行队列后面；且两类执行的并发上限各自可调。

## 6. 压力分布（已核实）

| 层 | 压力 | 结论 |
|----|------|------|
| 服务框架（调度/队列） | 可忽略 | 不构成瓶颈 |
| 本机执行进程（流程进程 + agent 子进程） | 真实约束 | 业务闸门据此而定 |
| 出口投递 | 毫秒级网络 IO | 出口闸门取值可宽；同目标串行天然限流 |
| 流式响应 | 仅占一个连接 | 廉价 IO，不是问题 |
| 厂商配额（RPM/TPM） | 按主账号计，内部规模充足 | 触顶再议：商务提额 → 多账号 → 多厂商 |

**要点**：厂商限流按账号（组织）合并统计，不按单个 Key、不按 IP——**多 API Key 不扩配额**，控制台暂不做多 Key 管理（最小设计）。

## 7. 演进

虚拟通道 → 实体子任务队列：将来拆分执行层为 worker 集群时物化，语义不变——两个循环天然就是两个 worker 池的雏形（业务执行池 + 投递池），信封契约原样平移。
