# 事件契约与队列

> 机制文档。术语定义见 `design/glossary.md`。

## 1. 事件信封（契约 v1）

```json
{
  "contract_version": "v1",
  "source": "github",
  "event_id": "evt_01J...",
  "event_type": "pr.create",
  "timestamp": "2026-09-14T15:30:00+08:00",
  "session_id": "emclient-ios.1062",
  "correlation_id": "evt_01J...",
  "hop_count": 0,
  "payload": {}
}
```

### 字段说明（为什么用 + 怎么用，一句话）

| 字段 | 说明 |
|------|------|
| `event_id` | **为什么**：一切追溯与幂等都需要唯一锚点。**怎么用**：入口包装任务时生成，全局唯一，日志/去重/引用都用它；**兼任第一层去重（入口幂等）键**——同一源生事件重推（webhook 超时重发等）时入口识别并丢弃，不产生新事件 |
| `contract_version` | **为什么**：信封结构未来破坏性变更时，新旧版本需要共存与路由依据。**怎么用**：生产者写入，消费者按值选择解析规则；使用规则见 §2 |
| `source` | **为什么**：channel_id 需要来源命名空间，不同来源的会话/日志/处理规则不同。**怎么用**：入口模块写入（wecom / jira / github / webhook / cron / internal / manual）；新来源 = 枚举新增，属向后兼容 |
| `event_type` | **为什么**：下游关注与处理链匹配的键。**怎么用**：**类别标签而非实例标识**——同一业务产出的所有通知共用同一个值（与 `event_id` 的根本区别）；业务创建时声明、不可修改、全平台唯一；internal 事件 = `业务id.产出类型`；依赖关系 = 关注上游的产出事件类型。唯一定义见 `design/glossary.md` 事件类型词条 |
| `timestamp` | **为什么**：排序、延迟观测与审计需要基准时间。**怎么用**：**入口接收并包装任务的时间**（ISO 8601，带时区） |
| `session_id` | **为什么**：channel_id 的第二维、通道上下文恢复的依据。**怎么用**：**必填**——**源生会话标识**，入口按来源规则直接从事件提取（群 id / 工单 key / 仓库+PR号 …），平台不生成；各来源规则的唯一定义见 `design/channel-model.md` §4。internal 派生时继承上游源生标识（channel-model §4.1）；cron/manual 用业务标识兜底（业务级串行） |
| `producer_business_id` | **为什么**：出口事件循环按产出方归属匹配出口绑定，需要可靠的产出方标识——从 `event_type` 字符串解析太脆。**怎么用**：**可选，仅 internal 派生事件填写**（= 产出方业务 id）；入口事件循环不使用，出口事件循环的归属匹配键 |
| `correlation_id` | **为什么**：一次业务联动会派生一串任务（A 的结果触发 B、B 的触发 C），需要一个键把整串连成一线。**怎么用**：等于**首个任务的 event_id**，派生任务原样继承；日志串联、最终结果路由回原始上下文（如回复到发起询问的企微会话）都靠它 |
| `hop_count` | **为什么**：A→B→A 式循环订阅会造成无限派生。**怎么用**：转发计数器，每次「结果触发新任务」+1，超阈值判为循环，进死信并告警（阈值属实现期配置）；只管入口事件循环——出口循环不派生事件，天然无循环 |
| `payload` | **为什么**：事件的具体数据载体。**怎么用**：来源自定义结构；大产物不进 body，走对象存储+引用（§4）。派生事件的 payload = 业务产出，出口循环投递的就是它 |

分隔符约定：复合键一律用**双下划线 `__`**，不用冒号——避免文件名/路径转义问题。

**去重职责划分（已定）**：第一层入口幂等由平台承担——同一源生事件重推（webhook 超时重发等）时，入口按 `event_id` 识别并丢弃。**业务语义去重归业务流程程序自行处理**——如同一工单的重复通知只需审一次：平台不了解业务细节，不定规范、不提供字段；业务在流程内自行判重（如调子程序按工单 key 过滤，已审过则提前返回），过滤后的才是真正需要处理的事件。

## 2. 契约版本管理

- **contract_version 的用途**：信封结构发生**破坏性变更**（改名/删字段/改语义）时升版本（v1 → v2），新旧信封靠它区分与路由；
- **兼容规则**：同一大版本内**只允许新增可选字段**（消费者忽略不识别的字段）；破坏性变更才升版本——接口稳定原则在契约层的落地；
- **并存期**：升级期新旧版本并存，生产者/消费者按 `contract_version` 各取所需；旧版本下线须先在 changelog 公告；
- **changelog**：契约与服务一样有版本号；每个契约文档末尾维护变更记录（版本 / 日期 / 变更内容 / 兼容说明），集中管理、随版本更新；
- 当前版本：**v1**，无 v2 计划。字段成本为零，但没有它，未来 v2 信封混入时消费者只能猜。

## 3. 队列要点

- **两条队列**：入口队列与出口队列，同一契约、两个实例（见 `design/scheduler.md` §2）；业务产出的派生事件无脑扇出、同时进两条队列；
- **事件进来即持久化**：事件不能丢——入口接收即落库，落库才算收到，崩溃后可找回，杜绝「内存里丢了就永远丢了」。事件的加入与获取都是低频操作，持久化不是性能瓶颈；
- **持久化用 SQLite**（见骨架 §4 技术选型）：单进程写入与模块化单体天然匹配，零运维，备份即文件拷贝；禁止纯内存队列；
- 入口模块收到事件只做两件事：校验、落队，立即返回——入口永远轻快，背压天然成立；
- 失败处理见 `design/failure-handling.md`（第一阶段：日志留痕；出口投递有界重试为已定例外）。

## 4. 大产物走引用

代码 diff、日志原文、报告文件等大产物不进信封 body；写入对象存储，信封内只带引用。

**第一阶段的「对象存储」= 平台工作目录下的文件区**（如 `{workspace}/artifacts/`，按业务/运行隔离），信封内带文件路径引用——**不引入外部 OSS/云存储**。后续真有外部存储需求时按演进路径单独立项，信封契约不变。
