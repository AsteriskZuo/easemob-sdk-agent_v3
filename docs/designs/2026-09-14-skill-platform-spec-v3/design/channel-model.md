# 通道模型

> 机制文档。术语定义见 `design/glossary.md`（通道、三种「会话」辨析为唯一定义处，本文不重复概念，只展开机制与规则）。

## 1. 三种会话与一张映射表

三种「会话」的辨析见 `design/glossary.md`：源会话（企微/工单/PR）是交互场所，agent-cli 会话托管大模型上下文，**通道**是平台侧的执行线与上下文串联单位。

**通道模块维护一张映射表**：串行键 ↔ agent-cli 会话 id。恢复、清空等操作通过映射落到 agent-cli 侧执行。同一条通道（相同会话 + 相同业务）上下文连续；跨业务、跨会话的上下文天然隔离（串行键不同）。

由此「多轮会话 token 成本」不成立为平台风险：上下文由 agent-cli 托管，平台只存映射与元数据。

## 2. 通道标识：维度组合模型

**串行键 = `source__session_id__business_id`**（三维，双下划线分隔）。**执行实例 = 串行键 + `event_id`**（第四维）——维度组合，越多越具体：三维定「排哪条队」，第四维定「这是哪一次」。

**session_id = 源生会话标识**：入口收到原始事件时，按来源规则直接从事件提取（§4），**平台不生成、不映射**——群 id、工单 key 本身就是最好的标识。由此入口侧不需要任何会话存储：提取即所得。

规则：

- 源生标识必须**可读、可区分**（与同来源同类型的其他事件区分开），不得使用无意义字符串；
- session_id 整体视为**不透明字符串**：任何模块不解析它、不从中提取信息（要信息查 §4 规则与映射表）；
- 多平台按独立 source 区分（github / gitee / feishu 各自一个入口）；平台内事件种类的区分归 event_type。

示例：`wecom__wmAb3xK9Qf__b01J8xk`（企微群 `wmAb3xK9Qf`，业务 `b01J8xk`）；执行实例再加 `__evt_01J...`。

## 3. 通道模块职责

1. **映射维护**：串行键 ↔ agent-cli 会话 id（§1）；
2. **四个基本操作**：
   - **创建**：通道首次触发执行时，建立映射（agent 会话 id 由首次执行产生）；
   - **恢复**：通道再次触发时，按映射找回 agent-cli 会话继续——多轮交互的载体；
   - **压缩**：上下文过长时调用 agent-cli 的压缩能力——由用户消息（如企微斜杠命令）原样透传给 agent-cli 执行，平台不翻译、不主动调用；
   - **清空**：解除映射；下次触发即重绑新 agent 会话（通道标识不变，agent 会话换代，历史仍可按时间追溯）。

## 4. 各来源的会话标识规则

| source | session_id（源生标识） | 串行效果 |
|--------|------------------------|----------|
| wecom | 群 id / 用户 id | 同群（同业务）串行，跨群并行 |
| jira | 工单 key | 同工单串行，跨工单并行（对同一工单的 comments 写不并发） |
| github | **按事件种类细分**：PR 类 = 仓库+PR号；issues 类 = 仓库+issue号；push/分支/tag = 仓库+分支 | 同 PR 串行（增量 review 上下文连续），跨 PR 并行 |
| internal | **继承上游源生标识**（标识继承、上下文独立，见 §4.1） | 同一外部对象的派生链落在同一串行维度 |
| cron / manual | 业务标识兜底 | 业务级串行（上次没跑完自动排队） |

**通道键 = 串行键**，同通道串行、跨通道并行（见 `design/scheduler.md`）。

### 4.1 internal 事件：继承标识、独立上下文（已定语义 + 理由）

派生事件（`source = internal`）的 session_id **继承上游的源生标识**（如审查业务处理 TKT-101，其派生事件的 session_id 仍为 `TKT-101`），但**上下文完全独立**——串行键的 `business_id` 段天然隔离，每个业务各有自己的 agent 会话。

- **为什么继承标识**：出口型业务（如企微通知）需要对同一外部对象的多次执行串行——同一工单触发的「审查完成」「crash 完成」两条通知，落到同一串行键 `(internal, TKT-101, 通知业务)`，按序发群、不乱序（验证见 `design/validation.md` S4）。纯随机新建会让每条通知各走各的通道，顺序失守；
- **为什么上下文独立**（已确认，不再重复讨论）：① 每个任务独立完成工作——虽与上游有依赖关系，但它**仅仅需要上游的结果**（结果形式很多：派生信封、外部业务系统记录等），不需要共享会话上下文；② 链式关系不丢：`correlation_id` 派生继承，把整条执行链上的所有任务连成一线，随时可追溯；③ 业务可以交叉：同一上游的结果可被多个不同业务消费（如审查结果既发企微通知、又供日志分析），各自独立执行、互不阻塞——如同前端和后端临时拉起一个项目组，各自干各自的，共同完成一件事。

一句话：**internal 独立的是上下文，不是标识符。**

## 5. 一个业务多个入口

业务与入口机械绑定（不会错配）；一个业务可绑定多个入口，**每个入口独立决定自己的会话标识规则**：

| 入口 | session_id | 并发效果 |
|------|-----------|----------|
| Jira webhook | 工单 key | 同工单串行，不同工单并行 |
| 企微消息 | 群/用户 id | 同群串行，不同群/人并行 |

业务本体一份（提示词 + skill 组 + agent-cli + 大模型），入口多个，**并发语义由通道自然决定，零配置**。

## 6. memory（占位留白）

通道级长期记忆（memory）是后续阶段的候选能力，**第一阶段不实现**，仅在此留白。

## 7. 常见问题

1. 同一个业务不同来源的场景

场景一：
jira事件通知自动审查工单 和 企业微信多轮对话审查工单，虽然都是审查工单，但是他们是不同的业务，虽然可能会用到相同的skill，但是他们就是不同的业务。所以，这类问题的解决思路就是创建不同的业务解决问题。

场景二：
jira事件通知自动审查工单 和 定时审查工单，如果一起发生会发生严重的写冲突，建议，这种的场景最好二选一，不要一起用。

2. 同一企微群里多人 @同一个业务

同群 + 同业务 = 同一条通道 = 共享同一个 agent 会话上下文（群机器人本色）。多人的话题会进入同一上下文，编写提示词时需注意多人场景。
