# 通道模型

> 机制文档。术语定义见 `design/glossary.md`（通道、三种「会话」辨析为唯一定义处，本文不重复概念，只展开机制与规则）。

## 1. 三种会话与一张映射表

三种「会话」的辨析见 `design/glossary.md`：源会话（企微/工单/PR）是交互场所，agent-cli 会话托管大模型上下文，**通道**是平台侧的执行线与上下文串联单位。

**通道模块维护一张映射表**：业务通道 channel_id ↔ agent-cli 会话 id。恢复、清空等操作通过映射落到 agent-cli 侧执行。同一条通道（相同会话 + 相同业务）上下文连续；跨业务、跨会话的上下文天然隔离（channel_id 不同）。**出口通道不过 LLM、无 agent 会话，不在映射表内**（出口通道规则见 §2）。

由此「多轮会话 token 成本」不成立为平台风险：上下文由 agent-cli 托管，平台只存映射与元数据。

## 2. 通道标识：维度组合模型

**业务通道 channel_id = `source__session_id__business_id`**（三维，双下划线分隔）。**执行实例 = channel_id + `event_id`**（第四维）——维度组合，越多越具体：三维定「排哪条队」，第四维定「这是哪一次」。

**出口通道 channel_id = `exit__destination_id`**（出口事件循环专用）：destination_id = 投递目标标识，由出口工具从绑定配置提取。**同目标串行、跨目标并行，不分业务**——同一目标的通知可能来自不同业务（S4 的三条通知来自 B.2/B.3/B.4，见 `design/validation.md`），键若含业务维度会把它们拆进并行通道、网络耗时不均即乱序；按目标取键则入队序 = 投递序，同时天然消化目的地平台的频率限制。出口通道只做串行投递，无 agent 会话映射。

各出口工具的 destination_id 提取规则（本表为唯一定义处；工具契约的 `destinationOf` 按此实现）：

| 出口工具 | destination_id | 串行效果 |
|---------|----------------|---------|
| github 操作 | 仓库地址规范化（去协议头与 `.git`，如 `github.com_AsteriskZuo_im_flutter_sdk`） | 同仓库串行 |
| jira 操作 | 站点 + 工单 key（如 `j1.private.easemob.com_HIM-23363`） | 同工单串行（与 §4 jira 业务通道规则一致） |
| confluence 操作 | 站点 + 页面标识 | 同页面串行 |
| 邮件 | 收件人地址 | 同收件人串行 |
| 企微智能机器人 | 机器人 id + 会话 id + 用户 id | 同人对同机器人串行 |
| 企微群 webhook | webhook 地址的 key 段（天然唯一标识一个群） | 同群串行 |
| 自定义 webhook | 目标地址规范化（host + path） | 同地址串行 |

规则：destination_id 必须**可读、可区分、文件路径安全**——channel_id 会用作通道日志文件名（见 `design/logging.md`），不得含 `/`、`:` 等路径分隔字符；规范化（去协议头、段间连接）由工具的 `destinationOf` 完成，它是唯一提取点。

**session_id = 源生会话标识**：入口收到原始事件时，按来源规则直接从事件提取（§4），**平台不生成、不映射**——群 id、工单 key 本身就是最好的标识。由此入口侧不需要任何会话存储：提取即所得。

规则：

- 源生标识必须**可读、可区分**（与同来源同类型的其他事件区分开），不得使用无意义字符串；
- session_id 整体视为**不透明字符串**：任何模块不解析它、不从中提取信息（要信息查 §4 规则与映射表）；
- 多平台按独立 source 区分（github / gitee / feishu 各自一个入口）；平台内事件种类的区分归 event_type。

示例：`wecom__wmAb3xK9Qf__b01J8xk`（企微群 `wmAb3xK9Qf`，业务 `b01J8xk`）；执行实例再加 `__evt_01J...`；出口通道示例：`exit__wmAb3xK9Qf`（投向企微群 `wmAb3xK9Qf` 的全部通知串行）。

## 3. 通道模块职责

1. **映射维护**：业务通道 channel_id ↔ agent-cli 会话 id（§1）；
2. **四个基本操作**（仅业务通道——出口通道无 agent 会话，不涉及）：
   - **创建**：通道首次触发执行时，建立映射（agent 会话 id 由首次执行产生）；
   - **恢复**：通道再次触发时，按映射找回 agent-cli 会话继续——多轮交互的载体；
   - **压缩**：上下文过长时调用 agent-cli 的压缩能力——由用户消息（如企微斜杠命令）原样透传给 agent-cli 执行，平台不翻译、不主动调用；
   - **清空**：解除映射；下次触发即重绑新 agent 会话（通道标识不变，agent 会话换代，历史仍可按时间追溯）。

## 4. 各来源的会话标识规则

| source | session_id（源生标识） | 串行效果 |
|--------|------------------------|----------|
| wecom | (群 id + 用户 id) / 用户 id | 同群（同业务）串行，跨群并行 |
| jira | 工单 key | 同工单串行，跨工单并行（对同一工单的 comments 写不并发） |
| github | **按事件种类细分**：PR 类 = 仓库+PR号；issues 类 = 仓库+issue号；push/分支/tag = 仓库+分支 | 同 PR 串行（增量 review 上下文连续），跨 PR 并行 |
| webhook | 入口配置指定的 payload 字段；未配置则以业务标识兜底 | 按配置串行 / 业务级串行 |
| internal | **继承上游源生标识**（标识继承、上下文独立，见 §4.1） | 同一外部对象的派生链落在同一串行维度 |
| cron / manual | 业务标识兜底 | 业务级串行（上次没跑完自动排队） |

**通道键 = channel_id**，同通道串行、跨通道并行（见 `design/scheduler.md`）。

### 4.1 internal 事件：继承标识、独立上下文（已定语义 + 理由）

派生事件（`source = internal`）的 session_id **继承上游的源生标识**（如审查业务处理 TKT-101，其派生事件的 session_id 仍为 `TKT-101`），但**上下文完全独立**——channel_id 的 `business_id` 段天然隔离，每个业务各有自己的 agent 会话。

- **为什么继承标识**：同一外部对象的派生链须落在同一串行维度——同一工单连续更新触发多次审查，派生出的 crash 分析按序消化（`(internal, TKT-101, B.3)` 同通道串行）；纯随机新建会让派生任务各走各的通道，同一对象的消化次序失守。通知的发群顺序不由业务通道保证，而由出口通道兜底（`exit__destination_id`，见 §2）；
- **为什么上下文独立**（已确认，不再重复讨论）：① 每个任务独立完成工作——虽与上游有依赖关系，但它**仅仅需要上游的结果**（结果形式很多：派生信封、外部业务系统记录等），不需要共享会话上下文；② 链式关系不丢：`correlation_id` 派生继承，把整条执行链上的所有任务连成一线，随时可追溯；③ 业务可以交叉：同一上游的结果可被多个不同业务消费（如审查结果既供 crash 分析、又供日志分析），各自独立执行、互不阻塞——如同前端和后端临时拉起一个项目组，各自干各自的，共同完成一件事。

一句话：**internal 独立的是上下文，不是标识符。**

## 5. 一个业务多个入口

业务与入口机械绑定（不会错配）；一个业务可绑定多个入口，**每个入口独立决定自己的会话标识规则**：

| 入口 | session_id | 并发效果 |
|------|-----------|----------|
| Jira webhook | 工单 key | 同工单串行，不同工单并行 |
| 企微消息 | 群/用户 id | 同群串行，不同群/人并行 |

业务本体一份（提示词 + skill 组 + agent-cli + 大模型），入口多个，**并发语义由通道自然决定，零配置**。

## 6. memory（占位留白）

通道级长期记忆（memory）是后续阶段的候选能力，**第一阶段不实现**，仅在此留白。

## 7. 常见问题

1. 同一个业务不同来源的场景

场景一：
jira事件通知自动审查工单 和 企业微信多轮对话审查工单，虽然都是审查工单，但是他们是不同的业务，虽然可能会用到相同的skill，但是他们就是不同的业务。所以，这类问题的解决思路就是创建不同的业务解决问题。

场景二：
jira事件通知自动审查工单 和 定时审查工单，如果一起发生会发生严重的写冲突，建议，这种的场景最好二选一，不要一起用。

2. 同一企微群里多人 @同一个业务

同群 + 同业务 = 同一条通道 = 共享同一个 agent 会话上下文（群机器人本色）。多人的话题会进入同一上下文，编写提示词时需注意多人场景。
