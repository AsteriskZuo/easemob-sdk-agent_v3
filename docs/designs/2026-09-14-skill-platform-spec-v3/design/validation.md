# 场景验证

> 定位：用具体业务组合对设计做压力测试——**设计必须经得起编排验证，不靠想象背书**。新机制定稿前应先过本页的相关场景；发现新反例时先补场景再改设计。
> 被验证对象：channel_id 模型（业务通道 `source__session_id__business_id`、出口通道 `exit__destination_id`）、链内并行、依赖=事件订阅、门禁只验收不等待、internal 继承源生标识、结果无脑扇出。

---

## 1. 测试数据

**入口 R**：R.1 wecom 事件通知｜R.2 jira 事件通知｜R.3 github 事件通知｜R.4 定时器事件通知

**业务 B**：

| 编号 | 业务 | 说明 |
|------|------|------|
| B.1 | 多轮审查工单 | wecom 入口，多轮交互；出口绑定 C.1（回复投递） |
| B.2 | 单轮审查工单 | jira 事件入口；产出 `b2.review.completed`，完成即扇出；出口绑定 C.2 |
| B.3 | 单轮 crash 分析 | 依赖审查工单（关注 B.2 产出）；产出 `b3.crash.completed`，完成即扇出；出口绑定 C.2 |
| B.4 | 单轮日志分析 | 依赖审查工单 + crash 分析（关注 B.3 产出，链式蕴含）；出口绑定 C.2 |
| B.5 | 单轮问题排查 | 监控系统通知触发 |
| B.6 | 多轮问题排查 | wecom 入口，多轮交互 |
| B.7 | 代码 review | github PR 事件入口 |
| B.8 | issues 问题分析 | github issues 事件入口 |

**出口工具 / 执行内 skill C**：C.1 企微智能机器人出口工具（交互回复投递）｜C.2 企微群 webhook 出口工具（通知投递）｜C.3 jira 编辑工具（public skill，业务执行内 `→s` 调用：添加 comments）｜C.4 github 提交 pr 工具（public skill，同）

**记法**：`→p` = 派生/关注（事件流）；`→s` = 执行内 skill 调用；`→ C.x` = 经出口工具投递（出口工具不是业务，不参与事件订阅）；channel_id 简写 `(来源, 会话id, 业务id)` / `exit__目标`。

## 2. 场景验证矩阵

### 组 1：多轮交互

| # | 编排 | channel_id 展开 | 结果 | 判定 |
|---|------|-----------|------|------|
| S1 | `R.1 → B.1 → C.1`（群A，循环问答） | `(wecom,群A,B.1)` | 追问与首轮同键 → 串行；同一 agent 会话恢复，"严重吗"的指代成立；回复经 B.1 的 C.1 出口绑定投递 | ✅ |
| S2 | 两人在群A/群B 各自跑 S1 | `(wecom,群A,B.1)` ≠ `(wecom,群B,B.1)` | 并行 | ✅ |
| S3 | 同人同群连发"审 TKT-101""审 TKT-102" | 同键 | 串行 + 上下文共享，"两个哪个严重"可追问 | ✅ |

### 组 2：jira 自动化全链（核心链）

**S4：`R.2 → B.2 →p B.3 →s C.3 →p B.4 →s C.3`（B.2/B.3/B.4 均配 C.2 出口，投向群 W）**

| 环节 | channel_id | 时序 |
|------|-----------|------|
| TKT-101 更新 → B.2 审查，执行内用 C.3 写 comments | `(jira,TKT-101,B.2)` | 起点 |
| B.2 完成**扇出**：派生 `b2.review.completed`（继承 TKT-101）投入口队列 → B.3；投出口队列 → 按 B.2 的出口绑定投递「审查完成」 | `(internal,TKT-101,B.3)`；`exit__W` | 下游分析与通知**并行**，通知不被分析的长耗时阻塞 ✅ |
| B.3 完成扇出：派生 `b3.crash.completed` → B.4；投递「crash完成」 | `(internal,TKT-101,B.4)`；`exit__W` | B.4 关注 B.3 产出，天然在 crash 之后 ✅ |
| 三条通知（审查/crash/日志分析完成）发群 W | 同通道 `exit__W` | **串行不乱序** ✅ |

顺序是双保险：**入队序 = 因果序**（B.3 由 B.2 的产出触发，其出口事件必然后入队，FIFO 保持）；**投递序 = 入队序**（三条通知来自三个不同业务——出口 channel_id 若含业务维度就会被拆进并行通道、网络耗时不均即乱序，故按目标取键，同目标一个 drain 串行投递）。B.4 的双重依赖（审查 + crash）：关注 `b3.crash.completed` 一个订阅即蕴含两者（crash 存在 ⇒ 审查已完成）✅。TKT-102 同时触发 → 全链按工单维度并行 ✅。B.2 失败不扇出（`on_failure` 默认关）→ 下游静默、无通知 = 默认 skip ✅。

**反面对照 S4' ❌**：B.4 错配为「关注 `b2.review.completed` + 门禁检查 crash 已完成」→ 与 B.3 **并行触发** → 门禁不过 → failed 完结 → crash 随后完成也不会再唤醒 → **日志分析永久丢失**。教训：**需要等待的依赖必须表达为事件订阅，门禁只验收、不等待**。

## 3. 验证结论：设计成立的关键规则（缺一不可）

1. **业务通道 channel_id = 来源+会话id+业务id**（三维）；第四维 `event_id` 只做实例追溯，不参与串行判定——**相同会话 + 相同业务才串行，其余一切组合并行**；
2. **依赖只走事件订阅**（关注上游的 `业务id.产出类型`），多重依赖关注最后一段产出（链式蕴含）；**门禁只验收、不等待**（S4' 反例）；
3. **internal 派生继承源生标识**（同一外部对象的派生链同维度串行），**上下文靠业务id 段隔离**（任务完全独立）——internal 独立的是上下文，不是标识符；
4. **通知有序双保险**：入队序 = 因果序（事件订阅结构天然保证）；投递序 = 入队序（出口 channel_id = `exit__目标`，同目标串行，见 S4）。

## 4. 特性确认（非缺陷，业务使用时须知）

- 同群多人 @同一业务：共享 agent 上下文（群机器人本色），提示词编写需注意多人场景；
- 同服务告警串行消化是防抖特性而非瓶颈；
- cron 与事件双触发写同一外部对象：维持「二选一」纪律（`design/channel-model.md` §7 场景二）。
