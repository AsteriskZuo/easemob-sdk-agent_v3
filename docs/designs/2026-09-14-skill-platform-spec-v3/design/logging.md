# 日志设计

> 机制文档。术语定义见 `design/glossary.md`。日志是平台的一等工具：**排查问题、追踪记录**。失败处理第一阶段就依赖它。

## 1. 四类日志

| 日志 | 内容 | 位置 |
|------|------|------|
| **系统级 system** | **日志总纲**：启动自检结果、初始化信息、通用信息、关键事件（任务入队/完结/死信、生命周期状态变更、配置变更、告警）——只记关键事实 + 关联键，细节到子日志查找 | `logs/system.log` |
| **入口事件循环 entry-loop** | 任务执行过程的机械流水：取出 → 匹配 → 挂通道 → 闸门 → spawn → 完结/扇出。**平台不认识业务细节，业务内容不在这里记录** | `logs/entry-loop.log` |
| **出口事件循环 exit-loop** | 投递流水：归属匹配 → 出口绑定 → 目标（destination_id）→ 投递结果/重试/死信——回答「发送到了哪里」 | `logs/exit-loop.log` |
| **业务 business** | 业务流程程序自己的记录（SDK 日志 API），**以业务为单位、按 run 分文件** | `businesses/{business_id}/logs/{run_id}.log` |

业务日志的采集通道：**stdout 是结果契约通道，不承载日志**（`design/business-workflow.md` §2）。SDK 日志 API 把结构化日志行写入 **stderr**，流程执行器捕获业务进程 stderr 追加到该 run 的业务日志；`sdk.run()` 子程序的 stderr 同样汇入（带子程序标记）。**采集要容忍非结构化内容**：结构化行解析，异常堆栈、库杂讯等非结构化行原样透传追加——日志管道自身永不因内容而失败。业务日志按 run 分文件，清理时机与 `runs/{run_id}/` 工作区一致（同属实现期清理策略），不单独设规则。

## 2. 日志工具的标准能力

| 能力 | 约定 |
|------|------|
| 开关 | 支持全局开启/关闭日志 |
| 等级 | `error / warn / info / debug`，运行时可配置输出级别 |
| 模块标记 | 每条日志必带模块标识（system / entry-loop / exit-loop / queue / console / lifecycle …） |
| 时间戳 | 每条日志必带（ISO 8601，带时区） |
| 封装形态 | 简单封装、**兼容 `console.log` 调用习惯**（Node + TypeScript 技术栈），替换成本为零 |
| 脱敏 | **敏感信息（密钥、token、账号密码）输出前脱敏**——内建于日志工具，各模块不用各自处理；业务日志同样经此管道 |
| 文件分割 | **平台不实现**——交给系统工具（如 Ubuntu 的 logrotate） |

## 3. 输出规则（各模块统一遵守）

| 级别 | 何时输出（必须/可选） |
|------|----------------------|
| `error` | **必须**：发生严重问题、无法继续执行（启动自检失败、任务失败、业务进程崩溃、投递重试耗尽、死信落库） |
| `warn` | **必须**：发生问题但不影响后续处理（重试发生、agent 调用接近配额、配置缺失走默认值） |
| `info` | **必须**：关键节点（任务入队/出队/完结、生命周期创建/销毁、通道创建、出口投递成功、配置变更） |
| `debug` | **可选**：排查用细节（信封内容、中间状态），生产默认关闭 |

纪律：error/warn/info 三级是契约性的——该打的必须打，排查问题不靠补日志。

## 4. 关联键

四类日志之间用键互跳：`event_id`（单个任务）、`lifecycle_id`（单次执行）、channel_id（跨任务的通道线——业务通道 `source__session_id__business_id`，出口通道 `exit__destination_id`）、`correlation_id`（一次联动的整串任务）。系统级日志的每条关键事件必带可用关联键——它是入口，子日志是现场。

## 5. 启动自检与崩溃纪律

平台是稳定优先的基础组件（`design/business-workflow.md` §6），日志侧配套三条纪律：

1. **启动自检，fail-fast**：服务启动时检查运行前提（工作目录可写、SQLite 可打开/迁移、必需配置齐全、socket 目录可用……），任一不满足 = 记 error 日志并**直接停止启动**——带病运行比不运行更危险；
2. **运行期不崩溃**：除物理故障、操作系统故障外，平台服务理论上不应崩溃。业务侧的一切错误由四道机械防线拦截，只影响该 run；平台自身的未捕获异常 / unhandled rejection 必须兜底——记 error 日志、保住主循环，不允许裸奔退出；
3. **泄漏是 bug**：内存泄漏、句柄泄漏不是可接受现象，发现即修，不靠定时重启缓解。
