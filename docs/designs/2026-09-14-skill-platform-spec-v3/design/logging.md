# 日志设计

> 机制文档。术语定义见 `design/glossary.md`。日志是平台的一等工具，失败处理第一阶段就依赖它。

## 1. 三层日志

| 层 | 内容 | 用途 |
|----|------|------|
| **通道日志** | 每条通道一个独立日志（业务通道与出口通道），按 channel_id 命名（如 `wecom__wmAb3xK9Qf__b01J8xk.log`、`exit__wmAb3xK9Qf.log`），该通道全部任务/生命周期/投递串联 | 排障第一现场；并发执行时写入天然不交错 |
| **总日志** | 系统级事件流水：任务入队 / 出队 / 完结 / 死信（两个队列各自记录） | 全局审计与回溯 |
| **模块日志** | 控制台日志、队列日志等各模块自己的运行日志 | 各模块运行排查 |

## 2. 日志工具的标准能力

| 能力 | 约定 |
|------|------|
| 开关 | 支持全局开启/关闭日志 |
| 等级 | `error / warn / info / debug`，运行时可配置输出级别 |
| 模块标记 | 每条日志必带模块标识（scheduler / exit-loop / queue / console / lifecycle …） |
| 时间戳 | 每条日志必带（ISO 8601，带时区） |
| 封装形态 | 简单封装、**兼容 `console.log` 调用习惯**（Node + TypeScript 技术栈），替换成本为零 |
| 脱敏 | **敏感信息（密钥、token、账号密码）输出前脱敏**——内建于日志工具，各模块不用各自处理 |
| 文件分割 | **平台不实现**——交给系统工具（如 Ubuntu 的 logrotate） |

## 3. 输出规则（各模块统一遵守）

| 级别 | 何时输出（必须/可选） |
|------|----------------------|
| `error` | **必须**：发生严重问题、无法继续执行（任务失败、沙箱崩溃、投递重试耗尽、死信落库） |
| `warn` | **必须**：发生问题但不影响后续处理（重试发生、门禁跳过、配置缺失走默认值） |
| `info` | **必须**：关键节点（任务入队/出队/完结、生命周期创建/销毁、通道创建、出口投递成功、配置变更） |
| `debug` | **可选**：排查用细节（信封内容、中间状态），生产默认关闭 |

纪律：error/warn/info 三级是契约性的——该打的必须打，排查问题不靠补日志。

## 4. 关联键

三层日志之间用三个键互跳：`event_id`（单个任务）、`lifecycle_id`（单次执行）、channel_id（跨任务的通道线——业务通道 `source__session_id__business_id`，出口通道 `exit__destination_id`）。一次联动的整串任务另可用 `correlation_id` 串联。
