## 1. 定位与边界

**控制台 = 服务系统全部控制开关与仪表盘的集合，是与服务交互的可视化入口**：查看状态、监控状态、控制运行规则、增减规则。它调用各模块的公开接口获取数据、修改数据、展示数据、统计结果，**本身没有任何业务逻辑**。

**明确不做：UI 拖拽式业务编排，也不做流程语言（DSL）。** 业务流程的承载体是**业务流程程序**（代码即流程，见 `design/business-workflow.md`）——代码是唯一的 source of truth，图至多由执行轨迹单向渲染。这是与 Dify 类产品的根本分野。

契约纪律同样约束控制台：只能经各模块的公开接口读写，不允许直接触碰其他模块的内部存储。

---

## 2. 易用性：设计的灵魂

用户的使用成本决定产品生死。很多产品不是死于功能不行，也不是死于软件质量，而是死于**违背使用者的习惯**。控制台的第一设计目标不是功能完备，而是：**简单到零学习成本**。

1. **一看便知**：界面自解释，用户不读任何文档就能完成核心路径：创建业务 → 跑通 → 看到结果。这一条也是验收标准。
2. **提示内建**：每个功能项、每个资料模块旁设叹号（❗），点击即知核心关键：**是什么、何时用、配错的后果**。不跳转外部文档。
3. **习惯优先**：表单就是表单，列表就是列表，不发明新交互范式。宁可少做功能，不做费解的功能。

## 3. 业务是什么（核心定义）

**业务 = 包 + 配置**：包是业务代码单位（恰好一个：业务流程程序与胶水代码的载体）；配置是控制台登记的资料（工具与 skill 绑定、提示词总纲、agent、大模型、入口、出口、key-value）——资源声明。概念上 **包 = 胶水代码 + 独立工具 + skill + 总纲提示词 + sdk 等**（非封闭枚举），机制上工具与 skill 的绑定挂在业务上、总纲提示词是配置中的业务资料字段（见 `design/asset-model.md` §1）。

- **业务流程程序**：业务侧编写的独立程序（TypeScript + 业务 SDK），承载全部流程逻辑——检查、获取、脱敏、大模型调用、还原、门禁都是程序里的环节。平台 spawn 它执行，约束只有一入一出（见 `design/business-workflow.md`）；
- **资产三族**：包 / 工具 / skill（见 `design/asset-model.md`）。业务绑定恰好 1 个包 + 任意多工具 + 任意多 skill 集合；选用他人共享的工具或 skill（如 Jira 工具）时，账号凭证由本业务自己提供（凭证按业务隔离）；
- **提示词（总纲）**：每个业务一个。它向大模型说明这个业务是什么——规则、边界、要求、不可做。由平台在每次 agent 调用时自动注入，业务代码无需关心；
- **业务与入口机械绑定**：入口配置即业务的触发身份，不会出现错误的、匹配不上的情况；
- **出口 = 出口工具绑定**：从平台内置出口工具菜单勾选并填配置（见 §4），业务完成即按绑定投递——**出口不过 LLM，业务产出即投递内容**。

## 4. 核心操作：业务创建与配置 = 资料集合的填写与管理

创建业务和管理业务是**同一个操作**：把业务所需的全部资料逐项填写、维护。控制台 UI 上，每项资料是一个可交互模块（可写入、可读取），且自带叹号提示（§2）：

| 资料模块 | 内容 | 必填 |
|----------|------|------|
| 业务名称 | 展示名（中英文均可），可修改；创建时生成**业务 id，不可修改**——内部引用（子目录、channel_id 等）一律用 id | 是 |
| 包绑定 | 绑定**恰好 1 个包**（自己的；git 仓库登记，见 `design/asset-model.md`），并从它的 programs 里选**流程程序入口**——业务工作流程序（TypeScript + 业务 SDK）：检查/获取/脱敏/大模型调用/还原/门禁等环节都是其中的代码。本地可离线调试（`design/business-workflow.md` §3） | 是 |
| 工具绑定 | 绑定任意多**工具资产**（自己的 + 他人共享的）：`sdk.run` 可调用的子程序全部来自本包 programs ∪ 绑定工具。绑定时机械校验：包清单 `requires.tools` 的名字被覆盖、程序名不重复 | 否 |
| skill 绑定 | 绑定任意多 **skill 集合**（自己的 + 他人共享的）：`sdk.agent` 的 skill 白名单 = 绑定集合的技能并集。绑定时机械校验：`requires.skills` 的名字被覆盖、技能名不重复 | 否 |
| agent 选择 | MVP 仅支持 **pi**；选项由注册表驱动，后续新增不改 UI | 是 |
| 大模型选择 | MVP 仅支持 **qwen3.8max**；同上 | 是 |
| 入口（必选） | 与业务机械绑定。三种：**外部事件**（入口模块 + 事件类型 + 过滤配置 + 会话标识规则）/ **内部队列事件**（关注哪个业务的哪类产出）/ **定时**（§5）。可配多个入口 | 是 |
| 出口（可选） | 从**内置出口工具菜单**勾选（企微智能机器人 / 企微群 webhook / 邮件 / 自定义 webhook / jira / confluence / github 操作），按工具的 configSchema 填配置（webhook 地址、各平台账号等，凭证按业务隔离）。可配多个；多业务可绑同一工具，互不影响——按 business_id 隔离路由。机器人按场景选：通知类用 webhook 机器人，交互类用智能机器人 | 否 |
| 提示词（总纲） | 见 §3 | 是 |
| 关注 | **依赖的唯一表达方式**：声明本业务消费哪个业务的哪类产出（关注其 `业务id.产出类型`）；需要等待上游就关注其产出事件类型，平台不提供链内排序（见 `design/processing-chain.md` §2） | 是 |
| 失败传播 | 本业务失败时是否仍扇出结果（默认**不扇出** = 下游天然不触发、出口无投递；扇出则派生事件带失败状态，由下游门禁验收） | 否 |
| 通用配置 | 平台级默认值；业务配置可与通用配置重合，**业务配置优先级更高**。首条落地项：run 超时（默认 60 分钟） | 否 |
| key-value（普通桶） | 业务级普通 key-value（如 jira 站点地址、github 仓库地址），运行时注入 | 否 |
| key-value（安全桶） | 业务级安全 key-value（如 jira token、github token）：只写不读明文、掩码回显、运行时注入、不落盘不进日志。github / jira 等账号凭证本质也是 key-value，统一在此配置，包/工具按 key 取用 | 否 |

**要点：**

1. 资料与注册表一一对应——**控制台创建业务 = 登记一份业务资料 + 上传一个流程程序**；
2. 资料模块按需增删，新资料类型 = 新增一个可交互模块，不动控制台骨架；
3. 控制台业务列表即注册表视图；处理链无顺序语义（链内并行），无需排序维护。

## 5. 定时触发

- 两种定时器：**周期定时器**（如每 50 分钟一次）、**绝对定时器**（支持多个，如每天 9:00、12:00）；
- **定时到点 = 包装成任务入队，不直接执行**——并发已满时会延迟，可接受；所有触发走同一条入口队列，语义统一。

## 6. 工作目录与数据分类

平台级工作目录（控制台可配置）。**数据按生命周期分类，不按归属混放**——分类的第一轴是「删了会怎样」：

| 类 | 一句话解释 | 位置 | 可删除性 |
|----|-----------|------|---------|
| **配置** | 人写给平台的输入：环境变量 + 可选配置文件兜底（优先级：env > 文件 > 代码默认值；格式 JSON） | `{workspace}/config.json`（可选） | 人工维护，进 git |
| **状态** | 平台运行中自己写的结构化数据：注册表/队列/通道/设置/账号/资产登记记录/身份目录 | `data/platform.db`（SQLite） | 平台自管（部分表 TTL 如队列 purge），备份即文件拷贝 |
| **缓存** | 可随时重建的物：资产物化（git clone）、仓库克隆、agent 会话（会话清了丢多轮上下文，不丢正确性） | `cache/` | 随时可清 |
| **业务执行产生的临时数据** | 每次 run 的隔离工作区与产物 | `runs/` | TTL 清理（不早于任务记录保留期） |
| **日志** | 排查追踪：平台三日志 + 业务日志（见 `design/logging.md`） | `logs/` | 轮转可删（logrotate），不备份 |

**身份目录（共享参考数据）**：jira↔github↔邮箱↔企微账号映射——投递时「找到这个人的所有通道」。存 sqlite（随 platform.db），全局一份、admin 维护。本版只定归属，实现归后续任务。

```
{workspace}/                        # 平台级工作目录（控制台配置）
├── config.json                     # 可选默认配置（环境变量优先）
├── data/
│   └── platform.db                 # 状态（全部 sqlite 表，含资产登记记录）
├── cache/                          # 可清（删除不丢正确性）
│   ├── assets/{asset_id}/          # 资产物化（git clone，可重拉）
│   ├── repos/{host}/{source}/{session_id}/{business_id}/   # 工作仓库克隆（可变工作区）：host = github.com/gitee.com 等，
│   │                                                       # 同一仓库在不同托管的克隆各自独立（从属关系使用者自负，平台不管）；
│   │                                                       # 同通道串行 ⇒ 无并发写
│   └── agent-sessions/{source}/{session_id}/{business_id}/ # pi 会话存储（--session-dir 指向）
├── runs/{source}/{session_id}/{business_id}/{run_id}/      # 业务执行产生的临时数据
└── logs/                           # 日志
    ├── system.log / entry-loop.log / exit-loop.log
    └── businesses/{source}/{session_id}/{business_id}/{run_id}.log
```

规则：五类分根、互不混放；运行可变区的三维键（source/session_id/business_id）与 channel_id 一致——**串行不变量靠键不靠父目录**，分类拆分不影响「同通道串行 ⇒ 同目录无并发写」；内部引用一律用业务 id；`runs/` 与 `cache/` 的清理策略属实现期细节。

## 7. 账号体系

- **标准账号**：注册、登录、管理；
- **两种角色**：**admin**（维护公共内容：公共 skill、公开配置、账号管理）与**普通成员**；
- **账号 → 多业务**：每个账号可创建和管理多个业务（如 sdk 账号、后端账号分属不同团队，各管各的业务）；
- 数据库账号与业务数据均存 SQLite（见骨架 §4）。

## 8. 监控与统计

| 项 | 约定 |
|----|------|
| 并发监控 | 控制台实时显示当前并发执行数（两个循环各自的通道并发情况）；**两道并发闸门（业务/出口）各自在控制台设置**（见 `design/scheduler.md`） |
| 资源监控（CPU/内存/容器） | **直接使用 Portainer**（Docker 控制台，自带 UI），不重复造轮子 |
| 任务监控 | 以业务为单位：任务列表、业务标记（创建/进行中/成功/失败/超时）、维护性干预（终止、重试）；出口投递状态（成功/失败/死信） |
| 结果统计 | 每个业务可按结果契约输出二维表；**缺省为按日期的调用统计**：成功/失败/超时次数（取自业务标记）+ 通用属性（token 调用量、调用耗时） |
| 日志检索 | 按 event_id / lifecycle_id / channel_id / correlation_id 检索（见 `design/logging.md`） |

## 9. 数据隔离

业务是隔离单位，五项边界：

1. **配置与密钥**——按业务注入，业务之间不可见（普通/安全两桶同规则；出口绑定同理，A 业务的结果永远触发不了 B 业务的出口）；
2. **会话与生命周期数据**——按业务命名空间隔离；
3. **执行 workspace**——按运行实例隔离（`runs/{run_id}/`）；
4. **仓库绑定**——仓库地址与凭证按业务绑定，平台内部对仓库可管理、可隔离；
5. **结果数据**——按业务归属，互不串扰。

## 11. MVP 范围

做：账号体系（admin + 普通成员）、资产登记与管理（包/工具/skill：git 登记、列表、下架；共享标记登记时定）、业务创建与配置（§4 资料模块，含叹号提示）、关注与依赖配置、出口工具勾选与配置、定时触发、并发监控与上限设置（两道闸门）、任务监控（业务标记 + 干预）、Portainer 资源监控、agent=pi / 模型=qwen3.8max（注册表驱动）。页面范围见 §12。

不做：定时通知出口类型、拖拽编排、二维表图形化、跨业务联合分析、多 API Key 管理、平台级共享连接、统计搜索页（§12，后续增加；结果缺省统计随该页一起落地）。

## 12. UI 骨架（页面结构）

页面 = 左侧导航项，七个页面覆盖全部职责。**导航按日常使用频率排序**（登录页是门槛，不进导航）；仪表盘空状态放"创建第一个业务"引导，保住首次使用路径（§2）。每页只经各模块的公开接口取数与写入——契约纪律延伸到 UI 层，页面不碰任何模块的内部存储。每个功能项带叹号提示（§2）。

| 顺序 | 页面 | 可见角色 | 职责 | 数据来源（公开接口） | 范围 |
|------|------|---------|------|---------------------|------|
| — | 登录页 | 未登录 | 账号密码登录 | `AccountService`（`design/accounts.md`） | MVP |
| 1 | 监控仪表盘（首页） | 全部登录用户 | 实时并发数（两个循环各自的通道并发情况）；任务监控：业务标记（创建/进行中/成功/失败/超时）与维护性干预（终止、重试） | `TaskQueue` ×2 / `ChannelPool` / `Lifecycle`（业务标记投影） | MVP |
| 2 | 统计搜索 | 全部登录用户 | 任务状态与结果数据的统计和检索：缺省按日期统计（成功/失败/超时次数 + token 调用量、耗时），按 event_id / lifecycle_id / channel_id / correlation_id 检索 | `Lifecycle`（业务标记与统计属性）/ `Logger`（检索） | 后续增加 |
| 3 | 业务管理 | 全部登录用户 | 业务列表（注册表视图）；创建/编辑业务 = §4 资料集合的填写与维护（含出口工具勾选与配置） | `BusinessRegistry` / `AssetRegistry` / `ExitRegistry` / `EnvProvider` / `ConfigStore` | MVP |
| 4 | 资产管理 | 全部登录用户 | 包 / 工具 / skill 三族资产的登记（git url + 分支/tag/commit + 子路径；工具/skill 定共享标记）、列表、下架；成员管理自己的，admin 只读查看全部 | `AssetRegistry` | MVP |
| 5 | 通用配置 | 所有用户全部可读，admin可写 | 全局设置（超时、hop 上限、业务/出口通道并发数等，仅 admin 写）；通用层 key-value 两桶（安全桶只显示键名与掩码，不明文回显） | `ConfigStore` / `EnvProvider` | MVP |
| 6 | 用户管理 | admin | 建号、停用/启用 | `AccountService` | MVP |

规则：**新页面 = 新增导航项 + 消费公开接口，不动本骨架**（与 §4 资料模块的增删逻辑一致）；页面内具体布局、组件选型属实现期。
