# 话术集 · 关键概念定义

> 本系统（**easemob-agent**）全部关键概念的统一解释。每个概念：一句人话 + 精确义 + 要点 + 英文术语（代码实现直接使用，不再现找）。
> 维护规则：新增关键概念先进本页；概念改名/废弃只在本页改，各细节文档引用本页、不重复定义。

---

## 调度循环（心脏）· Scheduler Loop（Heart）

一句话：平台唯一的主循环，系统的心脏。

精确义：它只做一件事——从任务队列取出下一个任务，找到关注该事件的业务，把 (任务, 业务) 挂上对应通道，驱动业务生命周期的创建、执行、完结。心跳一次，系统前进一步；心脏停跳，全系统静止。

要点：心脏不认识业务细节——入口懂业务，信封带答案，心脏只读信封字段。

## 任务队列（主任务队列）· Task Queue

一句话：系统的统一入口缓冲带。

精确义：任何触发（外部通知、内部通知、定时到点）都先被包装成任务放进来，由调度循环按到达顺序逐个取出消化。先进先出、持久化（SQLite）。

要点：系统中其他队列（如日志队列）都是局部的、服务于特定模块的；不加前缀说「任务队列」，专指这一条。

## 业务处理链（处理链）· Processing Chain

一句话：一个事件的全部关注者，并行消化。

精确义：任务被取出后，关注 `(source, event_type)` 的业务组成该任务的处理链。**链内并行**——每个业务有自己的串行键，各自挂通道、互不等待（见通道词条）。

要点：**业务间顺序的唯一表达方式 = 关注上游的产出事件**（B 依赖 A，则 B 关注 A 的 `业务id.产出类型`；A 不完成、事件不存在，B 自然不触发）。上游不知道谁关注了自己，关注是下游的声明。详见 `design/processing-chain.md`。

## 门禁 · Gate

一句话：业务在处理链上的质量检查，**执行者是大模型，不是平台代码**。

精确义：**双门禁**——① **自检**：业务产出结果前，按创建时定好的审查标准自查，不合格重做（重做次数有上限）；② **下游验收**：下游业务执行开始时，按创建时预定的验收标准检查输入（上游产出、外部业务系统状态），未通过则本次执行以失败完结（失败原因：输入未就绪），不派生、下游自然不触发。

实现形式由业务在创建时自定：**弱约束**——规则写进提示词/skill，大模型自觉遵守；**强约束**——检查逻辑写成脚本放在 skill 里，提示词约束大模型必须先调用脚本、以其返回为准（半机械检查）。

要点：平台不提供门禁函数契约——门禁判的是业务语义，业务语义归业务组合体（提示词 + skill）承载，与「心脏不认识业务」一致。**门禁只验收、不等待**：需要等待的依赖必须表达为事件订阅（反例见 `design/validation.md` S4'）。**本页是门禁的唯一定义处**。

## 通道 · Channel ｜ 串行键 · Channel Key

一句话：平台侧的执行线与上下文串联单位——同一条通道严格串行，不同通道自然并行。

精确义：通道以**串行键**标识：**`source__session_id__business_id`**（三维，双下划线分隔，不用冒号——避免文件名/路径转义问题）：

| 维度 | 含义 | 来源 |
|------|------|------|
| `source` | 来源命名空间 | 入口写入 |
| `session_id` | **源生会话标识**（群 id / 工单 key / 仓库+PR号 …） | 入口按来源规则提取（规则见 `design/channel-model.md` §4） |
| `business_id` | **执行业务** id | 匹配后按关注者补入 |

串行规则：**相同会话 + 相同业务 = 同通道串行；其余一切组合 = 跨通道并行**。

第四维：通道上的一次执行实例 = 串行键 + `event_id`——**维度组合，越多越具体**。`event_id` 只做实例追溯/幂等/日志，**不参与串行判定**。

要点：通道创建即持久化到数据库（防意外丢失），完成只做状态变更；串行/并行是通道的自然属性，不是业务的配置项；最大通道并发数可在控制台修改；agent-cli 会话映射以串行键为键（同通道上下文连续）。详见 `design/channel-model.md`。

## 三种「会话」辨析（易混概念对比）

| 概念 | 归属 | 作用 | 标识 |
|------|------|------|------|
| **源会话**（企微会话 / Jira 工单 / GitHub PR…） | 源平台 | 人与业务的交互场所 | 群 id / 工单 key / 仓库+PR号 —— 即串行键第二维 `session_id` 的来源 |
| **通道**（我们的） | 本平台 | 执行串行 + 上下文串联 | 串行键 `source__session_id__business_id` |
| **agent-cli 会话** | agent-cli 侧 | 大模型推理上下文（内容托管在 agent-cli，不在本平台） | agent-cli 会话 id，由通道模块维护 串行键 ↔ 它 的映射 |

要点：**平台术语只有「通道」，不叫「会话」**——防止与另外两个混淆。由此「多轮会话 token 成本」不成立为平台风险：上下文由 agent-cli 托管，平台只存映射与元数据。

## 并发闸门 · Concurrency Semaphore

一句话：全局执行并发上限。

精确义：一道全局信号量，生命周期执行前取令牌，取不到就等。作用是保机器——每个并发执行是一个真实沙箱进程（百 MB 级内存），闸门值按部署机器资源定，控制台可修改。

## 生命周期 · Lifecycle

一句话：业务的一次完整执行。

精确义：业务组合体被任务触发后创建的动态执行实例，单次执行，跑完即销毁。包是静态的，生命周期是活的。

要点：平台不支持多阶段代码；复杂业务的多阶段需求用两种转化路径承接（见 `design/lifecycle.md`）。

## 业务标记 · Business Markers

一句话：任务状态的平台统一投影。

精确义：生命周期实例的状态机（创建/进行中/成功/失败/超时）在控制台的呈现，由平台统一打标，业务管理者无需操作。业务标记与生命周期状态是同一内容、两个视角。

## 业务 · Business

一句话：一个完整可执行的自动化单元。

精确义：业务 = **提示词（总纲）+ 一组 skill（内置的/自己上传的/他人公开的）+ agent-cli + 大模型**，外加一个必选入口、一个可选出口。业务与入口机械绑定，不会错配。

要点：触发订阅事件的是业务组合体，不是单个 skill。**业务 id（business_id）创建时自动生成、不可修改**，是一切内部引用（子目录、串行键业务维度等）的锚；**业务名（business_name）仅展示用，可修改**。

## Skill（包）· Skill Package

一句话：能力单元、工具单元。

精确义：遵循公开 skill 规范的静态包（SKILL.md 式），是业务的组成部分，没有更多特殊身份。不为本平台做任何适配；推荐在必选字段之外添加版本号属性。

要点：分 public（通用共享）/ private（业务专属）两种可见性，存放位置不同；平台登记元数据（整包 hash、创建/修改时间等）。

## 事件 / 任务 · Event / Task

- 事件（Event）：驱动平台的最小输入单元，由事件信封承载。
- 任务（Task）：事件包装后的可执行单元，进入任务队列等待消化。外部通知、内部通知、定时到点统一包装成任务。

## 事件类型 · event_type

一句话：信封上的**类别标签**、处理链的匹配键——回答「这是什么事件」，而不是「这是哪一条」。

精确义：下游业务按 `(source, event_type)` 声明关注、组成处理链。它是**类别而非实例**：同一业务产出的所有通知共用同一个值——这是它与 `event_id`（每条事件唯一，追溯锚点）的根本区别，所以叫 `type` 不叫 `id`。所有来源统一使用本字段做匹配：外部事件（如 `pr.create`）、internal 派生、cron/manual 到点触发都填它——语义是「事件类别」，不限于「通知」。

规则（已定）：

- 业务创建时声明，**一旦创建不可修改**；**全平台唯一**，不得与现有标识符冲突，名字要有意义；
- internal 事件：`对象.动作` = `业务id.产出类型`（如 `b01J8xk.review.completed`）——业务创建时声明产出类型，供下游关注；**依赖关系的唯一表达方式就是关注上游的产出事件类型**（见处理链词条）。

要点：**本页是 event_type 的唯一定义处**；契约文档（`design/event-contract.md`、`design/scheduler-loop-contracts.md`）引用本页，不重复定义。

## 入口 · Entry Adapter

一句话：一个事件源一个适配小模块。

精确义：职责链固定——验签 → 包装信封（含 session_id）→ 落队，立即返回，永远轻快。新事件源 = 新增一个入口小模块，不动内核。

要点：入口懂业务——源适配（含各来源会话标识提取规则）在入口完成，把答案填进信封，心脏只读信封字段。详见 `design/entries.md`。

## 出口 · Exit

一句话：任务队列中的可选任务，由出口型业务消化。

精确义：出口不是独立分层——业务结果统一包装成信封回队；需要触达外部系统（企微通知、Jira 编辑、Webhook 通知等）时，由出口型业务（结果处置 = 终结）关注并代发，触达能力以 public skill 形式由 Skill 包仓提供。新通知目的地 = 新增/选用出口型业务，不动内核。

## 控制台 · Console

一句话：服务系统全部控制开关与仪表盘的集合。

精确义：与服务交互的可视化入口——查看状态、监控状态、控制运行规则、增减规则。本身无业务逻辑。

## 子任务队列 · Sub-task Queue（预留概念）

一句话：执行通道的实体化形态。

精确义：按业务特点划分的实体队列，各自独立决定串行/并行。当前阶段以虚拟通道实现，不实体化；将来拆分执行层时可物化。
