# 话术集 · 关键概念定义

> 本系统（**easemob-agent**）全部关键概念的统一解释。每个概念：一句人话 + 精确义 + 要点 + 英文术语（代码实现直接使用，不再现找）。
> 维护规则：新增关键概念先进本页；概念改名/废弃只在本页改，各细节文档引用本页、不重复定义。

---

## 调度循环（心脏）· Scheduler Loop（Heart）

一句话：平台的主循环机械，两个实例——**入口事件循环**与**出口事件循环**。

精确义：循环只做一件事——从自己的任务队列取出下一个任务，找到关注者，把 (任务, 关注者) 挂上对应通道，驱动消化。两个实例同一套机械（队列/通道/闸门），只是注册表与执行器不同：

| 实例 | 消化什么 | 关注者与匹配 | 执行 |
|------|---------|-------------|------|
| **入口事件循环** | 外部入口事件、internal 派生事件、定时/手动 | 业务；订阅匹配 `(source, event_type)` | 业务生命周期（子进程执行，分钟级） |
| **出口事件循环** | 仅业务产出的派生事件 | 产出方业务的出口绑定；归属匹配 `producer_business_id` | 出口工具投递（不过 LLM，毫秒级） |

要点：心脏不认识业务细节——入口懂业务，信封带答案，心脏只读信封字段。**结果无脑扇出**：业务完成即把派生事件同时投入两个队列，各循环自行过滤（无关注者 / 无出口绑定即丢弃，无害）。

## 任务队列 · Task Queue

一句话：两个循环各自的缓冲带，共两条——**入口队列**与**出口队列**。

精确义：任何触发（外部通知、内部通知、定时到点）先被包装成任务进入口队列，由入口事件循环消化；业务产出的派生事件同时进入口队列与出口队列（见调度循环词条「结果无脑扇出」）。两条队列同一契约：先进先出、持久化（SQLite），按到达顺序逐个取出消化。

要点：系统中其他队列（如日志队列）都是局部的、服务于特定模块的；不加前缀说「任务队列」，指入口队列。

## 业务处理链（处理链）· Processing Chain

一句话：一个事件的全部关注者，并行消化。

精确义：任务被取出后，关注者组成该任务的**处理链**——入口事件循环中，关注者是订阅 `(source, event_type)` 的业务；出口事件循环中，关注者是产出方业务的出口绑定（归属匹配，非订阅，见出口词条）。**链内并行**——每个关注者有自己的 channel_id，各自挂通道、互不等待（见通道词条）。

要点：**业务间顺序的唯一表达方式 = 关注上游的产出事件**（B 依赖 A，则 B 关注 A 的 `业务id.产出类型`；A 不完成、事件不存在，B 自然不触发）。上游不知道谁关注了自己，关注是下游的声明。详见 `design/processing-chain.md`。

## 门禁 · Gate（含检查、处理器）

一句话：业务流程内部的机械质量环节——**业务代码实现，不是平台概念**。

精确义：三个同类环节，按位置区分——**检查**（agent 调用之前，验收输入）、**门禁**（产出之后，验收结果）、**处理器**（流程中间，改写数据，如拉取工单、脱敏、还原）。实现形态业务自择：流程程序内的函数，或经 `sdk.run()` 组合的独立子程序（同一子进程契约，见 `design/business-workflow.md` §5）。机械程序优先；需要语义判断时才经 skill/大模型。

要点：**平台不设门禁契约、没有平台挂接点**——平台对业务只有内容无关的机械边界（信封/结果 schema、超时、配额）。**门禁只验收、不等待**：需要等待的依赖必须表达为事件订阅（反例见 `design/validation.md` S4'）；验收未通过 = 本次执行以失败完结（失败原因：输入未就绪），不扇出、下游自然不触发。**本页是门禁的唯一定义处**。

## 通道 · Channel

一句话：平台侧的执行/投递线与上下文串联单位——同一条通道严格串行，不同通道自然并行。

精确义：通道以 **`channel_id`** 标识，两个循环各有键规则：

| 通道 | channel_id | 串行效果 |
|------|-----------|---------|
| **业务通道**（入口事件循环） | `source__session_id__business_id`（三维，双下划线分隔，不用冒号——避免文件名/路径转义问题） | 相同会话 + 相同业务 = 同通道串行；其余一切组合 = 跨通道并行 |
| **出口通道**（出口事件循环） | `exit__destination_id`（destination_id = 投递目标标识，由出口工具从绑定配置提取；各工具提取规则见 `design/channel-model.md` §2） | 同一目标串行（不分业务，通知有序、天然限流）；跨目标并行 |

业务通道三维的含义与来源：

| 维度 | 含义 | 来源 |
|------|------|------|
| `source` | 来源命名空间 | 入口写入 |
| `session_id` | **源生会话标识**（群 id / 工单 key / 仓库+PR号 …） | 入口按来源规则提取（规则见 `design/channel-model.md` §4） |
| `business_id` | **执行业务** id | 匹配后按关注者补入 |

**`channel_id`** 即旧称「串行键」。

第四维（业务通道）：通道上的一次执行实例 = channel_id + `event_id`——**维度组合，越多越具体**。`event_id` 只做实例追溯/幂等/日志，**不参与串行判定**。

要点：通道创建即持久化到数据库（防意外丢失），完成只做状态变更；串行/并行是通道的自然属性，不是业务的配置项；两个循环的最大通道并发数各自在控制台修改；agent-cli 会话映射以业务通道 channel_id 为键（同通道上下文连续）——出口通道不过 LLM，无 agent 会话映射。详见 `design/channel-model.md`。

## 三种「会话」辨析（易混概念对比）

| 概念 | 归属 | 作用 | 标识 |
|------|------|------|------|
| **源会话**（企微会话 / Jira 工单 / GitHub PR…） | 源平台 | 人与业务的交互场所 | 群 id / 工单 key / 仓库+PR号 —— 即 channel_id 第二维 `session_id` 的来源 |
| **通道**（我们的） | 本平台 | 执行串行 + 上下文串联 | channel_id `source__session_id__business_id` |
| **agent-cli 会话** | agent-cli 侧 | 大模型推理上下文（内容托管在 agent-cli，不在本平台） | agent-cli 会话 id，由通道模块维护 channel_id ↔ 它 的映射 |

要点：**平台术语只有「通道」，不叫「会话」**——防止与另外两个混淆。由此「多轮会话 token 成本」不成立为平台风险：上下文由 agent-cli 托管，平台只存映射与元数据。出口通道不映射 agent-cli 会话（投递不过大模型）。

## 并发闸门 · Concurrency Semaphore

一句话：执行并发上限，两个循环各一道。

精确义：全局信号量，执行前取令牌，取不到就等。**业务闸门（`task_concurrency`）**保机器——每个并发执行是一个业务流程进程（可再拉起 agent 子进程，百 MB 级内存），闸门值按部署机器资源定，量级几十；**出口闸门（`result_concurrency`）**管结果通知投递——毫秒级网络调用、不占执行进程，量级可大得多。两道闸门值各自在控制台修改。

## 生命周期 · Lifecycle

一句话：业务的一次完整执行。

精确义：业务被任务触发后，平台 spawn 业务流程程序产生的动态执行实例——单次执行，进程退出即销毁。包与程序是静态的，生命周期是活的。

要点：一次执行内调用几次大模型、流程几个阶段，都是业务代码内部细节（见 `design/business-workflow.md`）；跨业务的阶段串联走事件订阅（见 `design/processing-chain.md`）。

## 业务流程程序 · Workflow Program

一句话：业务的执行体——业务侧编写的独立可执行程序，代码即流程。

精确义：TypeScript + 业务 SDK 编写的程序，承载业务的全部流程逻辑（分支/循环/多次大模型调用/各环节）。平台 spawn 它为独立子进程，约束只有**一入一出**（stdin 进信封与上下文、stdout 出唯一结果、进程退出 = run 结束）；子进程契约见 `design/business-workflow.md` §2——**本页不重复定义，唯一定义处在该文档**。

要点：平台不编排流程、不认识业务内容；业务上下文业务自己管理（程序内变量）；跨 run 无状态，多轮连续性由通道承接。

## 业务 SDK · Business SDK

一句话：平台提供给业务侧的唯一编程面。

精确义：业务程序的依赖包，封装读输入、读配置/密钥、调 agent、调子程序、返回结果的全部机制（进程管理、协议编解码、socket 通信）。API 与语义的唯一定义处：`design/business-workflow.md` §3。

要点：**SDK 是约定层，不是封锁层**——让正路最好走；真边界在系统层（沙箱分期）。

## agent 调用服务 · Agent Service

一句话：大模型调用的唯一通道，平台侧模块。

精确义：`sdk.agent()` 的另一端——每 run 一个本地 socket + 一次性 token；平台 spawn pi 子进程执行（pi 是唯一内核），注入提示词总纲、按业务白名单校验 skill 并经 `--no-skills` + `--skill` 注入、经 `-e` + `--no-extensions` 注入 skill 附带的 pi extension、按通道映射恢复会话、按 run 计配额。契约与 hooks 纪律的唯一定义处：`design/business-workflow.md` §4。

要点：模型凭据由平台持有，不进入业务进程。

## 业务标记 · Business Markers

一句话：任务状态的平台统一投影。

精确义：生命周期实例的状态机（创建/进行中/成功/失败/超时）在控制台的呈现，由平台统一打标，业务管理者无需操作。业务标记与生命周期状态是同一内容、两个视角。

## 业务 · Business

一句话：一个完整可执行的自动化单元。

精确义：业务 = **业务流程程序**（执行体，代码即流程）+ **业务资料**（提示词总纲、一组 skill、agent、大模型——资源声明，控制台登记），外加一个必选入口、一个可选出口（出口 = 出口工具绑定，见出口词条）。业务与入口机械绑定，不会错配。

要点：触发订阅事件的是业务，不是单个 skill。**业务 id（business_id）创建时自动生成、不可修改**，是一切内部引用（子目录、channel_id 业务维度等）的锚；**业务名（business_name）仅展示用，可修改**。

## 程序包 · Agent Package

一句话：平台管理的**唯一资产单元**——一个 git 仓库或上传包。

精确义：包内可含**多个子程序**（可执行入口）、**多个 skill**（包内的一种内容）、以及包自己需要的其他资源（脚本/数据/文档，平台不解析）。平台对包只做三件事：登记（引用或上传母本 + 元数据）、清单机械校验（`agent-package.json`）、物化后吊起执行（子进程，契约约束）。业务绑定多个包；包内资源名（程序名、skill 名）的解析范围 = 该业务绑定的全部包，同名冲突按可见性优先级 **业务级 > 账号级 > 公共** 首个命中。**模型与作者指南的唯一定义处：`design/package-model.md`**。

要点：资产单元从 skill 进化而来——业务的完整链路不是一个 skill 能承载的（取数/脱敏/门禁等机械环节与分支循环控制流都在 skill 之外），程序包以"代码即流程"承载全部环节，skill 归位为包内"给大模型用的能力"。物化缓存可清理、运行时缺了补拉；母本永不自动删。

## Skill

一句话：给大模型的能力单元——程序包内的一种内容，不是独立资产。

精确义：遵循公开 skill 规范（SKILL.md 式）的静态内容，不为本平台做任何适配；**包自洽原则**：随所在程序包版本化，用别包的 skill = 业务绑定那个包。业务代码经 `sdk.agent({ skills: [...] })` 按名引用（可多个、可跨包），平台白名单校验（绑定包的 skills 并集）后逐个 `--skill` 注入 pi 子进程（机制见 `design/package-model.md` §10）；skill 可附带 pi extension（会话内守卫，经 `-e` 白名单注入）。

要点：**没有 `sdk.skill` 运行时注册接口**——skill 是包内静态资产，运行时动态注册会绕过清单校验与白名单，不支持；可见性随包三级（公共/账号/业务），不再有独立的 public/private 划分。

## 事件 / 任务 · Event / Task

- 事件（Event）：驱动平台的最小输入单元，由事件信封承载。
- 任务（Task）：事件包装后的可执行单元，进入任务队列等待消化。外部通知、内部通知、定时到点统一包装成任务；业务产出的派生事件同时是两个循环的任务。

## 事件类型 · event_type

一句话：信封上的**类别标签**、处理链的匹配键——回答「这是什么事件」，而不是「这是哪一条」。

精确义：下游业务按 `(source, event_type)` 声明关注、组成处理链。它是**类别而非实例**：同一业务产出的所有通知共用同一个值——这是它与 `event_id`（每条事件唯一，追溯锚点）的根本区别，所以叫 `type` 不叫 `id`。所有来源统一使用本字段做匹配：外部事件（如 `pr.create`）、internal 派生、cron/manual 到点触发都填它——语义是「事件类别」，不限于「通知」。

规则（已定）：

- 业务创建时声明，**一旦创建不可修改**；**全平台唯一**，不得与现有标识符冲突，名字要有意义；
- internal 事件：`对象.动作` = `业务id.产出类型`（如 `b01J8xk.review.completed`）——业务创建时声明产出类型，供下游关注；**依赖关系的唯一表达方式就是关注上游的产出事件类型**（见处理链词条）。

要点：**本页是 event_type 的唯一定义处**；契约文档（`design/event-contract.md`、`design/scheduler-loop-contracts.md`）引用本页，不重复定义。internal 派生事件的信封另带 `producer_business_id`（产出方业务 id）——出口事件循环归属匹配的键（见 `design/event-contract.md` §1）。

## 入口 · Entry Adapter

一句话：一个事件源一个适配小模块。

精确义：职责链固定——验签 → 包装信封（含 session_id）→ 落队，立即返回，永远轻快。新事件源 = 新增一个入口小模块，不动内核。

要点：入口懂业务——源适配（含各来源会话标识提取规则）在入口完成，把答案填进信封，心脏只读信封字段。详见 `design/entries.md`。

## 出口 · Exit

一句话：业务结果的对外投递——出口事件循环消化，出口工具执行。

精确义：业务完成（或失败且配置 `on_failure`）即把派生事件**无脑扇出**到出口队列；出口循环按 `producer_business_id` 做**归属匹配**，找出产出方业务的全部出口绑定，逐绑定投递；业务未配出口即丢弃（无害，与入口循环空链同理）。出口与入口对称：新通知目的地 = 新增一个出口工具模块，不动内核。

要点：出口**不过 LLM**——业务产出即投递内容，出口不做内容加工；出口不派生事件、不参与 hop_count；同目标串行（出口通道 `exit__destination_id`），通知有序、天然消化目的地平台限流；投递失败有界重试，耗尽进死信并告警（见 `design/failure-handling.md`）。

## 出口工具 · ExitTool ｜ 出口绑定 · ExitBinding

一句话：出口工具 = 平台内置的投递器模块（一个目的地类型一个）；出口绑定 = 业务对某工具的一份配置实例。

精确义：工具契约 = `kind`（标识）+ `name`（展示名，控制台按它选用）+ `configSchema`（配置项声明，控制台据此渲染表单）+ `bind(config)` → `Exit`；`Exit.deliver(result)` 的配置在 bind 时注入并由实例持有（凭证从环境配置解析一次，只活内存）。出口绑定 = `(business_id, kind, config)`，控制台创建业务时配置；多个业务可绑定同一工具，按 business_id 隔离路由——A 业务的结果永远触发不了 B 业务的出口。

要点：内置菜单：企微智能机器人、企微群 webhook、邮件、自定义 webhook、jira / confluence / github 操作；出口工具是**平台模块、不是 skill**（skill 服务于业务执行中的 LLM 调用，出口工具由平台直接调用）；**工具实现独立可复用**——github / jira / confluence / 邮件等工具的实现是一个独立的 TypeScript 文件，skill（LLM 执行内调用）与出口工具（平台直接投递）是它的两种封装，复用同一实现（见 `design/core-modules.md` §5）；契约见 `design/scheduler-loop-contracts.md` §6。

## 控制台 · Console

一句话：服务系统全部控制开关与仪表盘的集合。

精确义：与服务交互的可视化入口——查看状态、监控状态、控制运行规则、增减规则。本身无业务逻辑。

## 子任务队列 · Sub-task Queue（预留概念）

一句话：执行通道的实体化形态。

精确义：按业务特点划分的实体队列，各自独立决定串行/并行。当前阶段以虚拟通道实现，不实体化；将来拆分执行层时可物化——两个调度循环天然就是两个 worker 池的雏形。
