# 调度循环与任务队列

> 机制文档。术语定义见 `design/glossary.md`。

## 1. 心脏的工作方式

调度循环是平台唯一主循环。每跳一次：

1. 从任务队列**有序摄取**下一个任务；
2. 读信封，按信封找到该任务的处理链（关注了它的下游业务）；
3. 按**通道键**将任务挂入对应会话通道；
4. 通道轮到该任务时：过并发闸门 → 创建生命周期 → 执行 → 销毁 → 结果统一包装成信封入队（出口/后续由关注者消化）。

**心脏不认识业务细节**：入口模块做源适配时把会话键填进信封，心脏只读信封字段——入口懂业务，信封带答案，心脏只读字段。

## 2. 任务队列

- **统一包装**：外部通知、内部通知、定时到点，统一包装为任务；
- **特性**：FIFO、**持久化（SQLite）**、有序消化；
- **第一阶段不预留并行接口**：并行化只是调度器的内部实现变更（一个 take 循环 → 多 worker），任务契约与业务配置一概不动，按最小设计原则无需预留。

## 3. 派发规则：通道键

**通道键 = `source__session_id`**（双下划线分隔，不用冒号——避免文件名/路径转义问题）。

| 情形 | 规则 |
|------|------|
| 已识别来源（wecom / jira / github …） | 按该来源的会话键规则处理（见 `design/session-model.md` §4） |
| **未识别来源** | **忽略该任务 + 日志记录**（不创建通道、不报错扩散） |
| 无会话的来源（cron / manual） | 通道键兜底为业务标识 → **业务级串行** |

「无会话」的准确语义：**没有会话就创建会话，已有会话就恢复会话**（由会话模块负责，见 `design/session-model.md` §3）——兜底规则只针对天然无会话的触发（定时/手动）。

## 4. 会话通道

- **虚拟通道**：以通道键为索引的执行链；同通道串行，跨通道并行，用完即焚；
- **持久化**：**通道创建即记录到数据库**（防意外丢失），后续只做状态变更（进行中/完结），不在完成时才落库；
- **通道并发**：准确说是「通道并发」——通道键唯一，不同通道并行推进；**最大通道并发数可在控制台修改**；
- 跨会话并行是自然结果，不是新功能——10 人聊天 = 10 条通道同时推进，各自的连续消息仍严格有序。

## 5. 并发闸门

全局信号量。瓶颈不在服务框架，在**本机沙箱**：每个并发执行 = 一个 agent 沙箱进程（百 MB 级内存起步）+ 独立 workspace。闸门值按部署机器资源定，量级为几十，**控制台可修改**。

## 6. 压力分布（已核实）

| 层 | 压力 | 结论 |
|----|------|------|
| 服务框架（调度/队列） | 可忽略 | 不构成瓶颈 |
| 本机沙箱（agent 进程） | 真实约束 | 并发闸门据此而定 |
| 流式响应 | 仅占一个连接 | 廉价 IO，不是问题 |
| 厂商配额（RPM/TPM） | 按主账号计，内部规模充足 | 触顶再议：商务提额 → 多账号 → 多厂商 |

**要点**：厂商限流按账号（组织）合并统计，不按单个 Key、不按 IP——**多 API Key 不扩配额**，控制台暂不做多 Key 管理（最小设计）。

## 7. 演进

虚拟通道 → 实体子任务队列：将来拆分执行层为 worker 集群时物化，语义不变。
