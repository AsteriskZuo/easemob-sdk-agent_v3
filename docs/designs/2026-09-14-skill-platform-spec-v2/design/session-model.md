# 会话模型

> 机制文档。术语定义见 `design/glossary.md`。

## 1. 两种会话，一张映射表（关键认知）

**我们的会话 ≠ agent-cli 的会话。**

- **我们的会话**：解决业务场景问题——多轮交互的串联、跨任务的上下文恢复、通道并发的粒度依据；
- **agent-cli 会话**：大模型的会话，推理上下文保存在 agent-cli 侧（会话内容在他们那边，不在我们这边）；
- **会话模块维护两者的映射**：我们的 session_id ↔ agent-cli 的会话 id。恢复、清空等操作通过映射落到 agent-cli 侧执行。

由此，「多轮会话 token 成本」不成立为平台风险：上下文由 agent-cli 托管，平台只存映射与元数据。

## 2. 会话标识

**会话标识 = `source__session_id`**（双下划线分隔，不用冒号——避免文件名/路径转义问题）。

**session_id = 业务id + 时间戳 + 随机数**。业务 id 在业务创建时生成、不可修改（业务名可改，子目录等内部引用一律用 id）。

示例：`wecom__b01J8xk-20260914153000-a7f3`

## 3. 会话模块职责

1. **绑定映射**：外部对象 ↔ session_id（企微会话、Jira 工单、GitHub PR）；
2. **agent-cli 会话映射**：session_id ↔ agent-cli 会话 id（§1）；
3. **四个基本操作**：
   - **创建会话**：新外部对象首次触发时创建（生成 session_id、建立两类映射）；
   - **恢复会话**：已有会话再次触发时，按映射找回 agent-cli 会话继续；
   - **压缩会话**：上下文过长时调用 agent-cli 的压缩能力；
   - **清空会话**：结束当前会话并解除映射；下次触发即创建新会话（新 session_id，历史仍可按时间追溯）。

## 4. 各来源的会话键规则

| source | 会话外部键 |
|--------|-----------|
| wecom | 群 id / 用户 id |
| github | 仓库 id + PR 号 |
| jira | 工单 key |
| internal | **继承上游任务的会话**（同一联动不另开会话） |
| cron / manual | 不建会话，走业务级串行兜底（见 `design/scheduler.md`） |

**通道键 = 会话标识**，同通道串行、跨通道并行（见 `design/scheduler.md`）。

## 5. 一个业务多个入口

业务与入口机械绑定（不会错配）；一个业务可绑定多个入口，**每个入口独立决定自己的会话键规则**：

| 入口 | 会话键 | 并发效果 |
|------|--------|----------|
| Jira webhook | 工单 key | 同工单串行，不同工单并行 |
| 企微消息 | 群/用户 id | 同会话串行，不同群/人并行 |

业务本体一份（提示词 + skill 组 + agent-cli + 大模型），入口多个，**并发语义由通道自然决定，零配置**。

## 6. memory（占位留白）

会话级长期记忆（memory）是后续阶段的候选能力，**第一阶段不实现**，仅在此留白。
