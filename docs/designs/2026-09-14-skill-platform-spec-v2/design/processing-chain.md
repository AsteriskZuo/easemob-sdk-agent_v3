# 业务处理链

> 机制文档。术语定义见 `design/glossary.md`。

## 1. 链的生成

全局只有一张有序业务列表（注册表的执行视图）。任务到达时：

1. 找到**关注了该任务**的下游业务（关注是下游的声明，上游不知道谁关注了自己）；
2. 按全局序组成该任务的处理链。

要点：全局序是顺序的唯一真相源；依赖关系在控制台可视化配置。

## 2. 链内执行语义

- 串行执行，且为「完成序」：前一个业务执行完毕才轮到下一个（依赖场景别无选择）；
- **依赖语义（每条依赖可配置）**：
  - 前置失败时，后者是否执行——**默认不执行**，可按依赖配置为继续执行；
  - 无依赖的业务：前者失败不株连，照常执行；
- **门禁（双保险，非常重要）**：在业务入口处拦截，对上个业务的产出**再次验证**——判「输入就绪」，不只是「与我有关」；未就绪则跳过，不阻塞链上后续业务。门禁是业务稳定运行的基础防线。

## 3. 业务间的数据约定：没有隐性接口

**平台内不存在隐性接口**——业务间的输入输出约定不在系统内部，而在 **skill 层**：

- 上游 skill 规定自己的输出格式，下游 skill 按约定读取；
- 格式不一致是 skill 层的问题，**不需要也不应该修改服务**；
- 所有跨业务的数据格式约定都必须显性列举（例如 Jira comments 的格式约定），不允许"靠默契"。

数据媒介两种：结果信封（入队）与外部业务系统（如 Jira comments——单一真相留在业务系统，人也可读）。

## 4. 示例（仅为理解）

工单审查完成 → 处理链 [企微通知（无依赖）→ crash 分析（依赖审查）→ 日志分析（依赖 crash）]：

企微通知把审查结果发到群；crash 分析门禁确认「工单含堆栈且审查已完成」后执行，结果按约定格式追加到 Jira comments；日志分析门禁确认「comments 已有 crash 结果」后执行，结果同样追加。

## 5. 防循环

两道防线：

1. **业务不得订阅自己的通知**（注册时校验，不言而喻的基本纪律）；
2. **hop_count（跳数上限）**：信封里的转发计数器——任务 A 的结果触发任务 B 时 +1，B 又触发 C 时再 +1……超过阈值判定为循环，进死信并告警。防的是 A→B→A 式的乒乓循环（阈值属实现期配置）。
