# 控制台设计

> 版本：v0.4
> 日期：2026-09-14
> 状态：待评审
> 定位：骨架文档（`skill-platform-spec-v2.md`）的子文档，定义控制台模块的设计要点。骨架只保留链接，细节以本文为准。

---

## 1. 定位与边界

**控制台 = 服务系统全部控制开关与仪表盘的集合，是与服务交互的可视化入口**：查看状态、监控状态、控制运行规则、增减规则。它调用各模块的公开接口获取数据、修改数据、展示数据、统计结果，**本身没有任何业务逻辑**。

**明确不做：UI 拖拽式业务编排。** 业务流程的承载体是业务组合体与提示词总纲（多阶段需求见 `design/lifecycle.md` §2），不是画布上的节点连线——这是与 Dify 类产品的根本分野。

契约纪律同样约束控制台：只能经各模块的公开接口读写，不允许直接触碰其他模块的内部存储。

---

## 2. 易用性：设计的灵魂

用户的使用成本决定产品生死。很多产品不是死于功能不行，也不是死于软件质量，而是死于**违背使用者的习惯**。控制台的第一设计目标不是功能完备，而是：**简单到零学习成本**。

1. **一看便知**：界面自解释，用户不读任何文档就能完成核心路径：创建业务 → 跑通 → 看到结果。这一条也是验收标准。
2. **提示内建**：每个功能项、每个资料模块旁设叹号（❗），点击即知核心关键：**是什么、何时用、配错的后果**。不跳转外部文档。
3. **习惯优先**：表单就是表单，列表就是列表，不发明新交互范式。宁可少做功能，不做费解的功能。

---

## 3. 业务是什么（核心定义）

**业务 = 提示词（总纲）+ 一组 skill（内置的 / 自己上传的 / 他人公开的）+ agent-cli + 大模型**，外加一个**必选入口**、一个**可选出口**。

- **提示词（总纲）**：每个业务一个。它向大模型说明这个业务是什么——规则、边界、要求、不可做。**业务本身需要让大模型知道是什么，模型才能更好地理解和处理业务**。内容不限于 skill 说明，用户可以写任何必要内容；
- **业务与入口机械绑定**：入口配置即业务的触发身份，不会出现错误的、匹配不上的情况；
- **skill 可见性**：选用他人公开的 skill（如 Jira 工具）时，账号凭证由本业务自己提供（凭证按业务隔离）。

---

## 4. 核心操作：业务创建与配置 = 资料集合的填写与管理

创建业务和管理业务是**同一个操作**：把业务所需的全部资料逐项填写、维护。控制台 UI 上，每项资料是一个可交互模块（可写入、可读取），且自带叹号提示（§2）：

| 资料模块 | 内容 | 必填 |
|----------|------|------|
| 业务名称 | 展示名（中英文均可），可修改；创建时生成**业务 id，不可修改**——内部引用（子目录、session_id 等）一律用 id | 是 |
| skill 组 | 选用内置/公开 skill，或上传自己的 skill（文件夹或压缩包，形态待定，见 §9）；上传时选择可见性（public/private） | 是 |
| agent 选择 | MVP 仅支持 **pi**；选项由注册表驱动，后续新增不改 UI | 是 |
| 大模型选择 | MVP 仅支持 **qwen3.8max**；同上 | 是 |
| 入口（必选） | 与业务机械绑定。三种：**外部事件**（入口模块 + 事件类型 + 过滤配置 + 会话键规则）/ **内部队列事件**（关注哪个业务的哪类产出）/ **定时**（§5）。可配多个入口 | 是 |
| 出口（可选） | **格式统一**：结果一律包装成标准信封放回任务队列。当前业务**不知道也不关心谁关注了自己**——关注是下游的声明；需要自己触达外部时，由「企微通知」这类出口型业务关注并代发（机器人按场景选：通知类用 webhook 机器人，交互类用智能机器人） | 否 |
| 提示词（总纲） | 见 §3 | 是 |
| 关注与依赖 | **关注**：声明本业务消费哪个业务的哪类产出（即成为其下游）；**依赖**：声明前置业务，并可配置「前置失败时本业务是否执行」（**默认不执行**）（见 `design/processing-chain.md`） | 否 |
| 通用配置 | 平台级默认值；业务配置可与通用配置重合，**业务配置优先级更高**。首条落地项：agent 超时（默认 60 分钟） | 否 |
| 环境变量 / 安全变量 | **通用 key-value**；安全变量运行时注入、不落盘不进日志 | 否 |
| GitHub / 企微 / Jira 设置 | **专用 key-value**（仓库地址与权限、机器人配置、站点与凭证），按业务隔离 | 否 |

**要点：**

1. 资料与 manifest 一一对应——**控制台创建业务 = 生成/更新一个业务组合体**；
2. 资料模块按需增删，新资料类型 = 新增一个可交互模块，不动控制台骨架；
3. 控制台业务列表即全局有序业务列表，处理链顺序在此可视化维护。

---

## 5. 定时触发

- 两种定时器：**周期定时器**（如每 50 分钟一次）、**绝对定时器**（支持多个，如每天 9:00、12:00）；
- **定时到点 = 包装成任务入队，不直接执行**——并发已满时会延迟，可接受；所有触发走同一条队列，语义统一。

---

## 6. 工作目录与文件树

平台级工作目录（控制台可配置），业务级目录在其下按业务 id 划分子目录：

```
{workspace}/                    # 平台级工作目录（控制台配置）
├── public/
│   └── skills/                 # 公共 skill（内置工具，如 jira 工具）
├── businesses/
│   └── {business_id}/          # 业务子目录（id 不可改，与可改的业务名解耦）
│       ├── skills/             # 私有 skill
│       ├── repos/              # GitHub 拉取的项目
│       ├── assets/             # 其他业务资源
│       └── runs/{run_id}/      # 每次执行的隔离工作区（任务级，运行时创建）
└── logs/                       # 三层日志（见 design/logging.md）
```

规则：公共与私有分离；内部引用一律用业务 id；`runs/` 由运行时创建，清理策略属实现期细节。

---

## 7. 账号体系

- **标准账号**：注册、登录、管理；
- **两种角色**：**admin**（维护公共内容：公共 skill、公开配置、账号管理）与**普通成员**；
- **账号 → 多业务**：每个账号可创建和管理多个业务（如 sdk 账号、后端账号分属不同团队，各管各的业务）；
- 数据库账号与业务数据均存 SQLite（见骨架 §4）。

---

## 8. 监控与统计

| 项 | 约定 |
|----|------|
| 并发监控 | 控制台实时显示当前并发执行数（通道并发情况）；**最大通道并发数在控制台设置**（见 `design/scheduler.md`） |
| 资源监控（CPU/内存/容器） | **直接使用 Portainer**（Docker 控制台，自带 UI），不重复造轮子 |
| 任务监控 | 以业务为单位：任务列表、业务标记（创建/进行中/成功/失败/超时）、维护性干预（终止、重试） |
| 结果统计 | 每个业务可按结果契约输出二维表；**缺省为按日期的调用统计**：成功/失败/超时次数（取自业务标记）+ 通用属性（token 调用量、调用耗时） |
| 日志检索 | 按 event_id / lifecycle_id / 通道键 / correlation_id 检索（见 `design/logging.md`） |

---

## 9. 数据隔离

业务是隔离单位，五项边界：

1. **配置与密钥**——按业务注入，业务之间不可见（通用/专用 key-value 同规则）；
2. **会话与生命周期数据**——按业务命名空间隔离；
3. **执行 workspace**——按运行实例隔离（`runs/{run_id}/`）；
4. **仓库绑定**——仓库地址与凭证按业务绑定，平台内部对仓库可管理、可隔离；
5. **结果数据**——按业务归属，互不串扰。

## 11. MVP 范围

做：账号体系（admin + 普通成员）、业务创建与配置（§4 资料模块，含叹号提示）、关注与依赖配置、定时触发、并发监控与上限设置、任务监控（业务标记 + 干预）、结果缺省统计（按日期）、Portainer 资源监控、agent=pi / 模型=qwen3.8max（注册表驱动）。

不做：定时通知出口类型、拖拽编排、二维表图形化、跨业务联合分析、多 API Key 管理、平台级共享连接。
