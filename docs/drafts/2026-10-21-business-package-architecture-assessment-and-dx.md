## 2. 关键史实（评估依据）

- 业务包与平台的边界是**语言无关协议**而非 TS 接口：stdin 一段 JSON（`StdinEnvelope`）/ stdout 唯一结果（`StdoutResult`）/ stderr `__biz_log` 日志行；SDK ↔ AgentService 走 per-run unix socket 一行一 JSON。见 t10 spec。
- agent 调用只能经 AgentService（pi spawn 在平台侧 `packages/agent-service/src/pi-runner.ts`）；凭据不进业务进程；四道机械防线（子进程隔离/超时强杀/输出上限/配额）。
- skill workflow（流程 DSL）已于 2026-09-27 否决，决策记录 `docs/decisions/2026-09-27-business-workflow-code-as-workflow.md`，转向代码即流程。
- 资产模型：git 仓库 + `agent-package.json` 清单 + 物化（平台不理解构建，只验收产物，初始化归 `agent.materialize.mjs`）。
- pi 已落地为 npm 依赖（2026-10-21，PROGRESS 最后一条），路径自解析、版本精确锁定，子进程执行不变。
- SDK 是普通 npm 依赖（不注入不 bundle），业务开发与运行用同一份代码（模板 README §3，t15 + 物化重构后的形态）。

## 3. 已定论：暂不支持 Python（后续有变化再说）

**结论**：多语言在架构上"近"而非"远"，但当前不做；未来若做，路径已探明。

**推理过程**：

- workflow-runner 与业务包之间是语言无关协议，真正绑定 Node 的只有四点：runner spawn 写死 node、manifest 校验 `.js`、物化入口固定 `node agent.materialize.mjs`、SDK 只有 TS 版。四点都可泛化。
- 但更关键的事实：**Python 业务包根本不需要自己面对 pi/codex CLI**——内核在平台侧 AgentService 之后，业务只讲 socket 协议。这里有个容易混淆的点值得记录：「能不能调用 CLI」与「能不能把 CLI 当依赖管」是两回事。pi/codex 官方都提供语言无关的 stdio JSON 接口（pi `--mode rpc`；codex `exec --json` / `app-server` JSON-RPC / 官方 `@openai/codex-sdk`），Python 直接驱动它们完全可行——但那会把它们降级为"工具"（靠 PATH 定位、版本不受项目控制）。本项目架构让依赖管理留在平台侧 npm，与业务语言解耦，上次的 npm 依赖化收益（版本锁定、路径自解析）因此不随业务语言退化。
- 成本核算：多语言化的真实成本不在架构改造，在**双 SDK 长期同步**（协议每加一个字段两个 SDK 都改，需跨语言契约测试矩阵）与 **Python 依赖治理**（无 esbuild 等价物，venv 是运行期实体）。当前无真实 Python 业务需求，不为假想需求付这个钱（AGENTS.md 核心原则 1/5 的直接应用）。
- 未来最小路径（若需求出现）：runner 启动泛化 + manifest runtime 字段 + 物化入口泛化 + Python SDK stdlib 实现（socket 客户端用标准库 `socket` 即可）。

## 4. 架构评估结论（高层视角）

### 4.1 独特性没有想象中高——这是好消息

**推理**：把架构拆开，每个零件都有成熟 prior art——一入一出 + spawn 隔离 ≈ Lambda/Actions job 调用模型；agent 经 socket 代理 ≈ Dapr sidecar / LLM Gateway；skill 资产 ≈ Agent Skills 开放标准本身；资产 git + 清单 + 物化 ≈ buildpack 轻量版；代码即流程 ≈ Temporal 战胜 DSL 的那场仗。独一无二的只是"面向 LLM 工单流水线"的**组合**。

**为什么这是好消息而非打击**：① 每个零件单独都被验证过，架构风险低；② 叙事成本低——不需要说服别人接受陌生思想，只需让他们认出已知模式的组合，这对"别人是否认可"这个担忧是直接解药；③ 评审答辩材料现成（决策文档的 DSL vs 代码对比表）。

### 4.2 真正做对的三件事

1. **契约薄，双向可迁移**。平台承诺面只有两个 JSON，业务不 import 平台任何东西。代价是锁定弱（业务迁走容易），收益是采纳门槛极低。为什么这个取舍在当前阶段正确：平台还没形成生态，锁定换不来任何东西，门槛才是采纳的瓶颈。
2. **护城河在内核代理层**。AgentService 独占凭据/配额/会话/审计，业务代码完全不可信这个前提因此成立，四道机械防线才有意义。"SDK 是约定层不是封锁层，真边界画在系统层"这句诚实判断值得保留——它比假装 SDK 能封死业务的设计更能经受评审。
3. **取消 DSL 今天看更正确**。除决策文档已列的理由（表达力逃逸、平台变解释器、无法本地单步调试）外，2026 年权重极高的一个论点：**业务代码的作者越来越是 AI**。私有 DSL 是 AI 必须额外学习、且最易幻觉的东西；"读 stdin JSON 写 stdout JSON 的 TS 程序"在每台 LLM 的训练分布里。这套架构 AI 可全程自助编写、调试、排错，拖拽/DSL 平台不具备此属性。这个论点当时没被充分强调，应作为对外叙事的一部分。

### 4.3 诚实的弱点（按当前目标重排）

1. **业务包缺少真实独立运行能力**。输入侧 pipe JSON 已可行，但 `sdk.agent()` 需要 socket endpoint；模板目前能构建、检查和做契约测试，却不能通过一条真实运行链路完成模型调用并呈现结果。大多数业务问题本可在开发者本机快速暴露，现在却要推上平台才能验证。
2. **状态与人工介入是架构性留白**。一入一出 + 失败整体重跑对分钟级工单成立；"审批后继续/等回调"技术上 = 入口再触发新 run + 业务自恢复状态，走得通——但目前无任何文档把它作为 pattern 教给业务。不补的后果：第一个遇到这需求的业务会认为"平台不支持编排"，尽管这是当年主动放弃的，感受上却是平台的缺陷。
3. **可观测性不对称**。平台知道 run 成败、不知道业务死在哪一步；步骤打点未升格为约定，平台管理员给业务方排错时隔着一层。
4. **知识供给与采纳漏斗仍有断点**。参数说明、开发文档、控制台提示和排错内容尚未形成统一来源；错误消息散落，无"错误目录 → 怎么办"自助排错页；run 期机械失败到 console 的呈现链路待验证。

**为什么这样排序**：独立运行是每个业务开发者、每次迭代都会经过的路径；状态与人工介入是特定复杂业务才遇到的需求。先打通高频开发闭环，再补复杂 pattern 与持续运营能力。v1 把状态留白排在独立运行之前，v2 修正这一判断。

## 5. 业务包运行与开发者体验（核心目标共识草稿）

### 5.1 业务包必须能真实独立运行（不是 mock）——最高优先级设计目标

**核心定义**：

> 业务包本来就是一个可执行程序。把原来由入口适配器提供的输入直接交给它，满足真实依赖，让它真正完成工作，再把原本交给出口通知器的结果直接展示出来。

**独立运行 = 真实业务程序 + 明确输入 + 真实依赖 + 可见输出。** 输入可以是虚构数据，业务执行不能是仿真。

**同一个业务包的两种运行模式**：

1. **手动运行**：业务开发者自行准备样例/重放输入、模型配置和其他必要参数，真实执行核心业务，直接查看输出、日志和错误。目的是开发、验证核心逻辑和复现问题。
2. **平台运行**：业务包内容不变，输入改由入口适配器或上游业务提供，输出交给出口通知器或下游业务；平台另外提供持续触发、排队、串行、审计和治理。目的是让业务真实、持续地工作。

**为什么这是最高优先级**：易用不只是"本地能调试"，而是"开发者验证过的同一份业务资产可以无修改地投入生产；线上输入也能带回手动环境复现"。这条闭环直接决定业务开发效率，也验证"业务包是核心产品单元，平台是它的运行与治理环境，而不是它能否运行的前提"。

**同构约束（目标验收标准）**：

- 两种模式使用同一个业务包版本、同一份入口代码、同一套 SDK 和真实业务依赖；不允许 `if (local)`、`main.local.ts` 或另一套模型调用路径；
- 执行边界统一为 `入口适配器 → [业务程序 + 真实依赖] → 出口适配器`。手动运行只替换左右两侧，中间不变；
- 手动运行输入位于**入口适配完成之后、交给业务进程之前的边界**，使用与该边界一致的事件信封；输出取自业务 `sdk.return` / `sdk.fail` 之后、出口投递之前的结果；
- 是否复用 WorkflowRunner、怎样提供本地 AgentService，是实现选择，不得反过来缩小同构目标。

**输入来源与"不是 mock"**：

- 手写样例：按业务输入规则准备的最小可用数据，随业务包版本维护；
- 线上重放：从真实线上日志取得事件信封，脱敏后在手动环境复现；如果拿的是原始 webhook 请求，会额外混入验签、解密和归一化，那是入口适配器调试，不是纯业务调试；
- 自定义输入：开发者为边界条件临时编写；
- 这些都只是输入数据，不替换业务、模型或工具。**mock 与单元测试是可选的工程质量手段，不是独立运行的前置条件，是否编写由业务开发者负责。**

**真实依赖与模型配置语义**：

- 业务开发者可以提供大模型所需的模型选择、API key 等配置；独立运行时由开发者直接准备，平台运行时由同一套配置语义供给；
- **配置由谁提供，不等于由哪段代码消费**。业务代码仍只走 `sdk.agent()`；模型凭据交给相应 agent 运行组件，不要求业务代码直接读取 key 或直连 pi；
- 用户配置优先，平台通用配置可作为后续缺省值能力。独立运行第一闭环不依赖平台通用配置是否已经实现；
- 回退只应发生在"用户未提供"时；用户明确提供但配置非法，应报错而非悄悄改用平台默认。运行前应能查看脱敏后的有效配置与来源，避免模型、费用和数据去向不符合预期；
- 当前实现是否已完整支持上述配置语义，需要另做差距清单。**现状差距不构成降低设计目标的理由。**

**参数的易用性边界**：开发者只准备有业务意义的输入——事件/payload、业务 config/secrets、模型与 skill/tool 配置等；`run_id`、workspace、socket token、correlation_id 等机械字段必须由启动工具生成。不能要求开发者手填整段平台内部信封，否则"理论上可运行"仍不等于好用。

**手动运行不承诺覆盖的平台集成行为**：入口验签与解密、队列幂等、通道串行、并发、结果扇出、真实通知投递与重试仍由平台集成验证。明确这条边界不会削弱独立运行，反而使其目标清晰。

**完整验收不能停在 hello agent**：至少还要用一条包含真实 `sdk.agent`、skill、`sdk.run` 工具、dataDir、日志和出口门禁的业务验证，证明独立运行不是只对简单范例成立。

### 5.2 业务包 I/O、参数说明与样例输入

- **诉求**：业务包必须明确说明输入要求、输出要求和必要启动参数；同一份内容服务业务开发、手动运行与控制台使用，绝不重复维护。
- **为什么"不维护两份"是硬要求**：两份内容必然漂移。控制台是配置时看到的，文档是开发时看到的，答案不一致会直接破坏用户对平台的信任。
- **一件事一个权威出处，不等于所有信息放进一个文件**：业务包拥有自己的业务 I/O 与参数说明；平台继续拥有通用入口适配器 eventDoc、出口工具 resultDoc 与配置规则；控制台按当前页面组合引用，不能把通用适配器说明复制进每个业务包。
- **说明与机器规则分工**：说明文字、注意事项和排错指引适合以文档为源；表单字段、I/O schema 与机械校验需要结构化定义，控制台不能从自然语言里猜行为。哪些内容由 Markdown 生成、哪些由 schema/类型生成文档，在具体设计中按事实类型决定。
- **参数说明的最低内容**：必填/可选、含义、示例、默认值、是否敏感、用户配置与平台默认的关系、缺失或非法时的表现。存储位置待定，但这些语义必须可供手动运行和控制台共同使用。
- **样例输入是两个目标的明确交点**：同一份样例可用于文档展示、手动真实运行，以及（若控制台提供手动触发）预填触发数据；线上脱敏事件也保存为同格式输入。它可展示、可执行、可校验，而不是文档里的死代码块。
- **同源还必须同版本**：控制台展示业务绑定的 commit 所对应的文档与样例，不读取开发者电脑上的文件，也不拿仓库最新分支解释旧版本业务。
- **v2 对 v1 的修正**：I/O 声明可以供给输入、输出和参数说明，但不能生成真实模型、skill、工具与会话环境。独立运行与文档同源相互协同，却不是同一个功能，也不共用一份配置就自然完成。

### 5.3 平台定位再确认

- **定位句**：平台存在的意义 = 替所有业务做它们不该关注的事——**入口适配、出口通知、agent 内核与凭据治理**。
- **业务包与平台的关系**：业务包是核心产品单元，可以独立验证核心逻辑；平台是它持续运行、事件接入、结果分发和治理的环境，不是它能否运行的前提。开发者手动验证与平台生产运行之间不应发生业务代码迁移或改写。
- **共同设计哲学**：核心资产只维护一份，不同场景通过边界适配使用。业务包是"同一份代码、两种运行模式"，文档是"同一知识来源、多种使用视图"（§6）。
- **为什么需要一句话定位**：独特的组合没有现成品类格子，别人不知道该把平台放进哪个格子比较。用已知词汇的组合（"面向 LLM 工单的 code-as-workflow 运行平台"）自己造格子，写进 README 第一屏，而不是藏在 docs/ 里。
- **边界纪律**：业务包**不自己做投递**（结果由平台扇出）、**不自己写入口适配**（归 entry-adapters）。5.4 的工具包也必须遵守这条纪律。

### 5.4 基础工具包化

- **诉求**：业务除 sdk 外，还应能引入平台提供的独立工具包：jira、github、邮件等。**用途是真实提升开发效率**（取数、写回等通用操作），**不是让业务自己写入口出口**。
- **为什么强调用途**：工具包一旦越界成"出入口积木"，业务就会拿它绕开平台的出入口治理（凭据、扇出、审计），平台定位（5.3）被掏空。邮件等发送能力只有作为明确的业务动作时才属于工具用途，不能替代 `sdk.return` 之后由平台负责的结果通知与扇出。这条纪律要写进工具包规范。
- **落地形态**：业务可能用到的基础工具沉淀为平台维护的**共享工具资产**（`shared=true`、随平台版本演进、绑定期校验覆盖）。
- **纪律（待细化）**：工具尽量纯逻辑零依赖；需要模型能力的环节经 `sdk.agent`，工具内不私嵌 LLM 调用与凭据。
- **价值判断**：工具采用量本身不是充分证据。更应观察新业务减少了多少重复胶水代码、从 clone 到第一次真实跑通需要多久、修改一次业务后多久能看到真实结果，以及同一工具在手动运行与平台运行中的行为是否一致。
- **与独立运行的关系**：完整工具生态可以后建，但手动运行必须能解析并执行当前业务真实引用的 skill/tool；否则只能证明简单范例可运行，不能证明真实业务可独立开发。

### 5.5 模板最小化要求（新增，2026-10-22；v2 重排）

**为什么现在要谈"最小化"**：模板是业务开发者看到的第一个东西，它的每一项要求都会变成业务作者心里的"平台规矩"。要求不清 → 作者要么过度敬畏（把工程实践当平台强制），要么过度轻视（删掉平台真正依赖的东西导致物化失败）。最小化要求必须显式分层：**哪些是平台硬性依赖（删了必坏），哪些是模板工程实践（删了可惜但不坏）**。

**平台硬性最小集**（物化与运行依赖，全部机械可验，缺一不可）：

1. `agent-package.json`：合法 JSON 对象；name/version/programs（值 = 相对包根路径）形状合法（validate.ts 校验）；
2. `agent.materialize.mjs`：package/tool 资产必带（skill 资产不需要）；跑完后 programs 每条路径真实存在；
3. programs 指向的入口是 node 可执行的 JS（清单扩展名规则）；
4. 运行时隐式契约：入口程序遵守一入一出——平台在运行期验收结果与退出行为，模板骨架负责教会推荐写法；契约测试可以辅助验证，但不是平台准入条件。

**模板最小体验承诺**（DX 层，非平台强制）：

- 拷贝后有明确的参数说明、样例输入和真实手动运行入口，运行结果、日志与错误可见；
- 手动运行与平台运行使用同一入口、同一业务代码，不附赠另一套 local 实现；
- 骨架程序承载契约与典型环节约束（注释即文档，见 §5.6）；
- 单元测试、mock、契约测试均由业务开发者按需要选择；模板是否提供可选示例另议，不把它们列为独立运行或平台准入的前置条件。

**待裁剪讨论**（开放问题，见 §8）：tsconfig/eslint/jest/prettier 四个配置文件、骨架 tests、六条检查是否对"胶水级"业务包过重？裁剪的判据 = 砍掉某项后，作者失去的是"平台保障"还是"工程舒适"。凡是平台没有机械强制的检查，不应仅因模板自带就被作者理解为平台规矩。v1 把 e2e 契约测试列为模板最小体验承诺，v2 撤销这一定位。

### 5.6 典型组件：入口检查、出口门禁（新增，2026-10-22）

- **诉求**：业务包里的典型组件应该包括**出口的门禁、入口的检查**。
- **与既有决策的关系**：2026-09-27 决策已明确检查/门禁不是平台挂接点（"平台钩子"概念被吸收），它们是**流程程序内部的环节**。本诉求不推翻该决策，落实位置在模板与范例层：骨架程序的阶段性结构 + 范例业务演示推荐写法。
- **推荐结构（写入模板骨架注释）**：
  1. **入口检查**：事件形态校验（字段存在性/类型）、来源合法性（白名单/关键词）、负载预处理（脱敏在检查通过后进行）；
  2. 业务主体：取数 → 脱敏 → `sdk.agent` → 还原；
  3. **出口门禁**：对将返回平台的结果做最终检查（敏感词/长度/格式/schema），两种失败语义要明确区分——**阻断**（`sdk.fail`，run 失败，平台按失败传播）vs **降级**（改返回降级内容，run 仍成功）——默认推荐哪种、何时用哪种，范例必须给出。
- **为什么门禁语义要写在范例里**："门禁不过怎么办"是业务第一个真实问题，不写就被每个业务各自发明，行为不一致。
- **与 5.4 的关系**：通用门禁能力（如敏感词表）将来可下沉为共享工具资产；但**门禁判断属业务语义**，默认留在业务内，平台不预置门禁策略。

### 5.7 范例业务：企微 + 大模型聊天（新增，2026-10-22；v2 增加双运行验收）

- **诉求**：提供一个示例业务包——使用企业微信和大模型聊天。
- **这个范例为什么选得好**（它一次演示五件事）：
  1. **双运行模式**（5.1）：同一份业务包先通过样例输入 + 真实模型手动运行并查看回复，再不改代码交给平台运行；
  2. **出入口分工**（5.3）：入口 = webhook 入口适配器（企微消息归一化为事件信封），出口 = 企微群机器人 webhook 出口绑定，**业务代码完全不碰适配**；
  3. **典型组件**（5.6）：入口检查（是否@机器人/关键词/消息体校验）+ 出口门禁（模型输出敏感词/长度检查，不过则降级回复）；
  4. **多轮会话**：`sdk.agent({ mode: 'channel' })` 演示会话延续，顺带展示 `session.compact/clear` 的使用场景；
  5. **I/O 与样例**（5.2）：企微消息体就是天然的"输入要求"示例，输出 = 回复文本及当前出口契约已支持的补充字段；样例同时用于文档与手动运行。
- **平台运行目标形态**（实现时细化）：入口 webhook 收消息 → 入口检查 → sdk.agent(channel) → 出口门禁 → `sdk.return` → 平台扇出到企微群机器人。
- **手动运行目标形态**：样例/重放事件 + 开发者提供的真实配置 → 同一个入口检查、业务主体与出口门禁 → 本地可见的成功结果或失败原因；不经过企微适配器，也不实际通知。
- **开放问题**：真实企微回调（URL 验证 + AES 解密）是 entry-adapters 的新适配器，还是范例先用通用 webhook 入口 + 企微消息体示例即可？前者工作量大但真实，后者一天能跑通。倾向后者优先（范例的目的是教业务包，不是做企微集成）。

## 6. 文档架构：一套知识来源，多种使用方式（v2 新增核心目标）

### 6.1 目标不是一篇大文档，而是一套完整知识体系

> 每项事实只有一个权威出处；同一套知识内容，按平台开发者、业务包开发者、业务使用者的任务生成不同视图。维护一处，就能服务开发、配置、控制台提示与排错。

- **平台开发者**需要架构边界、契约、配置解析、兼容规则和维护方法；
- **业务包开发者**需要模板、必要参数、SDK、手动运行、示例与发布流程；
- **业务使用者**需要创建与配置业务、理解输入输出、处理常见失败，不应被迫先理解 socket、物化和子进程。

**同源不等于同视图，也不等于同一阅读顺序。** 统一的是事实，不是把所有内容原样推给所有人。目标也不是用一篇架构文档覆盖所有细节，而是让日常开发和维护所需的有效知识都能从这套体系获得，不再翻旧稿、对比重复说明或询问设计者。

讨论稿、决策记录和历史设计仍有价值，但只用于追查演进原因，不再是理解当前有效规则的必读前置。文档由此从辅助材料升级为平台的一部分：有明确内容源、有生成、有校验、有版本、有消费方。

### 6.2 先设计内容归属与信息架构，再选择 Wiki 框架

- 目录应优先按读者任务与平台概念组织，而不是照搬代码包目录；否则业务使用者必须先理解平台实现才能找到配置说明。
- 平台通用知识、业务包自有 I/O 与参数说明分别归各自维护者所有，控制台按场景组合引用（见 §5.2）。
- 只有**显式导出**的段落才能进入控制台或其他公开视图，默认不公开内部讨论、实现细节与决策材料。
- Wiki 是可能的承载和阅读形式，不是同源本身。若内容归属、版本与消费关系没设计好，只搭 Wiki 仍会重复维护。

### 6.3 单向文档生成流水线（初步方向）

```text
人工维护的文档源 / 结构化契约
        ↓
解析、提取、校验、生成
        ↓
Wiki / 开发指南 / 控制台内容包 / 可执行示例
```

- **单向生成而非双向同步**：生成物不允许手工另改，控制台说明不能脱离源头单独编辑，否则很快重新出现两个事实源。
- **实现可以从 JS/TS 小工具开始**：第一阶段解决段落提取、锚点检查与目标格式生成，不预设引入重型文档平台。
- **推荐在平台文档发布或业务包物化时生成结构化内容**，而不是控制台每次打开页面临时解析 Markdown。这样控制台只消费稳定格式，版本、缓存、异常和安全渲染更容易控制。
- **文档不接管控制台 UI**：文档负责说明、示例、注意事项和排错；控制台代码负责布局、交互、权限与流程；表单字段和机械校验仍由结构化定义承载。避免把文档标记膨胀成私有 UI DSL。
- **不是所有事实都必须以 Markdown 为源**：说明文字可由 Markdown 生成目标内容，机器契约可由 schema/类型生成文档。一项事实不重复维护，比强求只有一种源文件更重要。

### 6.4 文档维护者与控制台开发者也必须好用

如果同源只减少代码里的重复字符串，却让文档难维护、控制台引用容易坏，最后仍会退回复制粘贴。生成体系至少需要：

1. **稳定语义锚点**：控制台引用 ID，不引用文件路径、标题或行号；标题润色、段落移动和文件重组不应迫使控制台跟随修改。
2. **作者预览**：能同时看到 Wiki/指南与控制台中的最终呈现，不必写完再猜效果。
3. **自动校验**：重复 ID、失效引用、错误链接、非法样例能够在生成期发现；控制台引用不存在的段落应使检查失败。
4. **生成可重复**：同一输入生成同一输出，无无关差异；生成物明确标识"请勿手改"。
5. **版本一致**：平台通用文档随平台版本发布，业务包文档随绑定 commit 物化，不用最新文档错误解释旧运行版本。

### 6.5 用任务闭环验收文档，而不是用篇幅验收

1. 平台开发者只看这套文档，能否理解边界并完成一次平台能力维护；
2. 业务包开发者只看这套文档，能否从模板开始，配置真实模型，手动运行成功，再无修改地部署到平台；
3. 业务使用者只看控制台及其中同源内容，能否完成配置、理解输入输出并处理常见失败。

**建议的首个垂直范例**：以"业务包独立运行"为内容源，生成业务开发指南、必要参数说明、控制台相关提示与同一份样例输入。先验证这条链路，再扩展到完整 Wiki，避免一开始建设庞大文档系统却没有真实消费者。

## 7. 后续投入顺序（v2 建议，待确认）

v2 不再把 mock endpoint 放在首位，也不把业务运行与文档体系硬排成一条互相阻塞的队列。两条主线可分别收敛，在样例输入与参数说明处汇合。

**A. 业务包真实运行主线**：

1. 真实手动运行最小闭环：样例输入 + 必要参数 + 真实 agent + 可见输出/日志/错误；
2. 配置解析与优先级语义、I/O/参数说明、线上事件重放格式；
3. 企微聊天范例验证双运行模式，再用包含真实 skill/tool/dataDir 的 Jira 业务做完整验收；
4. 模板最小化定稿，将手动运行入口与说明置于测试设施之前；
5. 示例业务库、人工介入/长流程 pattern、步骤打点、错误目录与基础工具生态。

**B. 文档与控制台同源主线**：

1. 内容盘点、读者任务、目录与事实归属；
2. 用独立运行主题完成第一个"文档 → 生成物 → 消费者"垂直切片；
3. 控制台内容消费、锚点校验、版本绑定与作者预览；
4. 扩展到稳定的 Wiki、适配器参考与错误目录。

**排序理由**：先让真实业务闭环与真实文档消费者出现，再抽象通用能力。v2 也不再预设所有改动都是"纯外围增量"；如果现状与同构目标存在配置、装配或发布差距，先形成差距清单，涉及既有契约的重大变化另行分析并确认。

## 8. 开放问题（待后续讨论）

### 8.1 独立运行与配置

- 手动运行的命令与配置载体是什么？本地 AgentService 如何启动、复用和发布，怎样避免形成第二套业务执行路径？
- 用户配置、平台通用配置与单次运行参数的完整优先级如何定义？如何展示脱敏后的有效值与来源？平台侧允许模型、配额与费用策略如何约束用户覆盖？
- 当前模型配置、API key 供给与平台通用配置分别实现到什么程度？差距需要逐项盘点，不在讨论稿里假定为已完成。
- 哪些机械字段由启动工具生成？本地 workspace/dataDir、会话映射、日志与审计如何布局，怎样支持连续手动运行和问题复现？
- 线上事件在哪一边界采集、怎样脱敏、怎样保存为可重放样本？成功输出与失败原因以什么形式展示和保存？
- I/O 与参数说明的载体及 schema：进 `agent-package.json`、独立约定文件还是生成产物？与 `contract_version` 的关系和版本演进纪律是什么？

### 8.2 文档与生成体系

- 稳定知识库与现有 drafts/designs/specs/decisions/refs 如何分工和迁移，日常入口是什么？
- 文档目录按哪些读者任务组织？平台通用内容与业务包内容分别由谁维护、审核和发布？
- 语义锚点采用什么标记语法，导出段落边界怎样表达？怎样做到作者少写标记、控制台不依赖脆弱标题？
- 生成物的格式、生成时机、是否入库、控制台读取方式和 Markdown 安全渲染边界是什么？
- 作者预览、控制台引用检查、样例校验与版本绑定怎样进入现有构建/物化流程？
- 哪些事实以 Markdown 为源，哪些以 schema/类型为源？怎样避免生成器扩张成私有 UI DSL？

### 8.3 既有议题保留

- 模板裁剪清单（5.5）：四个配置文件、骨架 tests、六条检查逐项判定；可选测试示例是否保留，不得变相成为平台准入条件。
- 门禁失败语义（5.6）：阻断 vs 降级的默认推荐与范例写法。
- 企微范例的入口形态（5.7）：真实企微回调适配器 vs 通用 webhook + 消息体示例。
- 人工介入/长流程 pattern 文档的写法（新 run 恢复状态的推荐姿势）。
- 基础工具包的归属、发布渠道与版本纪律；npm 依赖包、平台 tool 资产、业务 package 的术语与适用边界需保持清晰。
- console 手动触发 run（样例/重放事件）是否已有、没有则排期。
- 对外定位句（5.3）的最终确认。
- 用例密度：第 2、3 个真实业务何时上——独特性的解药是用例，不是文档。
